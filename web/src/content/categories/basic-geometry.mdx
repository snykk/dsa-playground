## The problem

Almost every geometry algorithm reduces to a few questions about points. How far apart are they? Does the path `a -> b -> c` turn left or right? Does a point lie inside a shape? Do two segments meet? This section answers them with the least machinery possible.

Both topics rest on one function, the cross product `cross(o, a, b) = (a.x - o.x)(b.y - o.y) - (a.y - o.y)(b.x - o.x)`. Its sign says on which side of the line from `o` to `a` the point `b` lies: positive on the left, negative on the right, zero on the line.

What the code actually does:

- Every test compares a cross or dot product with zero. There is no epsilon, so a result does not depend on the scale of the coordinates.
- With integer coordinates the tests are exact in Python. In C++ and Go they are exact while the products stay below 2^53.
- Collinear and degenerate input is handled on purpose. A zero-area triangle contains no point, and a zero-length segment is treated as a point.

The last row shows why the two functions are separate. `line_intersection` always returns the meeting point of the infinite lines, even when it lies outside both segments. Orientation codes follow the same exact rule. `orientation((0,0), (2,2), (4,4))` is 0, `orientation((0,0), (4,0), (4,4))` is 2 (counterclockwise) and `orientation((0,0), (4,4), (4,0))` is 1 (clockwise).

## Applications

- **Graphics and games.** Hit tests, collision checks and clipping.
- **Maps and GIS.** Point in polygon, route crossing and distance checks.
- **Robotics and CAD.** Line of sight and the intersection of edges.
- **Higher geometry algorithms.** The convex hull, rotating calipers and closest pair all call `cross_product`.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **An absolute epsilon on the cross product.** It is a length squared, so a fixed threshold treats tiny shapes as degenerate. These topics compare with exact zero instead.
- **Using acos for the angle.** It loses precision near 0 and pi. The code uses `atan2(|cross|, dot)`.
- **Dividing before deciding.** Computing the parameters `t` and `u` first loses touching and collinear cases. Test orientations, then compute the point.
- **Skipping the box check for collinear points.** A zero orientation says only that a point is on the line, not that it is between the endpoints.
- **Reading `line_intersection` as a segment test.** It works on infinite lines.
- **Assuming that decimals are exact.** Exactness holds for integer input. Rounded decimals can still look nearly collinear.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Point, Line and Circle first. It introduces the cross product and orientation. Line Intersection then uses both, and is a good first use of them.
  </FaqItem>
  <FaqItem question="Why no epsilon?">
    A tolerance depends on the scale of the input and makes tests inconsistent, for example it can call a pair of lines parallel at a small scale. Exact tests on integer input have none of these problems. For non-integer input convert to integers if you can, or choose a tolerance yourself.
  </FaqItem>
  <FaqItem question="What happens with a zero-length segment?">
    It is a point. The orientation tests handle it, so `segments_intersect` is true when that point lies on the other segment. A parametric formula would divide by zero.
  </FaqItem>
  <FaqItem question="Where do these functions show up later?">
    The convex hull uses the cross product to find turns. Rotating calipers uses it for areas, and the closest pair solution relies on distances. See Advanced Geometry.
  </FaqItem>
</Faq>
