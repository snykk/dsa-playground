## What this area covers

A DP solution has four parts: a state that names a subproblem, a transition that builds its answer from smaller states, an order that computes the smaller ones first, and base cases. The method pays off when two conditions hold:

- **Overlapping subproblems.** The same state is needed again and again. Without a table, `fibonacci_naive(30)` makes 2,692,537 calls for 31 distinct values.
- **Optimal substructure.** The best answer for a state is built from best answers for smaller states.

Memoization (top-down, with a dictionary) and tabulation (bottom-up, with an array) are two ways to store the answers. Both give the same result. Most topics here ship a table version, and some also a memoized or a space-saving one.

The five areas below are sorted by how the state looks, not by difficulty alone.

## A path through the area

1. **Basic DP.** Read Fibonacci first: it shows why the table exists, because naive recursion repeats work exponentially often. Climbing Stairs applies the same recurrence to counting.
2. **Linear DP.** The state is still one index, but the transition now chooses among several earlier states. Coin Change is the first problem where greedy fails.
3. **2D DP.** Two indices describe a state. LCS and Edit Distance share one table shape, 0/1 Knapsack uses it for items and capacity, and Matrix Chain fills intervals by length.
4. **Advanced DP.** The state is no longer a pair of numbers. It is a subset stored in an integer, a digit position, a tree node or a node of a DAG.
5. **DP optimizations.** Once a recurrence is right but too slow, exploit its structure. The Convex Hull Trick turns a minimum over all earlier lines into an amortized O(1) step.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Using greedy because it looks natural.** For coins `1, 3, 4` and amount 6, largest-first uses three coins, while `coin_change_min_coins` returns 2.
- **Reading a pseudo-polynomial bound as polynomial.** Knapsack and Coin Change run in O(n*W) and O(n*A), which depend on the value of the capacity or amount, not on the number of digits it has.
- **Filling the table in the wrong order.** Each state must see its inputs already computed. A one-row knapsack loops capacity downward so each item is taken once, and a one-row Coin Change loops upward so a coin can repeat.
- **Hitting limits of the host language.** C++ and Go Fibonacci are exact only up to `F(92)`, and the tree and graph DP recurse once per level, so a path of about 1,000 nodes reaches Python's recursion limit.
- **Applying DP to a cyclic graph.** DP on Graphs needs a DAG, and the code raises `ValueError` when a cycle is reachable.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="What is the difference between memoization and tabulation?">
    Memoization starts from the answer you want and stores each subproblem the first time the recursion reaches it. Tabulation fills a table from the base cases upward. Memoization computes only the states that are reached, and tabulation avoids deep recursion and often allows a smaller table.
  </FaqItem>
  <FaqItem question="How do I tell DP from greedy?">
    Greedy commits to one choice per step and never revisits it. DP keeps the answer for every state and combines them. If a local choice can be proved safe, greedy is simpler and faster. Coin Change with `1, 3, 4` is a case where the local choice is wrong.
  </FaqItem>
  <FaqItem question="Where should I start?">
    With Basic DP, then Linear DP and 2D DP in that order. Advanced DP and DP optimizations assume you can already write a state and a transition without help.
  </FaqItem>
  <FaqItem question="Can a table always be made smaller?">
    Often, when a row depends only on the previous row. 0/1 Knapsack drops from O(n*W) to O(W) space and LCS to O(min(m, n)), but then the table is gone and the chosen items or the sequence cannot be recovered by tracing back.
  </FaqItem>
</Faq>
