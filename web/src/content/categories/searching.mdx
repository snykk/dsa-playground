## The problem

Given a collection and a target value, return the index of the target, or `-1` when it is absent. All four algorithms in this section keep that contract in Python. What separates them is what they assume about the data:

- **Linear Search** assumes nothing. It reads elements until it finds the target, so it works on any order and on structures without random access.
- **Binary, Ternary and Interpolation Search** assume the array is sorted and that any index can be read in O(1). With that, one probe can rule out many elements at once.

If the data is not sorted, the sorted searches return a meaningless answer and raise no error. Sorting first costs O(n log n), so it pays off only when you search many times.

Ternary Search makes `2 log3(n)` probes against Binary Search's `log2(n)`, which is about 1.26 times as many, so for plain lookup it loses. Interpolation Search is the only one whose speed depends on the values, not only on `n`.

On even keys Interpolation Search lands almost on the target at once. An absent target below the first key costs it one read, because its loop only runs while the target lies between the first and last element. On the doubling keys the estimate is poor: it reads 10 elements for `2^28`, while Binary Search needs 4. Linear Search reads one element per index plus one, whatever the data.

Extra space is for the iterative versions. The recursive versions use stack: O(n) for Linear Search, O(log n) for Binary Search, about log3(n) frames for Ternary Search, and O(n) in the worst case for Interpolation Search. Linear Search averages `(n + 1) / 2` comparisons when the target is present and every position is equally likely, and `n` when it is absent. Binary Search makes at most `floor(log2 n) + 1` probes.

## Applications

- **Dictionary-style lookups** in sorted arrays and sorted files, with Binary Search.
- **Sequential ids and timestamps at a steady rate**, with Interpolation Search.
- **Small or unsorted collections**, such as a short list of options, with Linear Search.
- **Optimizing a unimodal function**, such as a cost that falls and then rises, with Ternary Search.
- **Binary search on the answer.** Binary Search also works on a yes-or-no test that flips once, which turns many optimization problems into a search.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Searching unsorted data with a sorted search.** The result is wrong and nothing warns you.
- **Computing the middle as `(lo + hi) / 2`.** In C++ and Go it can overflow on huge arrays. The repository writes `lo + (hi - lo) / 2`.
- **Expecting a particular match among duplicates.** The plain Binary, Ternary and Interpolation searches return some matching index. Use the first-occurrence or last-occurrence variant of Binary Search when the position matters.
- **Dividing by zero in Interpolation Search.** When `a[lo] == a[hi]` the estimate has a zero denominator, so the code checks for a flat window first.
- **Trusting Interpolation Search on skewed keys.** On exponential keys such as powers of two it removes about one element per probe and becomes linear.
- **Using Ternary Search for plain lookup.** It makes more probes than Binary Search. Its peak finder also needs a strictly unimodal function: on a plateau it can return the wrong peak.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Start with Linear Search, the baseline, then Binary Search, which most other sorted-data ideas build on. Ternary and Interpolation Search both list Binary Search as a prerequisite, so after it either order works.
  </FaqItem>
  <FaqItem question="Why is Ternary Search not faster than Binary Search?">
    It needs two comparisons per round to cut the range to a third. That is `2 log3(n)` probes, about 1.26 times `log2(n)`, so it is in the same O(log n) class but with a larger constant. It earns its place on unimodal functions, where one evaluation cannot tell you which side of the peak you are on.
  </FaqItem>
  <FaqItem question="When does Interpolation Search beat Binary Search?">
    On large sorted arrays whose values are close to evenly spread. Each probe then shrinks a range of size m to about the square root of m, so it needs about log log n probes. On skewed data it can fall to O(n), so Binary Search is the safe default.
  </FaqItem>
  <FaqItem question="Is a hash table better than any of these?">
    For exact lookups it usually is: O(1) on average and no sorting needed. It cannot answer ordered questions such as the closest value or the first value at or above a target, which Binary Search can, and it uses more memory.
  </FaqItem>
</Faq>
