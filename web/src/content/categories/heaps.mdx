## The problem

A priority queue must hand back the element with the best priority, again and again, while new elements keep arriving. A sorted array makes the read cheap and the insert expensive. An unsorted array does the opposite. A heap keeps just enough order to find the best element at once: every parent is ordered against its children, and siblings are not ordered at all.

The three topics here are three answers to the same job:

- The **min heap** and the **max heap** store a complete binary tree in a plain array. The children of index `i` sit at `2i + 1` and `2i + 2`, so no pointers are needed.
- The **Fibonacci heap** stores heap-ordered trees as linked nodes and postpones all tidying to the moment you extract the minimum.

A heap is not a search structure. Finding an arbitrary value costs O(n), and iterating a heap does not give sorted order.

The Fibonacci heap in this repository is the lazy core only: `insert`, `extract_min`, `peek`, `size`, `is_empty` and `clear`. It has no `decrease_key`, `delete` or `merge`, which are the operations that make a full Fibonacci heap worth its weight.

## The same keys through all three

Insert the keys `9 4 7 1 8 2 6` into each heap, then read the root and extract everything. The results come from running the Python classes.

<DataTable

    ['Max heap', '9', '`9 8 7 6 4 2 1`', 'not shown'],
    ['Fibonacci heap', '1', '`1 2 4 6 7 8 9`', 'none, it is a forest'],
  ]}
/>

Repeated extraction is heap sort: the min heap gives ascending order and the max heap gives descending order. The Fibonacci heap returns the same sequence as the min heap. Building the min heap from the array `[9, 4, 7, 1, 8, 2, 6]` with the constructor, which uses bottom-up heapify, gives the same array as the seven inserts.

Amortized means the bound holds over a whole sequence of operations. One Fibonacci `extract_min` right after n inserts can take O(n) time, because that is when the postponed linking happens.

## Applications

- **Priority queues.** Task schedulers, event simulations and bandwidth management.
- **Heap sort.** Build a max heap, then move the maximum to the end again and again.
- **Top-k queries.** Keep a heap of size k while you stream through the data.
- **Graph algorithms.** Dijkstra and Prim take the closest unvisited vertex from a heap.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Expecting sorted iteration.** Reading the array of a heap in order does not give sorted output; only repeated extraction does.
- **Searching a heap.** There is no order between siblings, so looking for a value is O(n), not O(log n).
- **Building by n inserts.** That costs O(n log n). Bottom-up heapify from an array is O(n).
- **Calling the Fibonacci extract a worst-case bound.** O(log n) is amortized; a single call can cost O(n).
- **Expecting decrease-key from the Fibonacci heap here.** It is not implemented, and the `marked` flag on each node is stored but never used.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Start with the min heap. It shows the heap property, sift up, sift down and bottom-up heapify. The max heap is the same code with the comparison reversed, so it takes minutes. Read the Fibonacci heap last; it needs the min heap as background.
  </FaqItem>
  <FaqItem question="Why is the Fibonacci heap not simply better?">
    Its insert is cheaper, but each node carries four pointers and extract-min must link trees together, so the constants are large. The textbook advantage is O(1) amortized decrease-key, and this repository does not implement it. A binary heap has an O(log n) decrease-key and is usually faster in practice.
  </FaqItem>
  <FaqItem question="Is a heap the same as a priority queue?">
    No. A priority queue is the interface: insert, and take the best element. A heap is one way to implement it. The Priority Queue topic under the queues shows the interface, and the heaps here show an implementation.
  </FaqItem>
  <FaqItem question="Why does build from an array cost only O(n)?">
    Bottom-up heapify sifts down each internal node, starting from the last one. Most nodes sit near the bottom and sink only a short way, so the total work sums to O(n), not n times log n.
  </FaqItem>
</Faq>
