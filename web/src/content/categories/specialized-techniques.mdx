## The problem

A plain scan answers a range query in O(n) and a plain DFS answers a path query in O(n). With many queries that is too slow. Each technique here pays a setup cost to cut the data into pieces, so that a query touches only a few pieces and a few elements.

The techniques split along two lines:

- **The data.** Square root decomposition and Mo's algorithm work on an array. Heavy-light and centroid decomposition work on a tree.
- **How queries arrive.** Square root decomposition answers each query as it comes (online) and allows point updates. Mo's algorithm needs every query up front (offline) and the array must not change. Heavy-light decomposition is online on a fixed tree shape. Centroid decomposition is a divide-and-conquer on a fixed tree.

A heavy-light path query that also asks for a sum, with a segment tree over the positions, costs O(log^2 n): O(log n) segments, each a range query in O(log n). That segment tree is not part of this repository. The centroid query cost is the template in the topic article, where each vertex has O(log n) centroid ancestors.

## Applications

- **Competitive programming.** All four are standard tools for range and tree queries with large limits.
- **Offline analytics.** Mo's algorithm answers batches of distinct-count or frequency queries on logs.
- **Hierarchies.** Heavy-light decomposition gives the LCA and path aggregates on trees such as organisation charts or file systems.
- **Network and road trees.** Centroid decomposition answers nearest-facility queries after each facility is marked.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **A block size of 0.** `sqrt(0)` is 0 and `i // 0` fails. Both array topics use a minimum block size of 1.
- **Using Mo's algorithm online or with updates.** It sorts all queries first and assumes the array never changes.
- **Shrinking Mo's window before expanding it.** The window can go invalid and a count can go negative. Expand first.
- **A slow add or remove in Mo's algorithm.** An O(log n) step makes the total O((N + Q) sqrt N log N).
- **Treating `pos` as the vertex id.** Segment tree indexes in heavy-light decomposition are `pos[u]`, not `u`.
- **Stale sizes or a missing removed flag in centroid decomposition.** Recompute sizes for each piece and never walk back into a removed centroid.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Square root decomposition first: it introduces blocks and the sqrt(n) balance. Mo's algorithm builds on it and on the two-pointer idea. The two tree techniques are independent of those two. Read heavy-light decomposition first, because it is the more common one, then centroid decomposition.
  </FaqItem>
  <FaqItem question="Why sqrt(n) for the block size?">
    A query scans up to two partial blocks of B elements and up to n/B whole blocks. B + n/B is smallest when B is about sqrt(n). Mo's algorithm balances pointer moves in the same way.
  </FaqItem>
  <FaqItem question="Do I need these if I know a segment tree?">
    For sums with updates, a segment tree is faster at O(log n) per operation. Square root decomposition wins on simplicity, and Mo's algorithm answers statistics that a segment tree cannot merge. Heavy-light decomposition is usually paired with a segment tree.
  </FaqItem>
  <FaqItem question="How do heavy-light and centroid decomposition differ?">
    Heavy-light decomposition cuts the tree into chains once and answers queries on paths between two vertices. Centroid decomposition removes the middle vertex repeatedly and answers questions about all pairs or the nearest marked vertex. Both give O(log n) levels or chains, but they organise the tree differently.
  </FaqItem>
</Faq>
