## The problem

A list answers most questions by looking at every item. A tree gives up that flat layout to answer one kind of question much faster. What differs between the trees is the question:

- Is this key present, and what comes next? The **search trees** keep keys in order.
- What is the sum or minimum of positions `l` to `r`? The **range structures** precompute blocks.
- Which stored intervals overlap this one, or which point is nearest? The **specialists** prune whole regions.
- Does any word start with this prefix? The **string trees** share common prefixes.

The cost of a search tree is its height `h`, and a tree does not control its own height. Sorted input turns a plain binary search tree into a chain. Most of this section is about the ways to prevent that.

## Applications

- **Databases and file systems.** B-trees and B+ trees as indexes, with the leaf chain serving range scans.
- **Ordered maps and sets.** Balanced search trees keep keys sorted while allowing inserts and deletes.
- **Competitive programming.** Fenwick, segment and sparse tables answer range queries on arrays.
- **Spell check and autocomplete.** Tries answer prefix queries.
- **Geometry and games.** K-D trees find nearest neighbours; interval trees find overlapping events.
- **Text indexing.** Suffix trees locate every occurrence of a pattern.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Trusting a plain BST with sorted input.** Each key goes to the same side as the one before, so the height becomes n - 1 and every operation is O(n).
- **Calling a splay tree O(log n) per operation.** The bound is amortized. A single operation can cost O(n), and reads change the tree.
- **Looking for delete in the red-black tree or the B+ tree.** Neither implements it in this repository.
- **Using a Fenwick tree for minimum or maximum.** It needs an operation that can be undone, such as a sum. Use a sparse table for static data or a segment tree for sums.
- **Expecting the sparse table to take updates.** It is static. Any change means a rebuild.
- **Feeding index 0 to Fenwick code by hand.** Inside, indices are 1-based, and index 0 would loop forever.
- **Assuming the K-D tree and interval tree rebalance.** Both are unbalanced, so sorted input makes a chain.
- **Skipping the terminator in a suffix tree.** Without a unique end symbol, a suffix can end inside another suffix and lose its leaf.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Start with the binary tree and the binary search tree. Then pick one balanced variant, AVL first, and read the red-black tree, splay tree and treap as other answers to the same problem. The range structures can be read on their own, from the Fenwick tree to the lazy segment tree. The B-tree comes after the balanced trees, and the string trees and specialists last.
  </FaqItem>
  <FaqItem question="AVL or red-black: which is better?">
    AVL is stricter: its height stays below about 1.44 log2(n), so search is a little faster. Red-black allows a taller tree, up to 2 log2(n+1), but an insert needs at most 2 rotations. Both give O(log n) search and insert.
  </FaqItem>
  <FaqItem question="Which range structure should I use?">
    Ask what changes. If nothing changes and you need a minimum or maximum, use the sparse table. If you need sums with point updates, use a Fenwick tree or a segment tree. If you also need to add a value to a whole range, use the lazy segment tree.
  </FaqItem>
  <FaqItem question="Why does a B-tree have so many keys per node?">
    Reading a node from disk costs far more than comparing keys in memory. A node with up to 2t-1 sorted keys makes the tree shallow, so a search reads only O(log_t n) nodes while still doing O(log n) comparisons.
  </FaqItem>
  <FaqItem question="What is the difference between a trie and a suffix tree?">
    A trie stores a set of words, one character per edge. A suffix tree is a compressed trie of every suffix of one string, so it answers substring queries, not only prefix queries, in O(m + occ).
  </FaqItem>
</Faq>
