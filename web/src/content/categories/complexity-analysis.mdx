## The problem

Two programs can give the same answer and differ by a factor of a million in running time or memory at large input sizes. Complexity analysis gives a way to say how, without timing a particular machine.

Three questions cover it:

- **How long?** Time complexity describes how the number of steps grows with the input size `n`. It has its own sub-category because it has three notations, and a separate idea of cases.
- **How much memory?** Space complexity describes the extra memory, usually without the input. Recursion counts, because every active call holds a stack frame.
- **How much per operation, over time?** Amortized analysis bounds the total cost of any sequence of operations and divides by the number of operations.

All three use the same notation and the same habit: pick the function you are measuring, then bound it.

## Applications

- **Choosing an algorithm** before writing code, from the input size and the time limit.
- **Reviewing code,** by reading loops and recursion for their order of growth.
- **Capacity planning,** from the memory an algorithm needs at the expected input size.
- **Designing data structures,** such as a dynamic array whose resizing rule keeps appends O(1) amortized.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Equating O with the worst case.** O, Omega and Theta are bounds. Best, average and worst are cases, and any case can take any bound.
- **Counting only the input for space.** The usual convention counts auxiliary memory, and recursion adds one frame per active call. Naive Fibonacci makes O(2^n) calls but uses O(n) space.
- **Mistaking amortized for average case.** Amortized O(1) is a guarantee over every sequence, with no probability. Average-case analysis averages over a distribution of inputs.
- **Ignoring the growth rule.** A dynamic array that adds a constant amount on each resize loses the O(1) amortized append. Multiplying the capacity keeps it.
- **Forgetting that constants are hidden.** `3n` and `300n` are both O(n), so growth rate alone does not tell you which is faster at small sizes.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Time complexity first, and Big-O before Big-Omega and Big-Theta, because the rest of the repository quotes Big-O everywhere. Then space complexity, which uses the same notation on memory. Amortized analysis comes last because it builds on both and needs a data structure to look at, the dynamic array.
  </FaqItem>
  <FaqItem question="Is space complexity counted with or without the input?">
    Usually without. The common measure is auxiliary space, the extra memory the algorithm allocates, including the call stack. When someone says Heap Sort uses O(1) space, they mean auxiliary space, because it sorts in place. Total space is the input plus the auxiliary part, and it is only counted when the problem says so.
  </FaqItem>
  <FaqItem question="Why can an O(n) append still be called O(1)?">
    Amortized analysis bounds the total. A dynamic array that doubles when full copies fewer than 2n elements over n appends, so the cost per append averaged over the sequence is O(1), even though a single append can cost O(n).
  </FaqItem>
  <FaqItem question="Does a better time complexity mean better code?">
    Not at every size. Big-O drops constants and lower-order terms, so a simple O(n^2) routine can beat a complicated O(n log n) one on small inputs. Use the growth rate to predict scale, and measure when the sizes are small.
  </FaqItem>
</Faq>
