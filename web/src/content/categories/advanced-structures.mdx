## The problem

Some questions cannot be answered fast by one basic structure. A hash map finds a key in O(1) but knows nothing about order. A linked list reorders in O(1) but cannot find a key. Putting the two together gives a cache that finds an entry and also knows which one to throw away.

The structures here solve two problems:

- **Bounded memory with the best entries kept.** A cache holds a fixed number of key-value pairs. When it is full, a new key evicts one old entry, and the policy decides which one. LRU and LFU are two policies.
- **Merging groups.** The disjoint set union starts with every item alone and merges groups on request. It answers "are these two in the same group?" without ever splitting a group.

Both policies agree until the second eviction. LRU looks only at when an entry was last used, so the old but popular key `1` goes. LFU counts uses, so it keeps `1` and drops the newer key `3`.

## Applications

- **Caches.** Page caches, database buffer pools and memoization with a size limit.
- **Minimum spanning trees.** Kruskal's algorithm uses the DSU to reject edges that close a cycle.
- **Connectivity.** Connected components and cycle detection in an undirected graph.
- **Eviction policies.** LRU is the common default, and LFU suits stable popularity.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Forgetting that a read is a use.** In both caches, `get` changes the order or the count, not only `put`.
- **Using a negative number as a stored value.** `get` returns `-1` for a missing key, so a stored `-1` looks like a miss.
- **Expecting LFU to adapt quickly.** An old key with a high count stays even after it stops being used.
- **Skipping the tie-break in LFU.** Among equal counts, the least recently used entry is evicted.
- **Trying to split a set in the DSU.** There is no operation for it, and no delete.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Read the LRU cache first, then the LFU cache, which builds on it with a count per key. The disjoint set union stands apart and needs only the array and the tree ideas, so it can be read at any point.
  </FaqItem>
  <FaqItem question="Why do the caches need two structures?">
    The map finds a key in O(1) but has no order. The list gives order and moves an entry in O(1), but cannot find a key. Together they do both in O(1).
  </FaqItem>
  <FaqItem question="LRU or LFU?">
    LRU is simpler and adapts as soon as usage changes. LFU keeps the entries with the most uses, which helps when popularity is stable but can hold on to a key that has gone cold.
  </FaqItem>
  <FaqItem question="Why is the DSU bound written with alpha(n)?">
    Union by rank keeps the trees shallow and path compression flattens them on each find. Together they make the amortized cost grow as the inverse Ackermann function, which is below 5 in practice.
  </FaqItem>
</Faq>
