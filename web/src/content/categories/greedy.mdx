## The problem

Many problems ask for the best of an enormous number of candidates: the largest set of compatible activities, the most valuable load, the shortest code. A greedy algorithm does not search them. It fixes one rule for the next choice, makes that choice, and never reconsiders it.

That is fast and short, but a rule that sounds right is not always right. A greedy algorithm is correct only for problems with two properties:

- **The greedy-choice property.** Some optimal answer contains the greedy first choice.
- **Optimal substructure.** After that choice, what remains is a smaller problem of the same kind.

Each topic in this section states its rule and why those two properties hold. The proofs have the same shape: take any optimal answer and swap in the greedy choice without making it worse. The weighted activities and the 0/1 knapsack show the other side. When the properties fail, the rule gives a wrong answer without any warning.

## One rule, right and wrong

The numbers below come from running the repository's Python code.

**Right.** Fractional Knapsack with capacity 50 and items given as (value, weight) `(60, 10)`, `(100, 20)`, `(120, 30)` takes the first two whole and two thirds of the third. The value is 240.

**Wrong.** The same rule on the 0/1 knapsack, where an item is taken whole or not at all, takes the first two items and stops, because the third no longer fits. That is a value of 160. The dynamic program in `0_1_Knapsack` finds 220, by taking the second and third items. The greedy answer falls 60 short, because only the cut item made the rule optimal before.

**Wrong again.** Activity Selection picks the most activities, so it ignores weights. Take the activities (start, finish, weight) `(0, 3, 5)`, `(2, 5, 6)`, `(4, 7, 5)`, `(1, 8, 11)`. The greedy rule takes the first and the third, a total weight of 10. The weighted variant, which is a dynamic program, finds 11 by taking the long fourth activity alone.

**Right again.** Huffman Coding on `abracadabra` gives `a` the code `0`, and `c`, `d`, `r`, `b` the codes `100`, `101`, `110`, `111`. The whole text takes 23 bits instead of 88 at 8 bits per character, which is 26% of the size. And Job Scheduling on the jobs (id, deadline, profit) `a 2 100`, `b 1 19`, `c 2 27`, `d 1 25`, `e 3 15` schedules `a`, `c` and `e` for a profit of 142.

None of these has a best, average or worst input in the usual sense: the work depends on the size of the input, not on its order. Fractional Knapsack's O(n) extra space is for the sorted copy in Python. C++ and Go sort the input in place. Each greedy rule needs a sort or a heap, which is where the log factor comes from.

## Applications

- **Scheduling.** Choosing meetings or tasks, and ordering jobs by deadline or by weight.
- **Compression.** Huffman codes sit inside file formats and compressors such as DEFLATE.
- **Resource allocation.** Filling a limited budget or capacity with divisible goods.
- **Networks.** Minimum spanning trees with Kruskal's and Prim's algorithms.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Trusting a rule because it sounds right.** Without a proof that the greedy choice is safe, test the rule against a brute force or a dynamic program on small inputs.
- **Sorting by the wrong key.** Activity Selection needs finish time. Earliest start or shortest duration gives wrong answers on easy inputs, such as the earliest-start trap.
- **Using the fractional rule on the 0/1 knapsack.** It is only optimal because the last item can be cut.
- **Ignoring weights in Activity Selection.** The greedy rule maximizes the count of activities, not their total weight.
- **Skipping the sort.** Activity Selection and Fractional Knapsack scan in sorted order, and the scan is only correct on that order.
- **Assuming the Huffman code is unique.** Ties between equal frequencies can be broken either way. The code lengths and the total size stay optimal, but the exact bit strings can differ.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Start with Activity Selection: it has the clearest greedy proof. Then Fractional Knapsack, which shows how the same idea fails when items cannot be cut. Huffman Coding and Job Scheduling come after them, since each needs one more tool, a min-heap for Huffman Coding and a slot table for Job Scheduling.
  </FaqItem>
  <FaqItem question="How do I know a greedy rule is correct?">
    Prove two things. First, that some optimal answer contains the greedy choice, usually by an exchange argument: take an optimal answer and swap the greedy choice in without making it worse. Second, that what remains after the choice is a smaller problem of the same kind. If you cannot prove it, treat the rule as a heuristic.
  </FaqItem>
  <FaqItem question="How is greedy different from dynamic programming?">
    A greedy algorithm commits to one choice per step and never looks back. Dynamic programming tries every choice, keeps the answers to the subproblems and picks the best afterwards. Dynamic programming handles more problems, such as the 0/1 knapsack and weighted activities, but it usually costs more time and memory.
  </FaqItem>
  <FaqItem question="Are Kruskal's and Prim's algorithms greedy?">
    Yes. Both grow a minimum spanning tree by repeatedly taking the cheapest safe edge. They live in the Minimum Spanning Tree category, not here.
  </FaqItem>
</Faq>
