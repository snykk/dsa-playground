## The problem

Given a text `T` of length `n` and a pattern `P` of length `m`, report every index `i` where `T[i..i+m-1] == P`. Matches may overlap: `aa` occurs in `aaaa` at `[0, 1, 2]`.

All four algorithms in this section keep the same contract in Python, C++ and Go:

- They return every start index, in increasing order, overlapping matches included.
- An empty pattern, an empty text, or a pattern longer than the text returns `[]`.
- Python indexes code points; C++ and Go index bytes, so offsets differ on non-ASCII text.

What separates them is one question: after a mismatch, how much of what you already read can you reuse?

    ['KMP', 'precompute the longest border of every prefix (the LPS table)', 'keep the border that is still matched; the text pointer never moves back', 'O(n + m)'],
    ['Boyer-Moore', 'compare right to left, starting at the last pattern character', 'jump so the bad character lines up with its last occurrence in the pattern', 'O(n*m)'],
  ]}
/>

Rabin-Karp's worst case needs many hash hits, so its expected time is O(n + m). Boyer-Moore's needs a repetitive text; on typical text with a long pattern it reads only a fraction of the characters.

Extra space excludes the list of results, and Boyer-Moore here uses the bad-character rule only. Rabin-Karp's hash hits come from real matches (`aaa` in `aaa...a` hits at every window) or from collisions. The code uses a modulus of 101 so the arithmetic stays readable, and about one window in 101 then shares the pattern's hash by chance. Every hit is verified, so the result stays correct, but a large prime keeps the running time near O(n + m).

## Choosing an algorithm

    ['A guaranteed bound, or a stream read once', 'KMP', 'O(n + m) on every input, and the text is read left to right without going back'],
    ['Many patterns of the same length', 'Rabin-Karp', 'hash every pattern once, then look each window hash up in a set'],
    ['A long pattern over a large alphabet, such as prose', 'Boyer-Moore', 'most alignments end after one or two comparisons, followed by a long jump'],
    ['Many patterns of different lengths', 'Aho-Corasick', 'one pass over the text finds every pattern of the set'],
    ['Many queries against one fixed text', 'Suffix array', 'build it once, then answer each query with binary search'],
    ['Everyday code', 'the standard library', '`str.find`, `std::string::find` and `strings.Index` are tuned and tested'],

## Applications

- **Editors and search tools.** Find and replace, and `grep`-like scans of files.
- **Bioinformatics.** Locating a short DNA motif in a long genome.
- **Plagiarism and duplicate detection.** Hashing fixed-length windows, as Rabin-Karp does, to find shared passages.
- **Network security.** Scanning traffic for known signatures, usually many at once with Aho-Corasick.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Shifting by `m` after a match.** It misses overlapping matches; all four searches here report `aa` in `aaaa` at `[0, 1, 2]`.
- **Moving the text pointer back in KMP.** On a mismatch only `j` falls back, to `lps[j - 1]`. Resetting `i` makes the search quadratic again.
- **Trusting a hash hit.** Different windows can share a hash, so Rabin-Karp must compare the characters before it reports a match.
- **Calling this Boyer-Moore linear.** The bad-character rule alone is O(n*m) on inputs such as `baaa` in `aaaa...a`. The linear bound needs the good-suffix rule, which is not implemented here.
- **Mixing empty-pattern conventions.** These searches return `[]`, while `'abc'.find('')`, `std::string::find` and `strings.Index` report index 0.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="In what order should I read these?">
    Start with the naive search: every other algorithm answers one of its weaknesses. Then Rabin-Karp, KMP and Boyer-Moore, as in the list above. Each of those three needs only the naive search as background, so after it any order works.
  </FaqItem>
  <FaqItem question="Which one is fastest?">
    It depends on the input. Boyer-Moore usually wins on prose with a long pattern, because it reads only part of the text. KMP has the best worst case, O(n + m) on every input. Rabin-Karp pays off when you look for many patterns of one length at once, and for short patterns the naive search is often fastest in practice because it needs no setup.
  </FaqItem>
  <FaqItem question="What do standard libraries use?">
    Tuned hybrids rather than one textbook algorithm. CPython's `str.find` mixes Boyer-Moore-Horspool-style skips with the two-way algorithm for long patterns, and Go's `strings.Index` switches to Rabin-Karp when its first-byte scan keeps failing on a long pattern. C++17 offers `std::boyer_moore_searcher` when you want Boyer-Moore explicitly.
  </FaqItem>
  <FaqItem question="How do I search for many patterns at once?">
    If they share a length, hash them all and check each window's rolling hash against the set, as Rabin-Karp does for one pattern. Otherwise build an Aho-Corasick automaton: it extends the KMP failure links to a trie of the patterns and finds every occurrence of every pattern in one pass.
  </FaqItem>
  <FaqItem question="Is there another linear-time method?">
    The Z-algorithm also runs in O(n + m): it computes the Z-array of the pattern, a separator and the text, and reports the positions where the Z-value is at least `m`. Suffix arrays take the opposite trade, a slower build in exchange for fast queries against one fixed text.
  </FaqItem>
</Faq>
