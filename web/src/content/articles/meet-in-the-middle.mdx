## When to use it

The signals are in the constraints.

- `n` is between about 30 and 45: too large for 2<sup>n</sup>, small enough for 2<sup>n/2</sup> (about a million).
- The values are large (up to 10<sup>9</sup> or more), so a DP over the sum is impossible.
- The choice per element is independent (take it or not), and the two halves interact only through one combined quantity, such as a total sum.

If `n` is at most about 20, plain subset enumeration is enough. If the sums are small, a DP over the sum (as in knapsack) is faster. Meet in the middle is for the gap between the two.

## How it works

<Steps>
  <Step title="Split the input in two halves">
    Cut the array at the middle: `left = nums[:n/2]`, `right = nums[n/2:]`. Each half has at most about `n/2` elements.
  </Step>
  <Step title="Enumerate each half">
    List every subset sum of the left half (2<sup>n/2</sup> values) and of the right half. This is brute force, but on half the size.
  </Step>
  <Step title="Combine through the shared quantity">
    A full subset is one left subset plus one right subset. For each left sum, look up the right sums that complete the goal: an exact partner (hash set) or the best partner not above a limit (sorted list and binary search).
  </Step>
</Steps>

<Callout title="Why it is correct">
Every subset of the whole array is exactly one pair (left subset, right subset), and the total is the sum of the two parts. Enumerating both halves covers every pair, and looking up the partner for each left subset finds the best pair without visiting all 2<sup>n</sup> of them.
</Callout>

## Template

```text
meetInTheMiddle(items, goal):
    left, right = split items in two halves
    L = all subset sums of left                  # 2^(n/2) values
    R = all subset sums of right                 # 2^(n/2) values
    prepare R for lookup:  sort it, or put it in a hash set
    best = nothing
    for each a in L:
        look up in R the value that combines with a toward the goal
        update best
    return best
```

## Implementation

The Python version solves the **closest sum** problem, `closest_subset_sum(nums, target)`: the largest subset sum that is at most the target, with a sorted list and `bisect`. It requires non-negative numbers and a non-negative target, and raises `ValueError` otherwise.

The C++ and Go versions solve a different question, **exact sum**: `subsetSumMeetInMiddle(arr, target)` answers whether some subset sums to exactly the target, using hash sets. They accept negative values. The languages do not implement the same problem.

Memory is the real limit: with 2<sup>20</sup> sums per half the lists hold about 2 million numbers, fine in C++ and acceptable in Python. At n = 50 each half has 2<sup>25</sup> sums, which is too much memory in practice.

## Applications

- Subset sum and its relatives (count, closest, partition) with a small number of large numbers.
- Cryptographic and number-theoretic searches that split a key space in two.
- Searching a game or puzzle state space from both the start and the goal.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Splitting unevenly.** The halves must have about equal size, otherwise one side is close to 2<sup>n</sup>.
- **Forgetting the empty subset.** Both halves include the sum 0.
- **Negative values with pruning.** The closest-sum code skips left sums above the target, which is only valid when every number is non-negative. The repository code rejects negative numbers with `ValueError`.
- **Negative target.** With non-negative numbers even the empty subset (sum 0) exceeds a negative target, so no subset qualifies; the code raises `ValueError` rather than returning 0.
- **Overflow.** The C++ version uses `int` sums, so values near 2<sup>31</sup> overflow; use 64-bit integers for large inputs.
- **Using it when DP fits.** If the sum is small, a knapsack DP is faster and uses less memory.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does splitting in half help so much?">
    The cost of enumeration is exponential in the size you enumerate. Two enumerations of size n/2 cost 2 &middot; 2<sup>n/2</sup>, while one of size n costs 2<sup>n</sup>. The combination step is only about one lookup per left subset.
  </FaqItem>
  <FaqItem question="Does the order of the elements matter for the split?">
    No for correctness, since any split into two groups works. For speed, an even split is best, and choosing the groups so that sums repeat can shrink the sets when you deduplicate.
  </FaqItem>
  <FaqItem question="Why do the Python and C++ versions answer different questions?">
    Python finds the largest subset sum not above the target. The C++ and Go versions only check whether the target can be hit exactly. Both are meet in the middle: they differ only in the combine step, a binary search versus a hash lookup.
  </FaqItem>
  <FaqItem question="How do I count subsets instead of testing existence?">
    Store a count per sum for the right half (a dictionary from sum to number of subsets) and add the count of `target - a` for every left sum `a`.
  </FaqItem>
</Faq>
