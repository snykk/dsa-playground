## How Merge Sort works

Quick Sort does its work before recursing; Merge Sort does it **after**. It splits the range blindly in the middle, sorts both halves, and then relies on one fact: two sorted lists can be merged into one sorted list in a single linear pass.

<Steps>
  <Step title="Divide">
    Split the array into a left half of `n / 2` elements (rounded down) and a right half with the rest. A range of zero or one element is already sorted, which ends the recursion.
  </Step>
  <Step title="Conquer">
    Sort the left half and the right half recursively.
  </Step>
  <Step title="Merge">
    Keep one pointer at the front of each sorted half. Repeatedly copy the smaller of the two front elements to the output and advance that pointer. When one half runs out, copy the rest of the other. On a tie, take the left element first.
  </Step>
</Steps>

<Callout title="Why it is stable">
The merge takes from the left half when `left[i] <= right[j]`, so an equal element from the left (which came earlier in the input) is always written before its twin on the right. Equal keys therefore keep their original order.
</Callout>

## Pseudocode

```text
mergeSort(arr):
    if length(arr) <= 1: return arr
    mid = length(arr) / 2                 # integer division
    left  = copy of arr[0 .. mid - 1]
    right = copy of arr[mid .. end]
    mergeSort(left)
    mergeSort(right)
    merge(arr, left, right)
    return arr

merge(arr, left, right):                  # writes into arr
    i = 0; j = 0; k = 0
    while i < length(left) and j < length(right):
        if left[i] <= right[j]:           # <= keeps it stable
            arr[k] = left[i]; i = i + 1
        else:
            arr[k] = right[j]; j = j + 1
        k = k + 1
    copy the rest of left, then the rest of right, into arr
```

## Implementation

The Python and Go versions follow the pseudocode: they copy the two halves, sort the copies, and merge back into the original. The C++ version works on index ranges `[left, right]` of one vector and builds two temporary vectors `L` and `R` inside every `merge`. Python also has `merge_sort_iterative`, a bottom-up version that merges runs of size 1, 2, 4, ... with no recursion; C++ and Go have no iterative variant.

## Complexity analysis

Each level of the recursion tree merges ranges that together cover all `n` elements, so a level costs <BigO of="n" />. Halving gives log<sub>2</sub>(n) levels.

<Equation label="Recurrence" expr="T(n) = 2 T(n/2) + O(n)" result="O(n log n)" />

<ComplexityTable
  rows={[
    { case: 'Best case', time: 'O(n log n)', space: 'O(n)', when: 'Sorted input still splits and merges every level: the algorithm does not look at the data when splitting.' },
    { case: 'Average case', time: 'O(n log n)', space: 'O(n)', when: 'Always log2(n) levels of linear merging.' },
    { case: 'Worst case', time: 'O(n log n)', space: 'O(n)', when: 'Never worse: the split is always even, whatever the input.' },

/>

The number of comparisons is between about `(n log<sub>2</sub> n) / 2` and `n log<sub>2</sub> n - n + 1`. The extra memory is the temporary halves: at most about `n` elements are live at once, plus <BigO of="log n" /> stack frames.

<Callout title="Memory is the price of the guarantee">
Merging in place is possible but complicated and slower. The versions here are the simple ones, and they allocate new buffers on every call: Python and Go slice or copy the halves at each level, and C++ allocates `L` and `R` inside each `merge`. A single reusable buffer would avoid those allocations (the code does not do this).
</Callout>

## Applications

- **Stable sorting.** When records must keep their relative order (sort by name, then by city), Merge Sort is the classic choice.
- **Linked lists.** It needs only sequential access, so it sorts a linked list without random access.
- **External sorting.** Data too large for memory is sorted in chunks and the sorted chunks are merged.
- **Counting inversions.** During a merge, every time a right element is taken before the remaining left ones, it forms inversions with all of them: the count comes at no extra asymptotic cost.
- **Merging sorted lists.** The merge step on its own combines two sorted sequences in `O(n + m)`.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Using `<` instead of `<=` when comparing the fronts.** With strict `<` an equal right element is taken first, which makes the sort unstable.
- **Forgetting to copy the leftover run.** When one half is exhausted, the rest of the other half must still be copied.
- **Wrong C++ index convention.** The C++ range is inclusive: `mid = left + (right - left) / 2`, the halves are `[left, mid]` and `[mid + 1, right]`. Mixing it with half-open ranges gives off-by-one errors.
- **Merging into the same array being read.** Without temporary copies the merge overwrites elements it has not read yet.
- **Assuming it is in place.** The temporary arrays are O(n).
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why is Merge Sort O(n log n) even in the worst case?">
    It always splits the range exactly in half, so the recursion has log<sub>2</sub>(n) levels, and each level does a linear amount of merging. Unlike Quick Sort, the data cannot make the split uneven.
  </FaqItem>
  <FaqItem question="Is Merge Sort stable?">
    Yes, as long as the merge prefers the left element on a tie (`<=`). All three implementations here do; the Python and C++ tests check it with records that have equal keys.
  </FaqItem>
  <FaqItem question="Why is it better for linked lists than arrays?">
    The merge only moves forward through both lists, so it needs no random access, and it can relink nodes instead of copying them. Quick Sort and Heap Sort both need fast random access.
  </FaqItem>
  <FaqItem question="Top-down or bottom-up?">
    They do the same merges, in a different order. Top-down is shorter to write; bottom-up avoids recursion. This repository has the bottom-up version in Python only.
  </FaqItem>
</Faq>
