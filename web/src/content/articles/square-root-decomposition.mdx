## When to use it

Choose square root decomposition when you need range queries **and** updates on an array and want something simpler than a segment tree:

- "Sum of `arr[l..r]`, with point updates in between."
- A summary that is easy to keep per block but awkward to put in a tree: counts of values, sorted blocks, per-block lazy flags.
- `n` is up to about 10<sup>5</sup>, where an O(sqrt n) query is still fast enough.

If queries dominate and nothing changes, prefix sums answer in O(1). If both are heavy, a segment tree or Fenwick tree gives O(log n).

## The idea

Cut the array into blocks of size `B`. Store, for each block, the sum of its elements. A query `[l, r]` touches three kinds of cells:

- the **left partial block**: individual elements from `l` to the end of its block;
- the **middle blocks**: fully covered, so use their stored sums;
- the **right partial block**: individual elements from the start of its block to `r`.

If `l` and `r` are in the same block, just add the elements.

<Callout title="The invariant">
`blocks[b]` always equals the sum of `arr[b*B .. b*B + B - 1]`. A point update changes one array cell, so it adds `new - old` to exactly one block sum; nothing else depends on that cell.
</Callout>

## How it works

<Steps>
  <Step title="Choose the block size">
    `B = ceil(sqrt(n))`, with a minimum of 1 so that an empty array does not divide by zero. Block `b` holds indices `b*B` to `b*B + B - 1`, and there are `ceil(n / B)` blocks.
  </Step>
  <Step title="Build the block sums">
    One pass over the array: `blocks[i // B] += arr[i]`.
  </Step>
  <Step title="Answer a query [l, r]">
    If `l // B == r // B`, add `arr[l..r]` directly. Otherwise add the left partial block, the stored sums of the blocks strictly between, and the right partial block.
  </Step>
  <Step title="Apply a point update">
    `blocks[i // B] += value - arr[i]`, then `arr[i] = value`. That is O(1).
  </Step>
</Steps>

## Pseudocode

```text
build(arr):
    B = max(1, ceil(sqrt(n)))
    blocks = [0] * ceil(n / B)
    for i in 0..n-1:  blocks[i // B] += arr[i]

update(i, value):
    blocks[i // B] += value - arr[i]
    arr[i] = value

query(l, r):                                  # inclusive
    lb = l // B;  rb = r // B
    if lb == rb:  return sum(arr[l..r])
    total = sum(arr[l .. (lb + 1) * B - 1])   # left partial
    total += sum(blocks[lb + 1 .. rb - 1])    # whole blocks
    total += sum(arr[rb * B .. r])            # right partial
    return total
```

## Implementation

The three languages implement the same class with the same three operations: build, `update(index, value)` (sets a value) and `query(left, right)` (inclusive sum), spelled `Update` and `Query` in Go. There are no range updates and no other aggregate such as min or max.

- **Python and Go** copy the input array, so `update` does not change the caller's list or slice.
- **C++** copies it as well (the constructor takes `const vector<int>&`).
- Queries and updates assume valid indices; an out-of-range index is not checked.
- Sums use the language's integer: Python integers are unbounded, C++ `int` and Go `int` can overflow on huge totals.

## Complexity analysis

With block size `B`, a query handles up to `B` elements on each side plus up to `n / B` block sums.

<Equation label="Query cost" expr="T(B) = 2B + n / B" result="O(sqrt n) at B = sqrt n" />

Making blocks smaller speeds up the partial scans but adds more blocks to sum; larger blocks do the opposite. `sqrt n` balances the two.

## Applications

- Range sum with updates on mid-sized arrays.
- Range queries where the block summary is a count, a frequency table or a sorted list.
- Offline problems solved by Mo's algorithm, which applies the same block idea to queries.
- A simple baseline to check a segment tree against.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Block size 0.** `ceil(sqrt(0))` is 0 and the index `i // 0` divides by zero. The code uses a minimum of 1.
- **Reading the stored value on update.** The update must use `arr[i]` before overwriting it: `blocks[b] += value - arr[i]`.
- **Treating the last block as full.** The last block may be partial; its sum is built from the elements that exist.
- **Off-by-one at block borders.** The left partial runs to `(left_block + 1) * B - 1` inclusive; the right starts at `right_block * B`.
- **Summing blocks when `l` and `r` share a block.** Handle that case first, or you count the wrong range.
- **Overflow in fixed-width integers.** Block sums can be much larger than single elements.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why is the block size sqrt n and not something else?">
    The query cost is about `2B + n / B`. The first term grows with `B`, the second shrinks, and their sum is smallest when they are of the same order, at `B` close to sqrt n.
  </FaqItem>
  <FaqItem question="Does update mutate my input array?">
    Not in any of the three languages: the constructor copies the array.
  </FaqItem>
  <FaqItem question="Is there a range update in the repository?">
    No. Only point `update(index, value)` and range `query` are implemented. Range add needs a lazy flag per block.
  </FaqItem>
  <FaqItem question="What happens on an empty array?">
    The block size is clamped to 1, there are no blocks, and construction succeeds. Any query on it would be out of range.
  </FaqItem>
</Faq>
