## How Radix Sort works

Sorting by the whole number is hard; sorting by one digit is easy, because there are only ten possible digits. LSD (least significant digit) Radix Sort sorts by the last digit first, then by the next digit, and so on up to the most significant one. After the pass for digit `d`, the array is sorted by the last `d` digits, and each pass leaves the earlier order intact for numbers whose current digit is equal.

<Steps>
  <Step title="Make every key non-negative">
    If the smallest value is negative, each pass uses the key `value - min` instead of the value. Shifting by a constant keeps the order and makes every key `>= 0`. With no negatives the key is the value itself.
  </Step>
  <Step title="Find the number of digits">
    Compute the largest key. Its number of decimal digits is the number of passes.
  </Step>
  <Step title="Sort by one digit, stably">
    For `exp = 1, 10, 100, ...` run a counting sort on the digit `(key / exp) % 10`. The counting sort must be stable.
  </Step>
</Steps>

<Callout title="Why stability is the whole trick">
When the pass for the tens digit runs, two numbers with the same tens digit must stay in the order the units pass gave them, because that order is the correct order of their last digit. A stable sort guarantees this. With an unstable digit sort the earlier work is scrambled and the final order is wrong.
</Callout>

## Pseudocode

```text
radixSort(arr):
    if arr is empty: return
    offset = min(min(arr), 0)               # shift so that every key >= 0
    maxKey = max(arr) - offset
    exp = 1
    while maxKey / exp > 0:                 # one pass per decimal digit
        countingSortByDigit(arr, exp, offset)
        exp = exp * 10

countingSortByDigit(arr, exp, offset):
    digit(v) = ((v - offset) / exp) % 10
    count[0..9] = 0
    for v in arr: count[digit(v)] += 1
    for i = 1 to 9: count[i] += count[i - 1]
    for i = length(arr) - 1 down to 0:      # back to front keeps it stable
        count[digit(arr[i])] -= 1
        output[count[digit(arr[i])]] = arr[i]
    copy output back into arr
```

## Implementation

All three versions are LSD base 10, sort in place, and support negative values through the `value - min` shift. They differ in how they stay safe near the limits of the integer type:

- Python integers do not overflow, so it needs no special care.
- C++ keeps the key and the exponent in `long long`, so values up to `INT_MAX` (where `exp * 10` would overflow a 32-bit `int`) and a spread from `INT_MIN` to `INT_MAX` work.
- Go uses `uint64` for the key and the exponent, and stops the loop before `exp * 10` could overflow.

Python and C++ expose the per-digit counting sort (`counting_sort_by_digit`, `countingSortByDigit`); in Go it is unexported.

## Complexity analysis

There are `d` passes, one per digit of the largest key. Each pass is a counting sort over `n` elements with `b = 10` possible digits, so it costs <BigO of="n + b" />.

<Equation label="Total time" expr="T(n) = d * O(n + b)" result="O(d (n + b))" />

<ComplexityTable
  rows={[
    { case: 'Best case', time: 'O(d (n + b))', space: 'O(n + b)', when: 'The cost depends on the number of digits, not on the order of the input. If every value is 0 there are no passes at all.' },
    { case: 'Average case', time: 'O(d (n + b))', space: 'O(n + b)', when: 'The same loops run on any input with the same n and d.' },
    { case: 'Worst case', time: 'O(d (n + b))', space: 'O(n + b)', when: 'A spread of values with many digits: d grows as log10 of the largest key.' },
  ]}
/>

The space is the output array of `n` elements plus the 10 counters. For keys below `n^c` for a constant `c`, `d` is about `c log<sub>b</sub> n`, so a larger base cuts the number of passes at the cost of a bigger count array. With a fixed `d` it is linear in `n`.

<Callout title="d is not a constant for free">
Radix Sort is linear only when the number of digits is small. For `n` distinct integers the keys need at least `log<sub>10</sub>(n)` digits, so the time is `n log n` in disguise. It still beats comparison sorts when the digit count is small and the constants are low, such as 32-bit keys sorted in base 256.
</Callout>

## Applications

- **Large arrays of integers.** Sorting many 32-bit or 64-bit keys, usually with a larger base such as 256 to cut the passes.
- **Fixed-length keys.** Phone numbers, ZIP codes, dates written as numbers, IDs.
- **Multi-key sorting.** Sorting records by several keys stably, least significant key first, is the same idea.
- **As a building block.** Suffix-array construction algorithms use radix sort on pairs of ranks.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **An unstable digit sort.** Any inner sort that can reorder equal digits breaks the result. Place elements back to front with prefix sums.
- **Most significant digit first with the same loop.** LSD only works from the least significant digit; MSD needs recursion into groups.
- **Negative numbers.** A negative value gives a negative digit (or, in Python, the wrong digit, because `%` returns a non-negative result). Shift by the minimum first, as the repository code does.
- **Overflow of the exponent.** `exp * 10` overflows a 32-bit `int` when the maximum is 10^9 or more; use 64-bit values.
- **Stopping one pass too early.** The loop must run while `maxKey / exp > 0`, so the highest digit is included.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does LSD Radix Sort start from the least significant digit?">
    Because the last pass decides the most important digit, and each earlier pass only has to break ties. Sorting the least significant digit first, with a stable sort, means that the final pass leaves equal high digits ordered by the lower digits.
  </FaqItem>
  <FaqItem question="Does it work with negative numbers?">
    Yes here: the code subtracts the minimum from every value (when it is negative) to get non-negative keys with the same order, and sorts those keys. The values themselves are not changed.
  </FaqItem>
  <FaqItem question="Is Radix Sort faster than Quick Sort?">
    It can be for large arrays of fixed-width integers, because its work grows like `d * n` instead of `n log n`. For small arrays or keys with many digits, a comparison sort is usually as fast or faster.
  </FaqItem>
  <FaqItem question="Why does it need Counting Sort?">
    Each pass sorts keys that have only 10 possible values, which is exactly what Counting Sort does in linear time, and it is stable. Radix Sort is Counting Sort applied once per digit.
  </FaqItem>
</Faq>
