## What a B+ tree is

A B+ tree has the same shape rules as a B-tree of minimum degree `t`: every node except the root holds between `t - 1` and `2t - 1` keys, and all leaves are at the same depth. The difference is **where the data lives**:

- **Leaves** hold all the (key, value) pairs, sorted, and each leaf points to the next one.
- **Internal nodes** hold only separator keys used to steer a search. They carry no values.
- Each separator is a *copy* of the smallest key of the subtree to its right, so a key can appear twice: once in an internal node and once in a leaf.

Keeping values out of internal nodes lets an internal node hold more separators per page, so the tree is a little shallower. The linked leaves turn "all keys between `a` and `b`" into a sequential scan.

## Operations

<DataTable
  columns={['Operation', 'What it does', { label: 'Time', kind: 'mono' }]}
  rows={[
    ['`search(key)`', 'descend to the one leaf that could hold the key', 'O(log n)'],
    ['`insert(key, value)`', 'split full nodes on the way down, insert into a leaf; an existing key is overwritten', 'O(log n)'],
    ['`range_search(lo, hi)`', 'descend to the leaf for `lo`, then follow `next` until a key exceeds `hi`', 'O(log n + k)'],
    ['`traverse()`', 'walk from the leftmost leaf along the chain', 'O(n)'],
  ]}
/>

There is **no delete** in any of the three languages. In Python `search` returns the value or `None`. In C++ and Go it returns the value or the empty string, so a missing key and a stored empty value look the same. C++ and Go also have `range_search` (`rangeSearch` is `RangeSearch` in Go) and `traverse`, returning key and value pairs.

### Search

At each internal node go to the first child whose separator is **greater than** the key, that is, take the child to the right of every separator `<=` key. Equal keys go right, because a separator is the smallest key of its right subtree. The search always continues to a leaf, even when a separator equals the key, since the value is only stored there.

### Insert: copy-up and push-up

Like the B-tree, insertion splits every **full** node (`2t - 1` keys) before entering it, so a leaf always has room. The two kinds of split differ:

- **Leaf split (copy-up).** The leaf's upper half (from index `t - 1`) moves to a new right leaf, the leaf chain is relinked, and the first key of the new leaf is **copied** into the parent. The key stays in the leaf.
- **Internal split (push-up).** The median separator moves **up** into the parent and is kept in neither half, as in a B-tree.

### Range query

Find the leaf for `lo`, then read keys while they are `<= hi`, hopping along `next`. In the nine-key tree above, `range_search(25, 65)`:

<Steps>
  <Step title="Descend">
    25 < 30 at the root, then 25 &ge; 20 in the left internal node: the target leaf is `[20]`.
  </Step>
  <Step title="Scan the chain">
    `[20]` has nothing in range (20 < 25). The next leaves `[30]`, `[40]`, `[50]` and `[60]` contribute 30, 40, 50 and 60.
  </Step>
  <Step title="Stop">
    The next leaf `[70, 80, 90]` starts with 70 > 65, so the scan ends. Result: 30, 40, 50, 60.
  </Step>
</Steps>

## Implementation

The three versions share the same structure: nodes with `keys`, `children` (internal) and `values` plus a `next` pointer (leaf), a proactive `split_child` with the two cases above, and `find_leaf`. The tests insert thousands of random keys and compare `search`, `range_search` and `traverse` with a dictionary or `std::map`, then check fill bounds, separators, equal leaf depth and the leaf chain. The C++ tree frees its nodes in a destructor and cannot be copied.

Comparisons inside a node are linear, so each node visit costs O(t) comparisons. Space is O(n) with at least half of every node used.

## Applications

- **Database indexes:** many relational databases use B+ tree variants, because range predicates (`BETWEEN`, `ORDER BY`) become leaf scans.
- **File systems and key-value storage engines** that keep sorted keys on block storage.
- **Any ordered map with frequent range queries** on large data.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Dropping the key on a leaf split.** The first key of the new leaf is copied up, not moved. Only an internal split moves its median up.
- **Stopping the search at an equal separator.** The value lives in the leaf; keep descending (equal keys go right).
- **Forgetting to relink `next`.** After a leaf split, the new leaf must take over the old `next` and the old leaf must point to the new one.
- **Using `-inf` to find the leftmost leaf.** It breaks for non-numeric keys; follow `children[0]` instead.
- **Reading an empty string as "missing".** In C++ and Go `search` returns an empty string for both a missing key and a stored empty value.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why are keys duplicated between internal nodes and leaves?">
    The leaves must hold every key to support scans, while internal nodes only need a boundary to steer searches. A separator is just a copy of a boundary key, so it does no harm if that key is later removed from a leaf.
  </FaqItem>
  <FaqItem question="Why is a range query faster than in a B-tree?">
    In a B-tree the keys of a range are scattered over internal and leaf nodes, so a scan must climb and descend. In a B+ tree they sit in consecutive leaves linked by `next`.
  </FaqItem>
  <FaqItem question="What happens when I insert a key that already exists?">
    The value is overwritten and the tree does not change shape: this implementation is a map, not a multimap.
  </FaqItem>
  <FaqItem question="Does the repository support deleting keys?">
    No. Insert, search, range search and traverse are implemented. A delete needs borrow and merge for leaves (with separator updates) and for internal nodes, and is left out.
  </FaqItem>
</Faq>
