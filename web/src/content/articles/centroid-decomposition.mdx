## When to use it

Reach for centroid decomposition when a tree problem is about **all pairs of nodes** or about **paths**, and a plain DFS from every node would be <BigO of="n^2" />.

- "Count (or find) the pairs of nodes at distance exactly `k`, or at most `k`."
- "After each update that marks a node, report the distance to the nearest marked node."
- "Sum something over every path in the tree."
- The tree is static and `n` is around 10<sup>5</sup>.

The idea is the one behind divide and conquer on arrays: pick a split point, handle everything that crosses it, recurse on both halves. On a tree the right split point is the centroid.

## What a centroid is

A **centroid** of a tree with `n` nodes is a node whose removal leaves every remaining component with at most `n/2` nodes. Every tree has one (sometimes two). Walk from any node towards the child whose subtree is larger than `n/2`; the walk must stop, and where it stops is a centroid.

## How it works

<Steps>
  <Step title="Measure the component">
    Run a DFS from any node of the current component and compute every subtree size, skipping nodes that are already removed. The root's size is the component size `total`.
  </Step>
  <Step title="Find its centroid">
    Start at the root and move to any child whose size is greater than `total // 2`. Stop when no child is that big. That node is the centroid.
  </Step>
  <Step title="Remove it and link it">
    Mark the centroid as removed and set its entry in the `parent` array to the centroid that was found one level up (`-1` for the first one).
  </Step>
  <Step title="Recurse on the pieces">
    Every neighbor of the centroid that is not removed starts a new component. Decompose each one, passing the current centroid as their parent.
  </Step>
</Steps>

<Callout title="Why the height is logarithmic">
Each component handed to the next level has at most half the nodes of the one before. A component of size 1 is the last one, so a node is separated at most floor(log<sub>2</sub> n) + 1 times. Removed centroids become the nodes of the **centroid tree**, and its height is therefore O(log n), however deep or skewed the original tree is.
</Callout>

## The key property

For any two nodes `u` and `v`, the path between them passes through their **lowest common ancestor in the centroid tree**. That ancestor is the first centroid removed from a component that contained both of them, and removing it is what separated them. So every path is "handled" at exactly one centroid, and each node has only O(log n) centroid ancestors.

## Pseudocode

The repository builds the decomposition. Queries are the reason to build it, so here is the standard template they follow (this part is not in the code):

```text
decompose(u, p):                      # as in the code
    total    = dfsSize(u, -1)
    centroid = findCentroid(u, -1, total)
    removed[centroid] = true
    parent[centroid]  = p
    for v in adj[centroid]:
        if not removed[v]:
            decompose(v, centroid)

# typical use: nearest marked node
mark(v):      for each centroid ancestor c of v:  best[c] = min(best[c], dist(v, c))
query(v):     answer = min over centroid ancestors c of v of  dist(v, c) + best[c]
```

`dist(v, c)` is the tree distance, which you precompute during `decompose` (one BFS or DFS from each centroid) or get from an LCA structure. Both `mark` and `query` touch O(log n) ancestors.

## Implementation

All three languages follow the same design: a size pass (`dfs_size`, `dfsSize` in C++ and Go), a walk to the centroid (`find_centroid` / `findCentroid`), a recursive `decompose` and a public `build(root)` (`Build` in Go). `build` resets the `removed` and `parent` state first, so calling it twice gives the same result.

- **Python** computes subtree sizes and walks to the centroid with loops instead of recursion, so a path of 5,000 nodes works. It also has `get_centroid_tree()`, which returns the centroid tree as an adjacency list.
- **C++ and Go** return the parent array (`getParent()` / `GetParent()`). Their size DFS is still recursive, so a path of many hundreds of thousands of nodes can overflow the C++ call stack; Go grows its stack on demand.

No language implements the distance or nearest-marked-node queries; they are shown above as the motivation.

## Applications

- **Counting paths** with a given length or a bounded sum: at each centroid, count pairs from different child components.
- **Nearest marked node** under insertions: the template above.
- **Tree distance queries** answered through the common centroid ancestor of two nodes.
- **Offline path problems** where a node can be both endpoint and intermediate: the CSES problems "Fixed-Length Paths I" and "Fixed-Length Paths II" are standard practice.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Forgetting the removed flag.** Without it the DFS walks back into earlier centroids and the components are not independent.
- **Using stale sizes.** Recompute `size` for each new component. Sizes from the previous level are wrong once the centroid is gone.
- **Taking the root of the DFS as the centroid.** The DFS root is arbitrary; only the walk towards oversized children finds the centroid.
- **Counting pairs inside one child.** When combining at a centroid, pairs whose paths do not actually pass through it are counted wrongly unless you subtract or process children one by one.
- **Deep recursion.** Use an iterative size pass (Python's is breadth-first) when the tree can be a long path and the language has a small stack.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is the centroid unique?">
    No. A tree with an even number of nodes may have two centroids, adjacent to each other, each leaving components of at most `n/2`. Either one gives the same O(log n) guarantee.
  </FaqItem>
  <FaqItem question="What is the difference between the centroid tree and the original tree?">
    They share the same nodes but not the same edges. The centroid tree's parent of a node is the centroid that was removed from the component containing it, and it is generally not adjacent in the original tree.
  </FaqItem>
  <FaqItem question="Does the implementation handle a forest?">
    No. `build(root)` decomposes only the component containing `root`, and it resets all state first, so a second call would erase the first result. Merge the trees under a virtual root, or run one object per tree.
  </FaqItem>
</Faq>
