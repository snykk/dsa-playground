## How it works

Comparing two strings of length m costs O(m). Comparing two numbers costs O(1). A **polynomial hash** reads the characters `c_0 c_1 ... c_(m-1)` as the digits of a number in base B and keeps its remainder modulo a prime M:

<Equation label="Polynomial hash" expr="hash = (c_0 * B^(m-1) + c_1 * B^(m-2) + ... + c_(m-1)) mod M" />

Equal strings always get equal hashes. Different strings of the same length can collide, but rarely, so a hash mismatch is a proof that two strings differ and a hash match is very strong evidence that they are equal.

Rabin-Karp, a prerequisite of this page, slides one window of this hash along a text to find one pattern. String hashing keeps the hash of **every prefix** of one string instead, so it can hash any substring, in any order, as often as needed.

<Steps>
  <Step title="Build the prefix hashes">
    `prefix[0] = 0`, and `prefix[i + 1] = (prefix[i] * B + c_i) mod M` by Horner's rule: shift one digit left, add the next character. `prefix[i]` is the hash of the first i characters.
  </Step>
  <Step title="Build the power table">
    `power[0] = 1` and `power[i + 1] = power[i] * B mod M`, so `power[i] = B^i mod M`. One pass builds both tables in O(n).
  </Step>
  <Step title="Hash any substring in O(1)">
    `prefix[r]` is the number written by `s[0:r]`. The digits of `s[0:l]` sit in it `r - l` places to the left, so `hash(s[l:r]) = (prefix[r] - prefix[l] * power[r - l]) mod M`.
  </Step>
  <Step title="Answer the queries">
    Two substrings of the same length are equal when their hashes are. The longest common prefix of two suffixes is a binary search on the length, and the first character after it orders the two.
  </Step>
</Steps>

<Callout title="Why the subtraction works">
It is the prefix-sum trick with a shift. `prefix[5]` for `mississippi` holds `m i s s i` as base-B digits. `prefix[1]` holds `m`; multiplied by `B^4`, it lines up with the `m` inside `prefix[5]`, and the difference keeps only `i s s i`, the hash of `s[1:5]`.
</Callout>

    ['`compare(l1, r1, l2, r2)`', 'the same search, limited to the shorter length; a proper prefix comes first, else the characters at offset k decide', 'O(log n)'],
    ['`count_distinct(length)`', 'the number of different hashes among the `n - length + 1` substrings of that length', 'O(n) expected'],
  ]}
/>

The binary search is valid because equal prefixes are monotone: if the first k characters of two suffixes agree, so do the first k - 1. It keeps `lo`, a length known to agree (0 at the start), and `hi`, the longest length that still might. It tries `mid = (lo + hi + 1) // 2`: equal hashes move `lo` up to `mid`, different hashes move `hi` down to `mid - 1`. The `+ 1` rounds up, so `mid` is always above `lo` and the loop ends.

## How likely is a collision?

    ['10^5 substrings, the largest prime below 2^32', 'about 1.16 pairs, at least one with chance 69%', '27 of 40 random strings had one'],
    ['10^5 substrings, `DoubleHash` (two moduli)', 'about `5 x 10^-9`', 'none of 5 random strings lost a count'],

<Callout title="One comparison: n / M">
When two strings of length n differ, `hash(x) - hash(y)` is a polynomial in B of degree at most n - 1, and it is not zero. Modulo a prime it has at most n - 1 roots. A base drawn at random from M values hits a root with probability at most `(n - 1) / M`: about 10<sup>-4</sup> for n = 10<sup>5</sup> and M near 10<sup>9</sup>.
</Callout>

**Many comparisons add up.** A query is rarely one comparison. A distinct-substring count compares every pair of 10<sup>5</sup> hashes at once, about 5 x 10<sup>9</sup> pairs, and the birthday bound says that one modulus near 10<sup>9</sup> (it fits in 32 bits) then expects 5 collisions. That is why the code here keeps **two moduli**: `DoubleHash` stores two hashes of every prefix, one modulo 1,000,000,007 and one modulo 998,244,353, each with its own base, and compares them as a pair, which behaves like one modulus near 10<sup>18</sup>. A single modulus near 2<sup>61</sup> works too, but its products need 128 bits.

<Callout title="Random base or fixed base">
The bound `(n - 1) / M` holds for **any** two strings when the base is random: an adversary who writes the input cannot know which base the program will pick. That is why contest code draws the base when the program starts. This repository fixes its bases (911,382,323 and 972,663,749), so that Python, C++ and Go compute the same numbers and the tests can pin them. Fixed public constants are fine for these tests, not for hostile input: anyone who knows them can prepare a colliding input offline, as the Thue-Morse strings below do for the modulus 2<sup>64</sup>.
</Callout>

## Why not let 64-bit integers overflow?

Unsigned 64-bit arithmetic in C++ and Go wraps around, so dropping the `mod` computes the hash modulo 2<sup>64</sup> for free. It is a classic mistake, and the code includes it, as `overflow_hash`, to show why:

- **An even base** forgets everything but the last 64 characters, since B<sup>64</sup> is a multiple of 2<sup>64</sup>. `x` followed by 64 `a`s and `y` followed by 64 `a`s collide for bases 2, 256, 1000 and 2<sup>32</sup>.
- **An odd base** loses to the **Thue-Morse** strings. Character i is `b` when i has an odd number of 1 bits: `abbabaab...`, against its complement `baababba...`. Up to sign, their difference is the product of `B^(2^j) - 1` for j below 10. For an odd B, 2 divides `B - 1` and `2^(j+2)` divides `B^(2^j) - 1`, so `2^(1 + 3 + 4 + ... + 11) = 2^64` divides the product: the strings of length 1024 collide for **every** odd base.

The tests check this for 207 odd bases, in Python, C++ and Go alike: every one collides at length 1024, while length 512 does not always collide (not for base 3). `DoubleHash` tells the two strings apart. The simpler estimate, `2^(j+1)` per factor, gives `2^(1 + 2 + ... + k)` and asks for k = 11, length 2048; counted exactly, length 1024 is already enough.

Six substring hashes answer the query. `DoubleHash("mississippi")` agrees: `lcp(2, 5) = 3`, `compare(0, 4, 1, 5) = 1` (`miss` comes after `issi`: `m` > `i` at offset 0), and the counts of distinct substrings of lengths 1 to 11 are 4, 7, 7, 7, 7, 6, 5, 4, 3, 2, 1.

A modulus this small collides easily. With base 31 and modulus 101, `abra` and `brac` in `abracadabra` both hash to 57, so `count_distinct(4)` returns 6 instead of 7. With base 7 and modulus 11, `abra` and `cada` collide and `lcp(0, 4)` returns 4 instead of 0: the search trusts the collision at length 4 and never tries length 1. `DoubleHash` gets both right.

## Pseudocode

```text
PolynomialHash(s, base, mod):            # 2 <= mod <= 2^32, 1 <= base < mod
    prefix[0] = 0; power[0] = 1
    for i, c in enumerate(codes(s)):
        prefix[i + 1] = (prefix[i] * base + c) % mod
        power[i + 1] = power[i] * base % mod

get(l, r):                               # 0 <= l <= r <= n
    return (prefix[r] - prefix[l] * power[r - l]) % mod

equal(i, j, length):
    return get(i, i + length) == get(j, j + length)

_lcp(i, j, limit):                       # longest k <= limit with equal hashes
    lo, hi = 0, limit
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if get(i, i + mid) == get(j, j + mid): lo = mid
        else: hi = mid - 1
    return lo

lcp(i, j) = _lcp(i, j, min(n - i, n - j))

compare(l1, r1, l2, r2):
    k = _lcp(l1, l2, min(r1 - l1, r2 - l2))
    if k == min(r1 - l1, r2 - l2): return sign((r1 - l1) - (r2 - l2))
    return -1 if codes[l1 + k] < codes[l2 + k] else 1

count_distinct(length):
    return size of { get(i, i + length) for i in 0 .. n - length }

DoubleHash(s): two PolynomialHash tables, (911382323, 1000000007) and (972663749, 998244353);
               get returns the pair, and the queries above work on pairs unchanged
```

## Implementation

Every language provides the same pieces with the same results:

- **`PolynomialHash`** with `get`, `equal`, `lcp`, `compare` and `count_distinct` (`countDistinct`, `CountDistinct`), for any modulus from 2 to 2<sup>32</sup> and base from 1 to mod - 1.
- **`DoubleHash`** with the same queries, on the two fixed pairs.
- **`polynomial_hash`** (`polynomialHash`, `PolynomialHashOf`) for one whole string, **`overflow_hash`** (`overflowHash`, `OverflowHash`) for the broken hash modulo 2<sup>64</sup>, and **`thue_morse_pair`** (`thueMorsePair`, `ThueMorsePair`).

**No overflow in C++ and Go.** Every hash and power is below the modulus, at most 2<sup>32</sup>, so a product of two of them is at most (2<sup>32</sup> - 1)<sup>2</sup>, below 2<sup>64</sup>: it fits in an unsigned 64-bit integer. `get` adds `mod` before subtracting, since an unsigned value cannot go below zero. Python's integers never overflow, and its `%` is never negative.

**Characters.** Python hashes the code points of a `str` (or the bytes of a `bytes`); C++ and Go hash the bytes of their strings, so text in UTF-8 is hashed byte by byte. For ASCII the three agree, and `s.encode("utf-8")` gives Python the numbers of the other two. The C++ and Go tests pin the tables of `mississippi`, the `DoubleHash` values, the tables at modulus 2<sup>32</sup> and base 2<sup>32</sup> - 1, and the hashes of a UTF-8 string and of a 100,000-character string, all computed by the Python code.

**Errors.** A bad base or modulus raises `ValueError` in Python, throws `std::invalid_argument` in C++, and returns an error wrapping `ErrBadParameters` in Go. A range outside the string raises `IndexError`, throws `std::out_of_range`, or panics in Go; a negative length raises `ValueError`, throws `std::invalid_argument`, or panics.

## Applications

- **Longest repeated or common substring**: binary search on the length, with a set of the hashes of every window of that length.
- **Palindromes**: hash the string and its reverse; a substring is a palindrome when both hashes of it agree.
- **Periods, borders and rotations**: `s[0:n-p] == s[p:n]` in O(1) per p; the smallest rotation by comparing rotations of `s + s`.
- **Deduplication**: equal file blocks or repeated lines, found by their hashes, then confirmed.
- **Building a suffix array**: sort the suffixes with `compare` as the comparison, O(n log<sup>2</sup> n) in all.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Comparing hashes of different lengths.** `\0` and `\0\0` both hash to 0. Compare lengths first, as every query here does.
- **A negative difference** in C++ and Go: add `mod` before taking the remainder.
- **Overflowing the product.** Keep both factors below 2<sup>32</sup>, or use a 128-bit product for a modulus near 2<sup>61</sup>.
- **Natural overflow as the modulus.** Thue-Morse strings break it for every odd base, and an even base keeps only the last 64 characters.
- **One modulus near 10<sup>9</sup> for 10<sup>5</sup> substrings.** About 5 collisions are expected. Use two moduli.
- **Signed `char` in C++.** Bytes of 0x80 or more would be negative; read them as `unsigned char`.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Do I need a prime modulus?">
    The bound of n - 1 roots holds modulo a prime. Modulo a composite a polynomial can have many more roots, and a power of two is a bad case, as the Thue-Morse strings show. Both moduli here are primes.
  </FaqItem>
  <FaqItem question="Should the base be larger than the alphabet?">
    It need not be. The collision bound comes from the random base, not from the size of the alphabet. A base below the largest character code only means two different strings can share a hash before the modulus is taken, which the bound already counts. The fixed bases here are near 10<sup>9</sup>, far above every code point.
  </FaqItem>
  <FaqItem question="Why binary search for the LCP instead of comparing characters?">
    A scan costs O(answer) per query, and the answer can be n. The binary search costs O(log n) whatever the answer, which matters when there are many queries, for example the O(n log n) comparisons of a sort.
  </FaqItem>
  <FaqItem question="Can hashing replace a suffix array?">
    For many problems, yes, at a log factor: comparisons in O(log n), distinct counts per length in O(n). A suffix array with an LCP array answers exactly and in O(1) per LCP, but its fast construction is much longer code.
  </FaqItem>
</Faq>
