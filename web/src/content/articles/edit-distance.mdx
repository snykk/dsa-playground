## How Edit Distance works

Look at the last characters of the two strings. Either they are equal and cost nothing, or the last step of some cheapest edit script is one of three moves. That reduces the problem to a smaller pair of prefixes, and the table stores the answer for every pair of prefixes. Let `dp[i][j]` be the distance between the first `i` characters of `s1` and the first `j` characters of `s2`.

<Steps>
  <Step title="Fill the borders">
    `dp[i][0] = i`: deleting `i` characters turns a prefix into the empty string. `dp[0][j] = j`: inserting `j` characters builds a prefix from nothing.
  </Step>
  <Step title="Match: copy the diagonal">
    If `s1[i-1] == s2[j-1]`, the last characters agree and `dp[i][j] = dp[i-1][j-1]`.
  </Step>
  <Step title="Mismatch: pay 1 for the best move">
    Otherwise `dp[i][j] = 1 + min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1])`: delete from `s1` (up), insert into `s1` (left), or replace (diagonal).
  </Step>
  <Step title="Read the corner">
    The distance between the whole strings is `dp[m][n]`.
  </Step>
</Steps>

<Callout title="Why copying the diagonal on a match is safe">
`dp[i-1][j-1]` is never larger than the other two neighbors plus 1, because dropping one character from a string changes the distance by at most 1. A free match can therefore never be beaten by a delete or an insert, so the code does not look at them.
</Callout>

The distance is the number of non-match steps: 3. The repository code returns only this number, so the traceback is a technique, not a function. When two moves tie, several equally cheap scripts exist.

## Pseudocode

```text
editDistance(s1, s2):
    m = length(s1); n = length(s2)
    dp = (m + 1) x (n + 1) table
    for i = 0 to m: dp[i][0] = i
    for j = 0 to n: dp[0][j] = j
    for i = 1 to m:
        for j = 1 to n:
            if s1[i-1] == s2[j-1]:
                dp[i][j] = dp[i-1][j-1]
            else:
                dp[i][j] = 1 + min(dp[i-1][j],      # delete
                                   dp[i][j-1],      # insert
                                   dp[i-1][j-1])    # replace
    return dp[m][n]
```

## Implementation

All three languages have the same single function over a 2D table, returning only the distance. Python compares Unicode code points. C++ and Go compare **bytes**, so a non-ASCII character that takes several bytes in UTF-8 costs several edits. An accented e takes two bytes, so comparing it with a plain e costs 1 edit in Python but 2 in C++ and Go. Normalize or convert to code points first if that matters.

Without the table the recursion branches three ways on every mismatch:

<Equation label="Plain recursion" expr="T(m, n) = T(m-1, n) + T(m, n-1) + T(m-1, n-1) + O(1)" result="exponential" />

Memoization makes each of the (m + 1)(n + 1) pairs of prefixes cost O(1), which gives the table bound.

## Applications

- **Spell checking and autocorrect.** Suggest dictionary words within a small distance of the typed word.
- **Fuzzy search.** Match queries that contain typos against stored names.
- **Bioinformatics.** Sequence alignment generalizes the same table with scores for matches and gaps.
- **Record linkage.** Decide whether two similar strings name the same thing.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Off-by-one on indices.** The table is one larger than the strings: use `s1[i-1]` and `s2[j-1]` for the cell `dp[i][j]`.
- **Wrong borders.** `dp[0][j] = j`, not 0: building a string of `j` characters from nothing takes `j` inserts.
- **Counting a replace as two edits.** A replace is a single operation.
- **Mixing up bytes and characters.** In C++ and Go a multi-byte character counts as several edits.
- **Expecting a swap to cost 1.** Levenshtein charges 2 for `ab` to `ba`; use Damerau-Levenshtein for 1.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is the edit distance symmetric?">
    Yes. A delete in one direction is an insert in the other, so `d(a, b) = d(b, a)`. The repository tests check this on several pairs.
  </FaqItem>
  <FaqItem question="How is it related to the Longest Common Subsequence?">
    If you allow only inserts and deletes, the distance is `m + n - 2 * LCS`. The replace operation can beat that by fixing a mismatch with one edit instead of two.
  </FaqItem>
  <FaqItem question="How do I reduce the memory?">
    Keep only the previous row and the current row, with the shorter string as the columns. You get O(min(m, n)) space and the same distance, but you lose the traceback.
  </FaqItem>
  <FaqItem question="Can it be faster than O(m n)?">
    For general strings no strongly subquadratic algorithm is known, and under a well-known hardness conjecture none exists. If the distance is small (at most k), there are O(k n) algorithms.
  </FaqItem>
</Faq>
