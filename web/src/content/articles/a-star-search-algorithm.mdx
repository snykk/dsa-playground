## How A* works

Dijkstra's algorithm expands vertices in order of the distance already travelled, g. That is safe but blind: it spreads in every direction. A* adds a guess h(v) of the distance still to go, and expands the vertex with the smallest **f(v) = g(v) + h(v)**. Vertices that look like they lead away from the goal wait in the queue and are often never expanded.

<Steps>
  <Step title="Start the queue">
    Push the start with g = 0 and f = h(start). Record `g[start] = 0`.
  </Step>
  <Step title="Pop the smallest f">
    Take the entry with the smallest f. If it is the goal, return its g and its path. If its g is larger than the recorded `g[v]`, it is a stale entry; skip it.
  </Step>
  <Step title="Relax its edges">
    For each edge to a neighbor, compute `g + w`. If that beats the recorded g of the neighbor, or the neighbor is new, record it and push the neighbor with f = g + h.
  </Step>
  <Step title="Repeat">
    Continue until the goal is popped or the queue is empty, which means the goal is unreachable.
  </Step>
</Steps>

<Callout title="Why the goal can be returned the moment it is popped">
If h never overestimates, then f(v) = g(v) + h(v) is a lower bound on the cost of any complete path through v. When the goal is popped with f = g, every other queued entry has f at least as large, so no path through them can be cheaper. This is also why **h must never overestimate**: a guess that is too large can hide the best path.
</Callout>

## Admissible versus consistent

- **Admissible:** h(v) is at most the true cheapest cost from v to the goal. Required for optimality.
- **Consistent (monotone):** h(u) &le; w(u, v) + h(v) for every edge. This is stronger: every consistent heuristic is admissible. With a consistent h, f never decreases along a path, and the first time a vertex is popped its g is already final.

Many textbook implementations keep a closed set and never reopen a vertex. That is correct only for consistent heuristics. The repository code has no closed set. It compares against `g_scores`, so a vertex whose cost improves later is pushed and expanded again. Here is a graph where the difference matters. The edges are `S->A 1, S->B 1, A->C 1, B->C 2, C->G 3`, with h(A) = 4 and 0 elsewhere. h(A) is admissible (the true cost from A is 4) but not consistent, because h(A) = 4 is more than 1 + h(C) = 1:

## Pseudocode

```text
astar(graph, start, goal, h):
    pq = [(h(start), 0, start, [start])]        # (f, g, vertex, path)
    g = {start: 0}
    while pq is not empty:
        f, gv, v, path = pq.popMin()
        if v == goal: return (gv, path)
        if gv > g[v]: continue                   # stale entry
        for (u, w) in graph.get(v, []):
            t = gv + w
            if u not in g or t < g[u]:           # also re-opens a vertex
                g[u] = t
                pq.push((t + h(u), t, u, path + [u]))
    return none
```

Ties in f are broken by the smaller g (Python tuple order), then by vertex number; C++ and Go compare only f, so equal-f entries can pop in a different order. The returned cost is the same either way.

## Implementation

All three languages take an adjacency list with `(neighbor, weight)` pairs and a heuristic function of one vertex, and return the cost and the path. Python returns `None` when there is no path, C++ returns `(-1, {})` and Go returns `(-1, nil)`. Python also offers `manhattan_distance` and `euclidean_distance` for coordinates; to use them as the callback you wrap them yourself, for example `lambda v: manhattan_distance(pos[v], pos[goal])`.

<TopicCode topic="Algorithms/Graph_Algorithms/Shortest_Path/A_Star_Search_Algorithm" />

Each priority-queue entry carries a copy of its whole path, which keeps the code short but costs O(path length) per push. A production version stores a `came_from` map and rebuilds the path at the end.

Memory is the practical limit: A* keeps every generated vertex, so on large searches it runs out of memory before it runs out of time.

## Applications

- **Grid pathfinding** in games and robots, with Manhattan or Euclidean distance as h.
- **Route planning** on road maps, with straight-line distance as h.
- **Puzzle solving** such as the sliding puzzle, with the sum of tile distances as h.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **An overestimating heuristic.** Optimality is lost silently: you still get a path, but not the cheapest. In this repository the tests check that an over-estimating h only guarantees a path at least as long as the optimum.
- **A closed set on an inconsistent heuristic.** It returns a worse path (the example above). Re-open on a better g, as the repository does.
- **Mixing the cost and the estimate.** The returned cost is g only, not f. The heuristic only steers the search.
- **Negative weights.** A* assumes non-negative weights, like Dijkstra.
- **Passing a pair-valued heuristic.** `manhattan_distance(a, b)` takes two coordinates. The `heuristic` argument takes one vertex, so wrap it.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is A* always better than Dijkstra's algorithm?">
    No. With a heuristic that is close to useless it expands about as many vertices, and it pays for computing h. A* also answers one goal only; Dijkstra gives the distance to every vertex.
  </FaqItem>
  <FaqItem question="What happens if the heuristic overestimates?">
    The search becomes greedy toward the goal. It is usually faster, but it can return a path that is not the cheapest.
  </FaqItem>
  <FaqItem question="Why must h(goal) be zero?">
    An admissible h cannot exceed the true cost, and the true cost from the goal to itself is zero. With h(goal) greater than 0, f would overstate the cost of the finished path.
  </FaqItem>
  <FaqItem question="What does A* return if the goal is unreachable?">
    It empties the queue and reports no path: `None` in Python, `(-1, {})` in C++ and `(-1, nil)` in Go. If start equals the goal, it returns cost 0 and the path with that single vertex.
  </FaqItem>
</Faq>
