## What a Fibonacci heap is

A binary heap is one tree stored in an array and kept tidy after every operation. A Fibonacci heap does the opposite: it keeps a **collection of min-heap-ordered trees** and tidies up only when it has to.

- The roots of the trees sit in a **circular doubly linked list**, the root list.
- Every node stores its key, its `degree` (number of children), a `parent` pointer, one `child` pointer, the `left` and `right` links of its sibling ring, a `marked` flag and an `in_heap` flag.
- A single pointer, `min_node`, points at the root with the smallest key. Every non-root key is at least its parent key, so that root is the global minimum.
- `insert` returns the new node as a **handle**. Passing it back to `decrease_key` or `delete` tells the heap which node to change, so nothing is ever searched for.

<Callout title="Laziness is the design">
Insert does no comparisons with the rest of the heap and no tree merging: it splices a one-node tree into the root list. Merge splices a whole root list. Decrease-key does not sift: it cuts the node off and makes it a root. The cost of the mess is paid later by extract-min, which cleans up all the trees in one sweep.
</Callout>

<Callout title="Handles and stale handles">
A handle is the caller's reference to one node: the node itself in Python and Go, a small `FibonacciHeapHandle` that shares ownership of the node in C++. It becomes **stale** when its node leaves the heap through `extract_min`, `delete` or `clear`: the node's `in_heap` flag turns false, and `decrease_key` and `delete` then refuse the handle with an error and change nothing (`ValueError` in Python, `std::invalid_argument` in C++, a panic in Go). A stale handle is still safe to hold and read. After `a.merge(b)`, the handles of `b`'s nodes belong to `a`. A handle passed to a heap that does not hold its node is not detected, because that check would cost more than O(1), and it leaves both heaps broken: pass a handle only to the heap it came from, or to the heap that heap was merged into.
</Callout>

## Extract min and consolidation

`extract_min()` is the only operation that restructures whole trees:

<Steps>
  <Step title="Promote the children">
    Every child of `min_node` loses its parent pointer and its mark and joins the root list.
  </Step>
  <Step title="Unlink the minimum">
    Remove it from the root list and flag it as no longer in the heap, so its handle turns stale. If it was the only root and had no children, the heap is now empty.
  </Step>
  <Step title="Consolidate">
    Walk the root list once. Keep a table indexed by degree. When two trees of the same degree `d` meet, make the one with the larger root a child of the other: the result has degree `d + 1`. Repeat until every degree appears at most once.
  </Step>
  <Step title="Find the new minimum">
    Scan the (now short) root list for the smallest root.
  </Step>
</Steps>

Inserting `5, 3, 7, 1, 9, 2, 8` leaves seven separate roots, with `1` as the minimum. Extracting it:

## Decrease-key and cascading cuts

Decrease-key is the reason Fibonacci heaps exist. It never sifts a node up. It cuts it loose:

<Steps>
  <Step title="Check and set">
    A stale handle is refused, and so is a key larger than the current one (an equal key is allowed and changes nothing). Otherwise the key is set.
  </Step>
  <Step title="Cut">
    If the node now beats its parent, it leaves the parent's child list and joins the root list right after `min_node`, with its whole subtree, unmarked. The parent's degree drops by one.
  </Step>
  <Step title="Cascading cut">
    Walk up from the parent. An unmarked non-root node has lost its first child: mark it and stop. A marked node has lost its second child: cut it too, and continue with its own parent. A root is never marked, so the walk stops there.
  </Step>
  <Step title="Update the minimum">
    If the new key is smaller than the key at `min_node`, `min_node` moves to the node.
  </Step>
</Steps>

Insert `0` to `8` and extract 0: one tree `1 (2, 5 (6, 7 (8)), 3 (4))` remains. Lowering 8 to 0 cuts it and marks 7; lowering 6 to 3 cuts it and marks 5:

Now lower 7 to 1. It beats its parent 5, so it is cut (and its mark cleared). Its parent 5 was already marked: losing a second child, it is cut as well. The walk reaches 1, a root, and stops.

Why stop a node at two lost children? A node of degree `d` then still roots at least `F(d+2)` nodes, where `F` is the Fibonacci sequence. That keeps every degree below about `1.44 log2(n)`, which is what consolidation needs. Without the cascading cut, the trees could thin out, and the repository's tests catch that: their invariant check after every operation fails as soon as the cascade is removed.

## Delete and merge

`delete(h)` is decrease-key to minus infinity followed by extract-min, without ever writing minus infinity. A sentinel needs a key smaller than every real key, and a Python tuple has none, while a C++ `int` key may itself be `INT_MIN`. So `delete` cuts the node and cascades exactly as decrease-key would, sets `min_node` to the node as if its key were the smallest, and calls `extract_min`.

`merge(other)` splices the circular root list of `other` in right after `min_node`, starting at `other.min_node`: four pointer writes, whatever the sizes. The minimum moves only if the other one is strictly smaller, the counts add up, and `other` is left empty but usable. Merging a heap with itself is an error. The Python tests count the pointer writes of a merge: four, both for heaps of 9 nodes and of 999.

## Why the bounds hold

Consolidation can look expensive: one extract-min may touch many roots. The accounting argument uses a potential function:

<Equation label="Potential" expr="Phi = t + 2m" result="t = number of trees, m = number of marked nodes" />

Insert raises `t` by one, so it costs O(1) plus one unit of potential. Consolidation spends one unit per link, and every link lowers `t` by one, so the work is paid for by potential saved earlier. What remains is the cost proportional to the **maximum degree**, which the `F(d+2)` bound keeps at O(log n).

Decrease-key makes one cut, which adds a tree, and sets at most one mark: O(1) plus a constant rise in potential. Every further cut in the cascade clears a mark, which releases two units: one pays for the cut, one for the new tree. So decrease-key is **O(1) amortized**, however long a single cascade is.

The repository's tests check this by counting rather than timing. After n inserts, a run of decreases (60%), deletes (10%) and extractions (30%) until the heap is empty makes 0.14 to 0.15 cuts per decrease or delete for every n from 1000 to 64000, while the links per extraction or delete grow slowly, from 6.1 to 10.5, like `log n`.

## Why decrease-key matters: Dijkstra

Dijkstra's algorithm extracts each vertex once but may lower a distance once per edge. With a handle per vertex, every improvement is a `decrease_key` instead of a new entry. This is the Python code, with `(distance, vertex)` tuples as keys:

```python
def dijkstra(graph, source):
    dist = {v: math.inf for v in graph}
    dist[source] = 0
    heap = FibonacciHeap()
    handle = {v: heap.insert((dist[v], v)) for v in graph}   # one node per vertex
    while not heap.is_empty():
        d, u = heap.extract_min()                             # V extractions
        for v, w in graph[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heap.decrease_key(handle[v], (dist[v], v))    # up to E decreases
    return dist
```

On the graph A&rarr;B (4), A&rarr;C (1), C&rarr;B (2), B&rarr;D (1), C&rarr;D (5) from A it returns `{'A': 0, 'B': 3, 'C': 1, 'D': 4}` after five `decrease_key` calls and four extractions. A settled vertex is never decreased again, since its distance cannot improve, so no stale handle is used. With O(1) amortized decrease-key the whole run costs O(E + V log V), against O(E log V) with a binary heap.

## Applications

- **Dijkstra and Prim** with many decrease-key calls on dense graphs: the reason the structure was invented.
- **Merging priority queues** often, as in some scheduling and simulation code: merge is a splice.
- **Teaching amortized analysis**: the potential-function argument is a classic example.
- **Insert-heavy priority queues** where most elements are never extracted: the lazy insert costs almost nothing.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Believing the insert advantage is the point.** The advantage is decrease-key.
- **Calling O(log n) extract-min a worst-case bound.** It is amortized; one call can cost O(n).
- **Skipping the cascading cut.** The trees thin out and the degree bound breaks.
- **Keeping a mark when a node becomes a root or is linked.** It would then be cut on its first lost child under the new parent, not its second.
- **Deleting with a sentinel key.** The key type may not have one; cut the node and make it the minimum instead.
- **Using a handle after its node left the heap.** All three languages refuse a stale handle.
- **Walking a tree recursively.** A crafted sequence turns one tree into a path of n nodes (1000 rounds gave a path of 1001), so `clear` uses an explicit stack.
- **Copying a heap in C++.** Nodes are linked through raw pointers, so the C++ class has its copy constructor and assignment deleted.
- **Reading from an empty heap.** `peek` and `extract_min` raise `IndexError` in Python, throw `std::runtime_error` in C++ and panic in Go.
</Callout>

## Implementation

All three versions keep `min_node`, the circular root list, a degree table for consolidation and a `count`, plus counters of links and cuts for the amortized analysis. Python and Go return the node itself as the handle. C++ returns a `FibonacciHeapHandle` that shares ownership of the node, so a stale handle never dangles, and names delete `erase`, because `delete` is a keyword. On equal keys the three agree node for node: the C++ and Go tests pin the trees the Python code builds on the same script.

## Frequently asked questions

<Faq>
  <FaqItem question="Why is it called a Fibonacci heap?">
    Because of the cascading cut, a node of degree d has at least F(d+2) descendants including itself, where F is the Fibonacci sequence. That growth bound is what keeps the maximum degree logarithmic.
  </FaqItem>
  <FaqItem question="What happens if I use a handle after extract_min returned its key?">
    The handle is stale: its node is flagged as no longer in the heap, so decrease_key and delete raise ValueError in Python, throw std::invalid_argument in C++ and panic in Go, and the heap is not changed.
  </FaqItem>
  <FaqItem question="Why mark a node instead of cutting it at its first lost child?">
    Cutting at once would make every decrease-key a long chain of cuts. Allowing one loss per node keeps the trees bushy enough for the F(d+2) bound, and the marks pay for the later cascades, so decrease-key stays O(1) amortized.
  </FaqItem>
  <FaqItem question="Is it faster than a binary heap?">
    Asymptotically better for decrease-key-heavy workloads, but the large constants and poor locality mean binary heaps usually win on real inputs.
  </FaqItem>
  <FaqItem question="Why does extract-min consolidate?">
    Without it the root list would only grow, and finding the next minimum would take O(n). Linking equal-degree trees leaves at most one tree per degree, so the root list has O(log n) entries.
  </FaqItem>
</Faq>
