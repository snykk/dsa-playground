## What a treap is

A treap is a **tree** plus a **heap**. Every node holds a key and a random priority, and the tree obeys two rules at once:

- **BST order on keys:** left keys are smaller, right keys are larger.
- **Heap order on priorities:** a parent's priority is at least its children's (a max-heap).

For a given set of keys and priorities there is exactly one such tree: the highest-priority node is the root, smaller keys go to its left, larger keys to its right, and the same rule applies recursively. Priorities are random, which makes this the same tree as a plain BST built by inserting the keys in a uniformly random order. The expected height of such a tree is O(log n), so it needs no rotations or balance fields.

## Operations

Everything is built from two operations, `split` and `merge`.

    ['`merge(a, b)`', 'join two treaps where every key in `a` is smaller than every key in `b`', 'O(log n)'],
    ['`insert(key)`', 'reject a duplicate; split at `key`; merge left, new node, right', 'O(log n)'],
    ['`delete(key)`', 'split at `key`, drop the minimum of the right part (it is `key`), merge the rest', 'O(log n)'],
    ['`contains(key)`', 'plain BST search', 'O(log n)'],
    ['`inorder()`', 'all keys in sorted order', 'O(n)'],
  ]}

### Split

`split(node, k)` returns `(left, right)` with all keys `< k` in `left` and all keys `>= k` in `right`. If `node.key < k`, the node and its left subtree go to `left`: split the right subtree and attach its left part as `node.right`. Otherwise do the mirror image. The recursion follows one root-to-leaf path.

### Merge

`merge(a, b)` looks at the two roots. The higher priority stays on top. If it is `a`, then `a.right = merge(a.right, b)`; otherwise `b.left = merge(a, b.left)`. This preserves both orders, because every key in `a` is smaller than every key in `b`.

## Implementation

All three versions are the split/merge formulation with these API differences:

<DataTable
  columns={['', 'Python', 'C++', 'Go']}
  rows={[

    ['insert / remove', '`insert`, `delete`', '`insert`, `erase`', '`Insert`, `Delete`'],
    ['membership', '`key in treap`', '`contains`', '`Contains`'],
    ['size', '`len(treap)`', '`size()`', '`Len()`'],
    ['duplicates', 'rejected (`False`)', 'rejected (`false`)', 'rejected (`false`)'],
    ['key type', 'anything ordered', '`int`', '`int`'],
  ]}
/>

Delete does not split at `key + 1`. That trick overflows at the largest integer (C++ undefined behavior, Go wraps around and silently leaves the key behind) and means nothing for float keys. Instead the code splits at `key` and drops the minimum node of the right part, which is exactly the key being deleted.

## Complexity

<DataTable
  columns={['Operation', { label: 'Expected', kind: 'mono' }, { label: 'Worst case', kind: 'mono' }]}
  rows={[
    ['search, insert, delete', 'O(log n)', 'O(n)'],
    ['split, merge', 'O(log n)', 'O(n)'],
    ['space', 'O(n)', 'O(n)'],
  ]}
/>

Why expected O(log n): fix the keys. A node's depth is the number of ancestors it has, and a key `j` is an ancestor of key `i` exactly when `j` has the highest priority among all keys between them. With random priorities that probability is 1 / (|i - j| + 1), so the expected depth is a harmonic sum:

<Equation label="Expected depth of key i" expr="sum over j != i of 1 / (|i - j| + 1)" result="<= 2 ln(n) = O(log n)" />

The worst case needs very unlucky priorities. Priorities are drawn by the program, so someone who controls only the keys cannot force a deep tree.

## Applications

- Ordered sets and maps in competitive programming, where short code matters.
- Implicit treaps for sequences: range reversal, cut and paste, insert at a position.
- Order-statistic queries (k-th smallest, rank) when each node stores its subtree size.
- Merging and splitting ordered collections.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Splitting off a single key with `key + 1`.** It overflows at the top of the integer range and fails for non-integer keys. Drop the minimum of the right part instead.
- **Weak or reused randomness.** Equal priorities or a predictable generator weaken the balance.
- **Merging in the wrong order.** `merge(a, b)` requires every key of `a` to be smaller than every key of `b`.
- **Leaving the duplicate policy open.** Decide up front: this code rejects duplicates and returns false.
- **Forgetting augmented data.** If nodes store size or sum, update it after every split and merge step.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why are treaps balanced?">
    The priority order decides the shape, and random priorities make the shape that of a BST built from shuffled keys. Such trees have expected depth O(log n).
  </FaqItem>
  <FaqItem question="Do treaps need rotations?">
    Not in this code. Split and merge restructure the tree along one path each. A rotation-based treap exists and gives the same shape.
  </FaqItem>
  <FaqItem question="What if two nodes get the same priority?">
    Ties are rare with floats or 32-bit random values, and the code breaks them without error (in merge, the second treap's root wins). Heavy ties would hurt balance but never correctness.
  </FaqItem>
  <FaqItem question="Why a max-heap on priorities and not a min-heap?">
    It is only a convention. The code keeps the largest priority at the root, which is what `merge` checks with `a.priority > b.priority`.
  </FaqItem>
</Faq>
