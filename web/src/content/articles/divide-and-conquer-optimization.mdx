## How Divide and Conquer Optimization works

Split `n` numbers into exactly `k` contiguous, non-empty groups so that the sum over the groups of `(sum of the group)^2` is as small as possible. The square punishes a heavy group, so the best split balances the sums. Let `dp[g][i]` be the best cost of the first `i` values in `g` groups. The last group is `values[j:i]` for some `j`:

<Equation label="One layer" expr="dp[g][i] = min over j in [g-1, i-1] of dp[g-1][j] + C(j, i)" result="C(j, i) = (P[i] - P[j])^2, from the prefix sums P" />

Filled directly, each cell tries every `j`, and a layer of `n` cells costs O(n<sup>2</sup>). Call the best `j` of cell `i` `opt(g, i)`. For this cost it never moves left: `opt(g, i)` &le; `opt(g, i + 1)`. One layer then goes like this:

<Steps>
  <Step title="Solve the middle cell first">
    Of the cells `lo..hi` of the call, take `mid = (lo + hi) // 2`. Try every `j` the call allows, from `max(opt_lo, g - 1)` to `min(opt_hi, mid - 1)`, going up, and keep the smallest `j` with the least `dp[g-1][j] + C(j, mid)`.
  </Step>
  <Step title="Split the range of j at that best j">
    Every cell left of `mid` has its best `j` at or below `opt(g, mid)`, and every cell right of it at or above. So the left half is solved with `j` in `opt_lo..opt(g, mid)` and the right half with `j` in `opt(g, mid)..opt_hi`.
  </Step>
  <Step title="Recurse, one layer after another">
    The first call covers the whole layer, cells `g..n` with `j` in `g-1..n-1`. Layer 1 is one group, `dp[1][i] = C(0, i)`, and each later layer reads the one before it.
  </Step>
  <Step title="Walk back to the groups">
    `bounds[k] = n`, then `bounds[g - 1] = opt(g, bounds[g])` down to `g = 2`, and `bounds[0] = 0`. Group `g` is `values[bounds[g]:bounds[g + 1]]`.
  </Step>
</Steps>

<Callout title="Why the halves never lose the answer">
The ranges of `j` that the calls at one depth of the recursion try only touch at their ends, so each depth tries about `n` values of `j` in all, and there are about log<sub>2</sub>(n) depths. That is only correct because `opt` is monotone. With a cost that breaks this, the recursion still returns a split and its true cost, just not the best one, and nothing fails.
</Callout>

Layer 3 tries 3 + 1 + 2 + 3 + 2 + 3 = 14 values of `j`. The walk back reads `opt(3, 8) = 6` and `opt(2, 6) = 4`, so `min_cost_partition(values, 3)` returns `(341, [0, 4, 6, 8])` after 8 + 19 + 14 = 41 cost evaluations; `min_cost_partition_plain` returns the same after 8 + 28 + 21 = 57.

**When the inequality fails.** With `values = [1, 2, 4, -5]` and `k = 2`, the prefix sums `0, 1, 3, 7, 2` go down at the end. The recursion solves `i = 3` first: `j = 1` gives 1 + 36 = 37 and `j = 2` gives 9 + 16 = 25, so `opt = 2`. The right half, `i = 4`, then tries only `j` in 2..3 and returns 9 + 1 = 10, the groups `[1, 2]` and `[4, -5]`. The best split is `[1]` and `[2, 4, -5]`, cost 1 + 1 = 2, at `j = 1`, which that call never tries. `partition_dp(4, 2, cost, optimized=True)` returns `(10, [0, 2, 4])`, and `optimized=False` returns `(2, [0, 1, 4])`.

## Pseudocode

```text
partition_dp(n, k, C):
    for i = 1 to n: dp[1][i] = C(0, i)                 # one group
    for g = 2 to k: solve(g, g, n, g - 1, n - 1)
    bounds[k] = n
    for g = k down to 2: bounds[g - 1] = opt[g][bounds[g]]
    bounds[0] = 0
    return dp[k][n], bounds

solve(g, lo, hi, opt_lo, opt_hi):
    if lo > hi: return
    mid = (lo + hi) // 2
    best = infinity
    for j = max(opt_lo, g - 1) to min(opt_hi, mid - 1):    # going up
        if dp[g-1][j] + C(j, mid) < best:                   # strictly: the smallest j wins ties
            best = dp[g-1][j] + C(j, mid)
            opt[g][mid] = j
    dp[g][mid] = best
    solve(g, lo, mid - 1, opt_lo, opt[g][mid])              # left: j <= opt(mid)
    solve(g, mid + 1, hi, opt[g][mid], opt_hi)              # right: j >= opt(mid)
```

**Which groups.** `opt(g, i)` is the smallest `j` that reaches the minimum: `j` goes up and only a strictly smaller candidate replaces the best. So of several best splits the code returns the one whose last cut is smallest, then the cut before it, and so on. With `[1, 1, 1, 1, 1]` and `k = 2`, the splits 2 + 3 and 3 + 2 both cost 13, and the code returns `[0, 2, 5]`. The plain DP uses the same `_best_split`, so both versions return the same bounds, and the tests check them against every split of small inputs. The C++ and Go tests check 44 inputs, 12 inputs where the recursion fails, and the cost evaluations on 8 more against outputs of the Python code.

**Edge cases.** Groups are never empty, so `k` runs from 1 to `n`: `k > n`, `k < 1` and every `k` on an empty list are errors. `k = 1` returns `P[n]^2` and `[0, n]`; `k = n` puts every value alone. A negative value is an error in the two concrete functions, because it can break the quadrangle inequality; `partition_dp` takes any cost and does not check.

## Complexity analysis

The calls at one depth of a layer's recursion cover disjoint cells, and their ranges of `j` follow each other, sharing at most an end. So one depth tries at most `m` plus its number of calls values of `j`, for a layer of `m` cells. With `floor(log2(m)) + 1` depths and `m` calls in all, a layer costs at most `m (floor(log2(m)) + 2)` cost evaluations.

At `n = 4096` each layer after the first costs between 48,000 and 49,200 evaluations, about `n log2(n)` = 49,152, where the plain DP costs about `n^2 / 2`. The space is the table of best `j`, needed for the walk back; the costs themselves need only two rows.

<Callout tone="warning" title="Overflow in C++ and Go">
Every number the DP forms is the cost of splitting a prefix into groups, at most the square of the total, and the DP forms that square itself in layer 1. So C++ and Go check once that the total is at most 3,037,000,499, whose square is the largest that fits in 64 bits, and report an overflow otherwise. Python is exact: `[3037000499, 1]` in two groups costs 9,223,372,030,926,249,002 there, which fits, but C++ and Go report it, because its total does not square into 64 bits.
</Callout>

## The quadrangle inequality

`opt` is monotone whenever the cost satisfies, for all `a` &le; `b` &le; `c` &le; `d`:

<Equation label="Quadrangle inequality" expr="C(a, c) + C(b, d) <= C(a, d) + C(b, c)" result="two crossing groups cost no more than the outer and the inner one" />

Suppose the smallest best `j` of cell `i` were larger than the best `j'` of a later cell `i'`. Then `j'` loses to `j` at `i`, and the inequality with `a = j'`, `b = j`, `c = i`, `d = i'` says that going from `i` to `i'` adds no more to `j`'s cost than to `j'`'s, so `j'` still loses at `i'`: a contradiction. For the square of the sum the two sides differ by exactly

<Equation label="This cost" expr="C(a, c) + C(b, d) - C(a, d) - C(b, c) = -2 (P[b] - P[a]) (P[d] - P[c])" result="at most 0 when every value is 0 or more" />

That is why this cost was chosen: integers only (the squared deviation from a group's mean needs fractions), O(1) per cost from the prefix sums, a proof in one line, and with one negative value the same formula breaks. In `1, 2, 4, -5`, `C(1, 3) + C(2, 4)` = 36 + 1 = 37 is more than `C(1, 4) + C(2, 3)` = 1 + 16 = 17. The tests check the inequality on 400 random inputs with no negative value, and on 3000 random inputs with negative values they find the recursion's answer different from the plain DP's 219 times.

For this particular cost the Convex Hull Trick applies too: `(P[i] - P[j])^2` expands into `P[i]^2 - 2 P[j] P[i] + P[j]^2`, a line in `P[i]` for each `j`. Divide and conquer needs no such formula, only the monotone `opt`, so it also covers costs that are not lines in anything, such as the number of equal pairs inside a group.

## Applications

- **Splitting a sequence into k parts.** Balanced loads, the least sum of squares, or any cost of a part with the inequality.
- **Placing k facilities on a line.** Mailboxes or warehouses for sorted houses, each serving a contiguous run.
- **Scheduling jobs in order on k days or machines**, when a day's cost grows faster than linearly with its work.
- **Grouping with a costly measure**, such as the number of equal pairs in a segment, where the cost is kept by a window that the recursion moves.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Not checking the inequality.** With `[1, 2, 4, -5]` the recursion returns 10 instead of 2. Prove it, or compare with the plain DP on small random inputs.
- **Forgetting to narrow.** Passing the whole range of `j` to both halves still gives the right answers, at the plain DP's cost; the tests count the evaluations to catch it.
- **The clamps.** `j` must stay below `mid`, so the last group is not empty, and at least `g - 1`, so the earlier groups are not.
- **`<=` for the update.** The cost stays right, but the code then keeps the largest best `j` and returns other groups on ties.
- **`k > n`.** Groups cannot be empty, so it is an error, not the same as `k = n`.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why solve the middle cell first?">
    Its best j splits the range of j in two for the cells on each side. Taking the middle cell halves the cells at every depth, so there are about log2(n) depths, and each depth tries about n values of j in all.
  </FaqItem>
  <FaqItem question="How do I know my cost has a monotone opt?">
    Prove the quadrangle inequality, as the topic does for the square of a group's sum with values of 0 or more. If you cannot, run the plain DP beside the recursion on small random inputs: a wrong answer is the only symptom.
  </FaqItem>
  <FaqItem question="What happens with k greater than n?">
    The code raises an error. Every group must hold at least one value, so there is no way to split n values into more than n groups; k = n puts every value alone.
  </FaqItem>
  <FaqItem question="Should I use the Convex Hull Trick instead?">
    When the cost expands into lines, as the square of a sum does, the Convex Hull Trick is O(k n) and faster. Divide and conquer is the choice when the cost has no such form, or when its monotone opt is easier to prove than the lines are to find.
  </FaqItem>
</Faq>
