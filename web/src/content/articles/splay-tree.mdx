## What a splay tree is

A splay tree is an ordinary binary search tree, plus one rule: **after every access, move the accessed node to the root** by a sequence of rotations called *splaying*. There are no colors, heights or priorities to maintain.

Why this helps:

- Keys that are used often stay near the top, so the tree adapts to the access pattern.
- A splay also roughly halves the depth of every node on the access path, which repairs bad shapes. A long path is expensive once, and then it is mostly gone.

The price: a single operation can take O(n) (a splay tree built from sorted inserts is a path), and even a read changes the tree. Only the *amortized* cost over a sequence is O(log n).

### The three splay cases

Let `x` be the node, `p` its parent and `g` its grandparent. Each step looks at the shape of the path `g - p - x`:

<DataTable
  columns={['Case', 'Shape', 'Rotations']}
  rows={[
    ['Zig', '`p` is the root', 'one rotation at `p`'],
    ['Zig-zig', '`x` and `p` are both left children (or both right)', 'rotate at `g` first, then at `p`'],
    ['Zig-zag', '`x` is a left child and `p` a right child (or the reverse)', 'rotate at `p`, then at `g`'],
  ]}
/>

The order in zig-zig matters. Rotating the grandparent first is what makes a long path shrink, while rotating `x` upward twice (as the naive "move to root" does) can leave the tree just as deep.

### Delete: split and join

Delete splays the key to the root, then glues the halves back together. The code detaches both subtrees and clears their parent pointers, splays the **maximum of the left subtree** to the top of that subtree (it then has no right child), and hangs the right subtree there.

## Implementation

All three languages keep a parent pointer in each node and use the same splay code. The behaviour on edge cases differs a little:

<DataTable
  columns={['Case', 'Python', 'C++', 'Go']}
  rows={[

    ['`search` miss', '`None`', 'empty string', 'zero value and `false`'],
    ['`find_min` on empty tree', '`None`', '`-1`', '`0, false`'],
    ['`delete` / `remove`', '`delete`', '`remove`', '`Delete`'],
    ['copying the tree', 'shares nodes', 'deleted', 'shares nodes'],
  ]}
/>

In C++ a missing key and a key stored with an empty value look the same from `search`, and `findMin` returns `-1` on an empty tree, which collides with a real key `-1`. Traversal, size and destruction are iterative, because sequential inserts build a path and recursion would overflow the stack on large inputs.

### Why amortized O(log n)

Define a potential equal to the sum over all nodes of log<sub>2</sub> of the subtree size. A tall thin tree has high potential, and a balanced one has low potential. The *access lemma* of Sleator and Tarjan shows that splaying a node costs at most 3 log<sub>2</sub> n + 1 amortized: expensive splays pay for themselves by lowering the potential.

<Equation label="Amortized cost of one splay" expr="actual cost + change in potential" result="<= 3 log2(n) + 1" />

The bound only holds if **every** access splays, including failed searches and failed deletes. That is why the code splays the last visited node on a miss. Without it, repeated searches for a missing key below a deep path would each cost O(n).

The same potential argument gives further guarantees: accessing all keys in sorted order costs O(n) in total, and a skewed access pattern costs about the entropy of the pattern.

## Applications

- Caches and lookup tables where a small set of keys is hot.
- Sorted maps where the access pattern is skewed or sequential.
- Building blocks for data structures that need split and join, because both are natural in a splay tree.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Not splaying on a miss.** Failed searches and failed deletes must still splay the last visited node, or the amortized bound is lost.
- **Dangling parent pointers in delete.** After detaching the two subtrees, clear their `parent` links before splaying inside the left one. Skipping this once corrupted the tree in the C++ and Go versions (a deleted node was rotated back in).
- **Zig-zig in the wrong order.** Rotate the grandparent first, then the parent.
- **Recursive traversal.** Sequential inserts make the tree a path; recursive size or traversal then overflows the stack.
- **Copying the tree.** Nodes are owned by one tree, so copying must be disabled (C++) or avoided (Go, Python share nodes).
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is amortized O(log n) the same as average O(log n)?">
    No. Amortized is a worst-case bound on the total cost of any sequence of operations divided by their number. Average-case would assume random inputs. A splay tree can have one very slow operation, but it cannot have many in a row.
  </FaqItem>
  <FaqItem question="Why does searching change the tree?">
    Moving the accessed node to the root is the whole mechanism for adaptation and for the amortized bound. A search is not read-only in a splay tree.
  </FaqItem>
  <FaqItem question="Why not just rotate the accessed node to the root one rotation at a time?">
    That works for a single access, but a sequence of accesses to a path can then cost O(n) each. The zig-zig and zig-zag cases halve the depth of the nodes on the path, which the amortized proof needs.
  </FaqItem>
  <FaqItem question="Which implementation detail is easiest to get wrong?">
    Delete. The key must be splayed to the root first, and both subtrees detached with cleared parent pointers before the maximum of the left subtree is splayed.
  </FaqItem>
</Faq>
