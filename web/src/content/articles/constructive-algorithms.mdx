## When to use it

The statement gives away constructive problems:

- "Print **any** array / string / graph such that ..." or "print `-1` if it does not exist".
- The output is large (size `n`), so the checker, not the contestant, verifies it.
- Constraints are about **structure**: sums, parities, distinct differences, degrees, no two equal neighbors.
- Brute force is impossible, yet small cases are easy to do by hand.

## How it works

<Steps>
  <Step title="Do the small cases by hand">
    Build solutions for `n = 1, 2, 3, 4, 5`. Write them next to each other and look for the shape: sorted, alternating, zig-zag, powers of two.
  </Step>
  <Step title="Find when it is impossible">
    Look for the cheapest necessary condition: a sum outside `[n*lo, n*hi]`, an odd degree sum, a character that appears more than `ceil(n/2)` times. Return "impossible" for those inputs first.
  </Step>
  <Step title="State the rule and build greedily">
    Turn the pattern into a loop: fill with the minimum and add the remainder, always connect the highest remaining degree, put the more frequent letter in even positions.
  </Step>
  <Step title="Prove it, then verify it">
    Argue that every constraint holds (an invariant per step), and write a checker that you run over all small inputs. Most wrong constructions fail on the first few sizes.
  </Step>
</Steps>

<Callout title="The two-sided guarantee">
A constructive solution must be both **sound** (whatever it returns satisfies the constraints) and **complete** (it only reports "impossible" when no object exists). Checking soundness is easy with a verifier; completeness needs the necessary condition from step 2 to match what the builder can actually produce.
</Callout>

## Template

```text
solve(input):
    if not feasible(input):         # necessary condition, derived on paper
        return IMPOSSIBLE
    result = empty
    while result is not complete:
        result.append(next piece by the rule)    # greedy / zig-zag / alternate
    assert check(result, input)     # in tests, run on all small inputs
    return result
```

## Worked example: k distinct differences

Build a permutation of `1..n` whose adjacent differences `|p[i+1] - p[i]|` contain **exactly** `k` different values. For `n = 7` and `k = 3` the code returns `[1, 4, 2, 3, 5, 6, 7]`.

    { label: 'differences', values: [3, 2, 1, 2, 1, 1], tones: 'ppplll', note: 'The zig-zag gives 3, 2, 1: exactly k = 3 distinct values. The tail adds only 2 and 1, both already present.' },

/>

Why it works: alternating between the smallest and the largest unused number of `1..k+1` produces differences `k, k-1, ..., 1`, each once. The first tail element `k + 2` differs from the last zig-zag value by between 1 and `k`, and later steps are 1. No new value appears, so there are exactly `k`.

<Callout tone="warning" title="This was a bug in the repository">
The earlier code only reversed a suffix of `1..n`, which gives at most 2 distinct differences whatever `k` is: for `(5, 3)` it returned `[1, 5, 4, 3, 2]`. The zig-zag version is checked against every `(n, k)` with `n` up to 12 in all three languages' tests.
</Callout>

## Worked example: a graph from degrees

`construct_graph([3, 3, 2, 2, 2])` repeats: take the node with the largest remaining degree `d`, connect it to the next `d` largest, reduce those degrees. Result: edges `(0,1) (0,2) (0,3) (1,4) (1,2) (3,4)`.

## Implementation

Python has all nine builders, C++ has seven (everything except `construct_tree` and `construct_balanced_string`), Go has three (`ConstructPermutation`, `ConstructArrayWithSum`, `ConstructGraph`). Impossible input returns `None` in Python, an empty vector in C++ and `nil` in Go. In C++, `constructString` returns an empty string for impossible input, so `n = 0` and "impossible" look the same.

Each language has tests: Python `constructive_test.py`, C++ `constructive_test.cpp`, Go `main_test.go`. They check the permutation builder over all small `n` and `k`, and the graph builder against an Erdos-Gallai test in Python.

## Variants

- **Existence only:** decide whether an object exists (Erdos-Gallai) without building it.
- **Count or lexicographically smallest:** the same rule with a tie-breaking order, or a counting formula.
- **Construction from the end:** build in reverse, then flip it.
- **Randomised verification:** write a brute force for small `n` and compare feasibility and validity with your builder.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Skipping the feasibility check.** `construct_string(5, 1, 1)` used to return `abaaa`, which has equal neighbors, because `n != a + b` was never checked.
- **Trusting a pattern after one example.** Test every size `n` up to about 10 with a checker. The old permutation passed a test that only compared the length.
- **Hard-coded bit limits.** Scanning 30 bits silently dropped bit 30 and above in `construct_by_decomposition`.
- **Ignoring the empty case.** Empty input and `n = 1` are where divisions by zero and off-by-ones hide.
- **Mutating the caller's input.** The C++ matrix builder now takes its sums by value.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="How is a constructive problem different from greedy or DP?">
    Greedy and DP optimise a value over choices. A constructive problem asks for any object satisfying constraints. Greedy rules are a common way to build it, but the focus is on producing and proving the object, not on optimality.
  </FaqItem>
  <FaqItem question="How do I know my construction is complete?">
    Show that if the input passes your feasibility test, the builder always succeeds, and that every input failing the test truly has no answer. A brute force on small inputs checks both directions.
  </FaqItem>
  <FaqItem question="Why is Havel-Hakimi correct?">
    If a graph with the degree sequence exists, there is one in which the vertex of largest degree is adjacent to the next largest ones. Removing it and lowering their degrees leaves a smaller problem of the same kind. The repository's `construct_graph` is Havel-Hakimi and agreed with an Erdos-Gallai check on thousands of random sequences.
  </FaqItem>
  <FaqItem question="What does the matrix builder do with negative sums?">
    Nothing special: it assumes non-negative row and column sums. With equal totals, the north-west corner rule always fills it.
  </FaqItem>
</Faq>
