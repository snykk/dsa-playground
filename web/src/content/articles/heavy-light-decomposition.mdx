## When to use it

Use heavy-light decomposition (HLD) when you must answer **many queries or updates on tree paths**, online:

- "What is the sum / max of the values on the path from `u` to `v`?"
- "Add `x` to every node on the path from `u` to `v`."
- "What is the lowest common ancestor of `u` and `v`?"

A path in a tree is not a contiguous range of anything, so a segment tree cannot answer it directly. HLD renumbers the nodes so that long stretches of a path *are* contiguous.

## Heavy and light edges

Root the tree and compute every subtree size. For each internal node, the edge to its **heavy child** (the child with the largest subtree; the first one in adjacency order on ties) is a *heavy* edge. All other edges are *light*. Heavy edges join into vertical **chains**, and every node belongs to exactly one chain.

<Callout title="Why only O(log n) chains">
Going from a node up to the root, each light edge leads to a parent whose subtree is **more than twice** as large as the child's (the heavy sibling is at least as big as the child). Sizes can double at most log<sub>2</sub> n times, so a path to the root uses at most log<sub>2</sub> n light edges, and therefore crosses at most floor(log<sub>2</sub> n) + 1 chains.
</Callout>

## How it works

<Steps>
  <Step title="Sizes, depths and heavy children">
    Walk the tree from the root and record each node's `parent`, `depth` and subtree `size`. For every node, `heavy[u]` becomes the child with the largest size (`-1` for a leaf).
  </Step>
  <Step title="Number the nodes chain by chain">
    Visit the tree in pre-order, always descending into the heavy child first. Each node gets `head[u]` (the top of its chain) and `pos[u]` (its index in the array). A heavy child continues its parent's chain; a light child starts a new chain with itself as the head.
  </Step>
  <Step title="Answer a query by climbing chains">
    While `u` and `v` are on different chains, take the one whose chain head is deeper, handle the segment from that head down to the node (contiguous in `pos`), and jump to the head's parent. When both are on one chain, the last segment lies between them.
  </Step>
</Steps>

Because the heavy child is visited first, every chain occupies consecutive positions, and each subtree is contiguous too.

## Pseudocode

```text
build(root):
    reset parent, depth, size, heavy, cur_pos
    dfs_size(root, -1)            # parent, depth, size, heavy child
    decompose(root, root)         # head, pos

decompose(u, h):                  # pre-order, heavy child first
    head[u] = h
    pos[u]  = cur_pos++
    if heavy[u] != -1:  decompose(heavy[u], h)
    for v in adj[u]:
        if v != parent[u] and v != heavy[u]:
            decompose(v, v)       # a light child heads a new chain

lca(u, v):
    while head[u] != head[v]:
        if depth[head[u]] < depth[head[v]]:  swap(u, v)
        u = parent[head[u]]
    return u if depth[u] <= depth[v] else v

query_path(u, v):                 # Python only
    segments = []
    while head[u] != head[v]:
        if depth[head[u]] < depth[head[v]]:  swap(u, v)
        segments.append((pos[head[u]], pos[u]))
        u = parent[head[u]]
    if depth[u] > depth[v]:  swap(u, v)
    segments.append((pos[u], pos[v]))
    return segments
```

## Implementation

What each language really provides:

- **Python** builds the decomposition (`head`, `pos`, `depth`, `parent`, `size`, `heavy`), and offers `lca(u, v)` and `query_path(u, v)`, which returns the list of `(lo, hi)` position segments. Its two passes are iterative, so a path of thousands of nodes is fine.
- **C++ and Go** build the same arrays and offer only `lca` (`lca` / `LCA`). Their DFS is recursive.
- **No language contains a segment tree**, a path sum, or a path update. The segments are the hook where you plug one in; the code stops there.

`build` resets its working state, so it can be called more than once.

## Applications

- Path sums, maxima and minima with point updates.
- Adding a value along a path and querying a node.
- LCA without a separate structure.
- CSES Tree Algorithms: "Path Queries II" and "Path Queries" are the standard exercises.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Skipping the size pass.** `decompose` needs `heavy` first. Calling it on a fresh object gives a broken decomposition.
- **Wrong swap rule.** Always climb from the node whose chain **head** is deeper, not the node that is deeper.
- **Off-by-one in the last segment.** When both nodes share a chain, the segment runs from the shallower to the deeper `pos`, inclusive.
- **Forgetting that `pos` is not node id.** Segment tree indices are `pos[u]`, not `u`.
- **Edge values.** If values live on edges, the LCA node must be excluded from the final segment.
- **Reusing state.** A second build without resetting `cur_pos` numbers nodes past `n - 1`; the repository's `build` resets it for you.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why heavy by subtree size and not by depth?">
    Size is what bounds the number of light edges: a light edge at least doubles the subtree size above it.  A decomposition by depth is a different technique and does not give the same guarantee.
  </FaqItem>
  <FaqItem question="Are subtrees contiguous in pos?">
    Yes. The pre-order visits a node and then its whole subtree before moving on, so the subtree of `u` is `pos[u]` to `pos[u] + size[u] - 1`.
  </FaqItem>
  <FaqItem question="Do the repository implementations answer path sums?">
    No. They provide the decomposition, `lca` in all languages, and `query_path` (position segments) in Python only. A segment tree over `pos` is left to the reader.
  </FaqItem>
  <FaqItem question="When is binary lifting better?">
    When you only need LCA or a static aggregate along an ancestor path and do not mind O(n log n) memory. HLD wins when values change.
  </FaqItem>
</Faq>
