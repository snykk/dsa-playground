## What an AVL tree is

An AVL tree is a binary search tree with one extra rule, the **AVL property**: for every node, the heights of its left and right subtrees differ by at most 1. The difference `height(left) - height(right)` is the node's **balance factor**, and it must be -1, 0 or +1.

Each node stores its own height (a leaf has height 1 in this repository, an empty subtree 0), so the balance factor costs two lookups. Whenever an insert or delete pushes some balance factor to +2 or -2, a **rotation** restores the property without breaking the search order.

<Callout title="Why balanced means logarithmic">
Let N(h) be the fewest nodes an AVL tree of height h can have. The sparsest tree has one subtree of height h - 1 and the other of height h - 2, so N(h) = N(h - 1) + N(h - 2) + 1. That is a Fibonacci-style recurrence (N = 1, 2, 4, 7, 12, 20, ...) which grows exponentially, so n nodes force a height of at most about 1.44 log<sub>2</sub>(n + 2). A plain BST has no such bound: sorted input turns it into a chain of height n.
</Callout>

## Rotations

A rotation is a local change of three links that lifts one node above its parent. Take the right rotation at `z`, whose left child is `y`. The subtree `T2` between them moves from `y` to `z`, which is safe because every key in `T2` is greater than `y` and smaller than `z`.

After the insert or delete, the first node on the way back up with balance factor +2 or -2 falls into one of four cases:

<DataTable
  columns={['Case', 'Condition', 'Fix']}
  rows={[
    ['Left-Left', 'bf(node) > 1 and the left child leans left or is even (bf >= 0)', 'rotate right at the node'],
    ['Right-Right', 'bf(node) < -1 and the right child leans right or is even (bf <= 0)', 'rotate left at the node'],
    ['Left-Right', 'bf(node) > 1 and the left child leans right (bf < 0)', 'rotate left at the left child, then right at the node'],
    ['Right-Left', 'bf(node) < -1 and the right child leans left (bf > 0)', 'rotate right at the right child, then left at the node'],
  ]}
/>

The "even" sub-case (child balance factor 0) never happens after an insert, but it does after a delete, and it needs a single rotation. Treating it as a double rotation is a classic bug.

Insertion needs at most one rebalancing (a single or a double rotation): once the lowest unbalanced node is fixed, its subtree has the height it had before the insert, so the ancestors above are fine again.

## Delete walk-through

Delete is a plain BST delete (zero, one or two children, with the in-order successor replacing a two-child node), followed by the same rebalancing on every ancestor. Unlike insert, a fix can shorten the subtree, which can unbalance the parent too, so rotations may repeat up to the root.

## Implementation

The Python, C++ and Go versions are line-for-line the same recursive design: `insert` and `delete` recurse down, then update the height and rebalance as the calls return. Rotations are `rotate_left` and `rotate_right`. Differences:

- Python also has pre-order, post-order and level-order traversals; C++ and Go have in-order only.
- Empty-tree `find_min` and `find_max`: Python returns `None`, C++ throws `std::runtime_error`, Go returns an error.
- The C++ class owns raw pointers, so it is not copyable (copy constructor and assignment are deleted).
- Recursion depth is the tree height, about log n, so deep recursion is not a concern.

## Applications

- Ordered maps and sets where lookups far outnumber updates.
- In-memory indexes and dictionaries that need a worst-case guarantee.
- A reference point for learning other balanced trees (Red-Black, Treap, Splay).

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Reading stale heights.** Update the height of a node after its children changed and before computing its balance factor, and in rotations update the lower node first.
- **Wrong case after a delete.** When the heavy child has balance factor 0, use a single rotation, not a double one.
- **Choosing the case by the inserted key only.** That works for insert but not for delete, where no key has been added. Look at the heavy child's balance factor.
- **Stopping at the first rotation on delete.** Keep walking to the root; the recursive code does this by checking every ancestor.
- **Testing balance with stored heights.** A test that trusts the stored `height` field cannot catch a stale height. Recompute heights from scratch.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why is the height bound about 1.44 log2(n)?">
    The thinnest AVL tree of height h has N(h) = N(h - 1) + N(h - 2) + 1 nodes, which grows like the Fibonacci numbers, about 1.618<sup>h</sup>. Taking logarithms gives h &lt; 1.44 log<sub>2</sub>(n + 2).
  </FaqItem>
  <FaqItem question="Does insert ever need more than one rotation?">
    No. It needs at most one single or one double rotation, because that fix brings the subtree back to its old height. Delete can need one rotation per level.
  </FaqItem>
  <FaqItem question="AVL or Red-Black?">
    AVL is stricter, so it has faster lookups and slower updates. Red-Black does less rebalancing work per update. For read-heavy data AVL tends to win; for write-heavy data Red-Black does.
  </FaqItem>
  <FaqItem question="What happens when I insert a duplicate key?">
    Nothing: the tree stores each key once and returns without changing it.
  </FaqItem>
</Faq>
