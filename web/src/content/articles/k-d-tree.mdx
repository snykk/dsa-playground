## What a K-D tree is

A binary search tree splits the number line: smaller keys left, larger keys right. A K-D tree does the same for points in k dimensions by changing the **splitting axis with depth**: the root splits on coordinate 0, its children on coordinate 1, and so on, returning to 0 after k levels (axis = `depth mod k`).

Each node stores one point. At a node with axis `a`, points with a smaller `a`-coordinate go left and the others go right. Each node therefore owns a rectangular region of space, cut in two by the line (or plane) through its point.

<Callout title="The invariant">
At a node splitting on axis `a`, points in the left subtree have an `a`-coordinate at most the node's, and points in the right subtree have one at least the node's. (Repeated inserts send equal coordinates right; the median builder can leave an equal coordinate on the left.) The searches below only rely on this split value, so they are correct either way.
</Callout>

## See it in action

Run **Nearest to (1,3) (README)**: the build draws each split line inside its parent's region, then the search shrinks the best-so-far circle from the root to `(2,3)` and skips every far side whose split line lies outside the circle (hatched). **Sorted inserts: a chain** builds a tree of height 6 that the explicit-stack search still handles.

The languages differ in how k is fixed. Python and Go take any dimensionality at runtime (all points must agree; a wrong-sized point or query raises `ValueError` in Python and panics in Go). C++ fixes it at compile time with a `size_t K` template parameter on `KDTree`. `nearest` returns `None` (Python), `nil` (Go) or an empty `std::optional` (C++) on an empty tree. Python's `nearest` and `range_search` use an explicit stack, so a degenerate tree does not hit the recursion limit; C++ and Go recurse.

### Nearest neighbour

Descend toward the query's side of every split first, remember the best point so far, and on the way back decide whether the *other* side can still hide something closer. It can only if the query is closer to the splitting line than to the best point: `diff^2 < best_distance` (squared distances, so no square root).

Nearest to `(1, 3)`:

<Steps>
  <Step title="Go down the near side">
    Root `(7,2)`: distance<sup>2</sup> 37. 1 < 7, so go left. `(5,4)`: 17. The query's y is 3 < 4, so go left again to `(2,3)`: distance<sup>2</sup> 1, the new best.
  </Step>
  <Step title="Check the far side of (5,4)">
    The split line y = 4 is at squared distance (3 - 4)<sup>2</sup> = 1 from the query, which is not smaller than the best, 1. Skip `(4,7)`.
  </Step>
  <Step title="Check the far side of the root">
    The line x = 7 is at squared distance 36, much more than 1. The whole right subtree `(9,6)`, `(8,1)` is skipped.
  </Step>
</Steps>

### Range search

For a box `[lo, hi]`, report a node's point if it lies inside, descend left only if `lo[axis] <= point[axis]` and right only if `hi[axis] >= point[axis]`. Searching the box `(3,3)` to `(8,7)` on the tree above reports `(5,4)` and `(4,7)`: the root `(7,2)` has y = 2 < 3 so is outside the box but both sides are searched; `(2,3)` and `(8,1)` and `(9,6)` are visited and rejected.

### Insert

Inserting walks down like a BST, using the axis of each level, and attaches the new point as a leaf. There is no rebalancing, so inserting points in sorted order produces a chain of height n. Build from the whole list when you can, and rebuild periodically when you cannot.

## Implementation

The three versions share the same structure: a node with a point, an axis and two children; a median-split build; an iterative insert (Python and Go); a nearest search with plane pruning; and a pruned range search. Tests cross-check nearest and range queries against brute force on random 2D and 3D data, with ties and duplicates.

The **curse of dimensionality**: with many dimensions the plane test rarely prunes, so queries approach a linear scan. As a rule of thumb, K-D trees are for roughly 2 to 10 dimensions.

## Applications

- **Spatial search:** nearest store or point of interest to a location.
- **k-NN classification and graphics:** neighbour lookups on low-dimensional features, collision queries, photon mapping.
- **Computational geometry:** closest points, range counting on point sets.
- **Practice:** LeetCode 973 (K Closest Points to Origin) can be solved with a K-D tree, though a heap or quickselect is the usual answer.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Skipping the far-side test.** Searching only the near side is a heuristic, not an exact nearest-neighbour search.
- **Comparing the point distance with the plane distance in different units.** Compare squared against squared: `diff^2 < best_squared`.
- **Off-by-one in the axis.** The axis at depth d is `d mod k`; shifting it silently breaks the pruning.
- **Building by sorted inserts.** The tree becomes a chain; build from the full list instead.
- **Mixed dimensionality.** All points and queries must have the same k.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does nearest-neighbour search need to look at the far side?">
    The closest point may lie across the splitting line if the query is near the line. The test `diff^2 < best` is exactly "could a point on the other side be closer than the best so far".
  </FaqItem>
  <FaqItem question="Why is range search O(sqrt n + k) and not O(log n + k)?">
    A box can cross many splitting lines. In 2D a balanced tree has about sqrt(n) regions that touch the boundary of a query box, and each must be explored even if it holds no result.
  </FaqItem>
  <FaqItem question="Can I delete a point?">
    This repository does not implement it. Deleting a node requires replacing it by the minimum along its axis from a subtree, which is trickier than in a BST because the axis changes by level. Rebuild the tree if deletes are rare.
  </FaqItem>
  <FaqItem question="Why does a K-D tree get worse in high dimensions?">
    Almost every point is nearly as far away as the nearest, so the plane test rarely rules out a subtree, and the search visits most of the tree.
  </FaqItem>
</Faq>
