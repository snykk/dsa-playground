## What it is

A stack lets you add (`push`) and remove (`pop`) items at one end only, the **top**. The item pushed last is the first one popped, which is the last-in, first-out (LIFO) rule. Think of a pile of plates.

An array fits a stack well. The bottom of the stack is index 0 and the top is the last used index, so push and pop touch only the end of the array and never move other items.

The word *dynamic* means the array is not a fixed size. When it fills up, it is replaced by a bigger one, so a push never fails for lack of room.

<Callout title="The invariant">
Only the end of the array is ever read or changed, and the end is always the most recently pushed item. That is what makes the order LIFO and every operation cheap.
</Callout>

The Go methods are `Push`, `Pop`, `Peek`, `IsEmpty` and `Size`. Python and C++ use `is_empty()`. Popping or peeking an empty stack fails in a language-specific way:

- Python raises `IndexError`.
- C++ throws `std::out_of_range`.
- Go panics. Its `Pop` and `Peek` return a plain `int`, so callers should check `IsEmpty()` first.

## How the array grows

The implementations in this repository do not manage capacity themselves. They push with the built-in growable array: `list.append` in Python, `vector::push_back` in C++ and `append` in Go. These containers keep a **capacity** at least as large as the **size**. When a push finds the array full, they allocate a larger block, copy every item and carry on.

The textbook scheme doubles the capacity. The picture shows it for a stack that starts with capacity 1. It is the model behind the amortized bound, and the exact growth factor of a real container is an implementation detail.

### Why push is O(1) amortized

A single push that triggers a resize costs O(n), but resizes become rarer as the array grows. With doubling, the copies over n pushes are 1 + 2 + 4 + ... up to at most n, a geometric series below 2n. Adding the n plain writes gives under 3n operations in total, so under 3 per push.

<Equation label="Total work for n pushes" expr="n + (1 + 2 + 4 + ... + n/2) < n + n" result="< 3n, so O(1) amortized per push" />

Growing by a fixed amount (+10 slots, say) does not work: the copies add up to about n<sup>2</sup>/20, so push would be O(n) amortized. The growth must be by a constant factor.

None of the three implementations shrinks the array on pop. After many pushes and pops the capacity can stay larger than the size.

## Applications

- **Undo and redo:** each action is pushed, and undo pops it.
- **Expression evaluation and parenthesis matching:** push openers, pop on a closer.
- **Depth-first search** with an explicit stack instead of recursion.
- **The call stack** of a program follows the same push and pop discipline.
- **Monotonic stack problems** such as next greater element.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Popping or peeking an empty stack.** Check `is_empty()` first. Go panics, Python raises `IndexError` and C++ throws `std::out_of_range`.
- **Growing by a constant amount.** That makes push O(n) amortized. Grow by a factor.
- **Holding on to a pointer into the array across a push.** A resize moves the items, so old pointers or references become invalid (a C++ `vector` and a Go slice both behave this way).
- **Assuming the stack is bounded.** It is not: an endless loop of pushes exhausts memory.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Does this implementation really double its capacity?">
    The repository relies on the built-in array and does not track capacity. Each container grows by a constant factor, which is what the amortized argument needs, but the exact factor is up to the language runtime.
  </FaqItem>
  <FaqItem question="Why is push amortized O(1) and not O(1)?">
    One push can trigger a full copy and cost O(n). Averaged over a sequence of n pushes, the copies add up to less than 2n, so the average per push is constant.
  </FaqItem>
  <FaqItem question="When should I prefer a linked-list stack?">
    When every push must be O(1) in the worst case, or when you cannot afford the temporary memory spike of a resize. Otherwise the array stack is faster in practice.
  </FaqItem>
  <FaqItem question="How is this different from the static size stack?">
    The static stack has a fixed capacity and rejects a push when full. The dynamic stack replaces its array with a bigger one instead.
  </FaqItem>
</Faq>
