## What problem it solves

Many DPs have the form

<Equation label="Linear-in-i transition" expr="dp[i] = min over j < i of ( m_j * x_i + b_j )" result="one line y = m_j * x + b_j per earlier state j" />

Each earlier state `j` contributes a **line** whose slope and intercept depend on `j`, and the query point `x_i` depends on `i`. Scanning all `j` costs O(n) per state and O(n<sup>2</sup>) overall. Only the lines on the **lower envelope**, the pointwise minimum of all lines, can ever be the answer. The envelope is a convex piecewise-linear function, so it can be stored compactly.

## How it works: the monotonic version

Two conditions make a simple deque enough: lines arrive with **non-increasing slopes**, and queries come with **non-decreasing x**. Then the line that is best moves from the steep lines to the flat ones as `x` grows.

<Steps>
  <Step title="Keep a deque of useful lines">
    The deque holds the envelope from left to right, with strictly decreasing slopes.
  </Step>
  <Step title="Insert: pop from the back">
    Before adding line `l3`, look at the last two lines `l1`, `l2`. If `l2` is never strictly best once `l3` exists, remove it. Repeat, then push `l3`. A new line with the same slope as the last keeps only the lower intercept.
  </Step>
  <Step title="Query: pop from the front">
    While the first line is no better than the second at `x`, remove it. Since later queries are at least as large, a line that lost once never wins again. Answer with the first line.
  </Step>
</Steps>

<Callout title="Why the back test uses cross-multiplication">
With slopes `m1 > m2 > m3`, line `l2` is redundant when `l3` overtakes `l1` no later than `l2` does: the intersection of `l1` and `l3` is at or before that of `l1` and `l2`. Dividing would introduce rounding, so multiply both sides by the (positive) slope differences instead: `(b3 - b1) * (m1 - m2) <= (b2 - b1) * (m1 - m3)`. This is exactly the predicate in the code. It needs strictly decreasing slopes, which is why equal slopes are handled before the test.
</Callout>

## Li Chao tree: any order

When slopes or queries are not sorted, use a segment tree over the range of `x`. Each node stores **one line**: the one that is best at the node's midpoint among the lines that reached it.

<Steps>
  <Step title="Insert a line into a node">
    Compare the new line and the stored one at the midpoint of the node's range. Keep the better one in the node.
  </Step>
  <Step title="Send the loser to one side">
    The loser can only still win where it is better at an end of the range: if it is better at the left end, recurse left; if better at the right end, recurse right; otherwise discard it.
  </Step>
  <Step title="Query at x">
    Walk from the root to the leaf containing `x`, taking the minimum of the stored lines on the path.
  </Step>
</Steps>

For the four lines above over the range 0 to 7, the tree ends like this:

Each insertion follows one root-to-leaf path and each query follows one too, so both cost O(log V) for a range of V integer points. Nodes are created lazily, at most one per inserted line.

## Pseudocode

```text
MonotonicCHT.addLine(m, b):            # slopes non-increasing
    if last line has slope m:
        if last.b <= b: return         # the new line is never better
        pop last
    while size >= 2 and bad(second_last, last, (m, b)):
        pop last
    push (m, b)

bad(l1, l2, l3):                       # slopes strictly decreasing
    return (b3 - b1) * (m1 - m2) <= (b2 - b1) * (m1 - m3)

MonotonicCHT.query(x):                 # x non-decreasing
    while size >= 2 and value(first, x) >= value(second, x):
        pop front
    return value(first, x)

LiChao.insert(node, lo, hi, line):
    if node is empty: store line; return
    mid = (lo + hi) / 2
    if line(mid) < node.line(mid): swap(line, node.line)
    if lo == hi: return
    if line(lo) < node.line(lo):  insert(left child, lo, mid, line)
    else if line(hi) < node.line(hi): insert(right child, mid + 1, hi, line)
```

## Implementation

All three languages have `MonotonicCHT` and `LiChaoTree` for the **minimum**. The monotonic version uses a deque in Python and C++ and a slice in Go. The C++ cross-multiplication uses `__int128` and the Go version uses `big.Int`, so the back test does not overflow; the line values `m * x + b` themselves must still fit in 64 bits. Querying an empty `MonotonicCHT` raises `ValueError` in Python and is a precondition violation in C++ (undefined behaviour) and Go (a panic); an empty `LiChaoTree` returns `inf`, `LLONG_MAX` or `math.MaxInt64`.

In the monotonic version every line is pushed once and popped at most once, so a sequence of n operations costs O(n) in total. This needs O(1) pops at both ends: the Python version uses `collections.deque` for that, because `list.pop(0)` would make a query sweep quadratic. Space is O(n) for the lines, and O(n) nodes for the Li Chao tree.

## Applications

- DP optimizations in competitive programming, such as splitting an array into groups with a setup cost per group.
- Cost minimization where the cost of a segment is quadratic: expanding `(x_i - x_j)^2` gives a line in `x_i` for each `j`.
- Any problem that repeatedly asks for the minimum of many linear functions at a point.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Equal slopes.** Three lines with the same slope make the cross-multiplied test see 0 on both sides, and an unprotected version drops the line with the lowest intercept. Keep only the lowest intercept per slope. This repository did not do so before this fix: `(2,5), (2,1), (2,3)` queried at 0 returned 3 instead of 1.
- **Wrong order.** Slopes must be non-increasing and queries non-decreasing for the minimum. Violating the order gives wrong answers with no error.
- **Min versus max.** The predicate flips for the upper envelope. Write the maximum version separately.
- **Floating point.** Comparing intersection points with division loses exactness; cross-multiply.
- **Overflow.** Products of coordinates need 128-bit integers in C++ or `big.Int` in Go, and the query value must fit in 64 bits.
- **Empty queries.** Query an empty `MonotonicCHT` and C++ has undefined behaviour while Go panics; check first.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="How do I know my DP can use CHT?">
    Expand the cost. If `dp[i] = min over j of (dp[j] + f(j, i))` and `f(j, i)` splits into a part that depends only on `j` plus `m_j` times a part that depends only on `i`, then each `j` is a line evaluated at an `i`-dependent point.
  </FaqItem>
  <FaqItem question="What if the slopes are not sorted?">
    Use the Li Chao tree, or keep the hull in an ordered container with binary search. The deque version cannot handle unsorted slopes.
  </FaqItem>
  <FaqItem question="Is the Li Chao tree always slower?">
    It costs a logarithmic factor, but it is simpler to reason about and has no ordering requirements, so it is often the safer choice when the limits allow.
  </FaqItem>
  <FaqItem question="Why does the code pop the front when values are equal?">
    When two lines tie at `x` and queries never decrease, the one with the larger slope can only get worse afterwards, so the front line is no longer needed.
  </FaqItem>
</Faq>
