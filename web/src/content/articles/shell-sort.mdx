## How Shell Sort works

Insertion Sort is slow on random input because every shift moves an element one place: a small value near the end needs about `n` shifts to reach the front. Shell Sort first compares elements that are far apart. With a gap of `h`, one shift moves an element `h` places, so a few long jumps bring it close to where it belongs, and the later passes with smaller gaps only fix short distances.

<Steps>
  <Step title="Choose the gaps">
    Take the terms of a gap sequence that are below `n`, largest first. The default here is Ciura's: for 12 values, the gaps 10, 4 and 1.
  </Step>
  <Step title="Insertion-sort with a stride">
    For a gap `h`, the indices with the same remainder modulo `h` form a group: `arr[r], arr[r + h], arr[r + 2h], ...`. One pass inserts every element among the earlier members of its own group, exactly as Insertion Sort does, but stepping `h` places at a time.
  </Step>
  <Step title="Shrink the gap">
    After the pass the array is **h-sorted**: `arr[i] <= arr[i + h]` for every `i`. Move on to the next, smaller gap.
  </Step>
  <Step title="Finish with gap 1">
    The last gap is always 1. That pass is plain Insertion Sort, and it leaves the array sorted, however the earlier passes went.
  </Step>
</Steps>

<Callout title="Why the passes add up">
Any sequence that ends with 1 sorts correctly, because the last pass is Insertion Sort. The earlier passes are there for speed, and they help because a later pass never undoes an earlier one: an h-sorted array stays h-sorted after a pass with a smaller gap. The tests in all three languages check that after every pass, for every earlier gap.
</Callout>

## Pseudocode

```text
shellSort(arr, sequence):
    for gap in gaps(length(arr), sequence):      # largest first, the last is 1
        hSort(arr, gap)
    return arr

hSort(arr, gap):
    for i = gap to length(arr) - 1:              # arr[i] is in group i mod gap
        key = arr[i]
        j = i
        while j >= gap and arr[j - gap] > key:
            arr[j] = arr[j - gap]                # shift right by gap
            j = j - gap
        arr[j] = key

ciuraGaps(n):                                    # the default
    take 1, 4, 10, 23, 57, 132, 301, 701 while below n
    h = 701
    while the next gap 2h + floor(h / 4) is below n:
        h = 2h + floor(h / 4)                    # floor(2.25 h), in integers
        take h
    return the gaps, largest first
```

The comparison `arr[j - gap] > key` is strict, so an equal element stops the shifting, as in Insertion Sort. That keeps the gap-1 pass stable on its own, but the earlier passes still reorder equal keys.

## Complexity analysis

The running time depends on the gaps. Every sequence here has O(log n) terms below `n` (19, 13 and 16 of them for Shell's, Knuth's and Ciura's at `n = 10^6`), and a pass makes at least `n - h` comparisons.

The extra space is the key, two indices and the list of gaps. Nothing is copied and nothing recurses.

**Why Shell's gaps are quadratic.** Take `n` a power of 2 and place `1, 2, ..., n/2` at the even indices and the larger half at the odd ones: `1, 9, 2, 10, 3, 11, ...` for `n = 16`. Every gap but the last is even, so no pass before the last ever compares an even index with an odd one, and both halves are already in order. The gap-1 pass is left with all `n(n - 2)/8` inversions. Counted on the Python code, the comparisons are exactly:

What these counts show, and no more:

- All three grow far more slowly than `n^2` here. Doubling `n` multiplied the comparisons by 2.34 to 2.53 with Shell's gaps, 2.23 to 2.43 with Knuth's and 2.14 to 2.30 with Ciura's.
- Ciura's gaps made the fewest comparisons and the fewest shifts at every size: 60% fewer comparisons than Shell's at `n = 256,000`.

- Even so, an O(n log n) sort pulls ahead: Shell Sort with Ciura's gaps made 1.61 times as many comparisons as the repository's Merge Sort at `n = 16,000`, and 1.68 times as many at 256,000.

The three sequences in the code, and three well-known ones that are not implemented here:

**Ciura's extension.** Ciura found the gaps up to 701 by experiment. Past 701 the code multiplies by 2.25 and rounds down, computed in integers as `2h + floor(h / 4)` in all three languages: 1577, 3548, 7983, 17961, 40412, 90927, and so on. The rounding matters: rounding to the nearest gives 17962 instead of 17961, and rounding up gives 1578 instead of 1577.

**Why Ciura's is the default.** It made the fewest comparisons and shifts of the three on every random input measured above, and it is the best sequence known in practice. Its weakness is theory: nobody has proved a bound for it, so when a guarantee matters, Knuth's gaps (or Heap Sort) are the safer choice.

**Knuth's starting gap.** The usual statement of Knuth's sequence has no gap above about `n/3`. The code uses every term below `n` for all three sequences, which adds at most one pass with a gap above `n/3`, and such a pass makes at most 2 comparisons per element.

## Applications

- **Small and medium arrays without recursion.** Where a stack is small or recursion is unwelcome, a short in-place sort helps, and sorted or reversed input does not hurt it: at `n = 100,000`, Ciura's gaps make 1,236,363 comparisons on sorted input and 1,729,428 on reversed input, against 2,552,922 on random input (the average of 5 permutations).
- **Teaching gap sequences and h-sorting.** Changing only the gap list moves the cost from quadratic to near `n log n`, which the counts above show.
- **Sorting interleaved groups.** The idea of one pass, sorting every `k`-th element on its own, is what problems like sorting the even and odd indices independently, or sorting with swaps `k` apart, ask for.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **A sequence that does not end with 1.** The array is then only h-sorted for the last gap, not sorted. Halving `n` and stopping at 2 is the usual way to get this wrong.
- **Powers of 2 as gaps.** With Shell's gaps on `n` a power of 2, even and odd positions never meet until the last pass, which then costs Theta(n^2).
- **Unsigned indices in C++.** Test `j >= gap` before reading `arr[j - gap]`: with `size_t`, `j - gap` wraps around instead of going negative.
- **Expecting stability.** `[2a, 2b, 2c, 2d, 1e]` becomes `[1e, 2b, 2c, 2d, 2a]` with Ciura's or Knuth's gaps: the gap-4 pass swaps `2a` with `1e` and carries it past its three twins. Shell's gaps give `[1e, 2b, 2a, 2d, 2c]`.
- **Using `>=` in the inner loop.** Equal keys then shift past each other for nothing: on 500 equal values, Ciura's gaps make 176,042 comparisons with `>=` and 2,972 with `>`.
- **Gaps in floating point.** `round(2.25 h)` and `floor(2.25 h)` part ways at 17962 and 17961. Compute `2h + floor(h / 4)` in integers.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does Shell Sort sort correctly whatever the gaps are?">
    Because the last gap is 1, and a pass with gap 1 is plain Insertion Sort, which sorts any array. The earlier passes only change how much work that last pass has left.
  </FaqItem>
  <FaqItem question="Why is it faster than Insertion Sort?">
    Insertion Sort removes one inversion per shift. A shift with gap `h` moves an element `h` places and can remove many inversions at once. On the worked example, Insertion Sort needs 40 shifts and Shell Sort 12.
  </FaqItem>
  <FaqItem question="Why is Shell Sort not stable?">
    A pass with a large gap swaps elements that are far apart, and an equal key in between does not stop it. In `[2a, 2b, 2c, 2d, 1e]` the gap-4 pass swaps `2a` and `1e`, so `2a` ends up behind its three twins.
  </FaqItem>
  <FaqItem question="Which gap sequence should I use?">
    Ciura's, the default here: it made the fewest comparisons on every random input counted above. If you need a proven worst case, Knuth's gaps give O(n^(3/2)). Avoid Shell's own halving gaps: they are quadratic when `n` is a power of 2 and the input is unlucky.
  </FaqItem>
  <FaqItem question="Is Shell Sort O(n log n)?">
    Not with these sequences. Its best case, sorted input, is O(n log n). On random input, Ciura's gaps came close to `n log n` in the counts above, but the ratio was still rising, and no bound is proven for them.
  </FaqItem>
</Faq>
