## How Quick Sort works

Quick Sort is a divide-and-conquer algorithm, but unlike Merge Sort it does all of its work **before** it recurses. One pass splits the range around a pivot. After that pass the two sides are independent: no element ever crosses from one side to the other again.

<Steps>
  <Step title="Pick a pivot">
    Any element can serve as the pivot. The implementations in this repository take the last element of the range, `arr[high]`.
  </Step>
  <Step title="Partition around it">
    Rearrange the range so that every element `<=` the pivot comes first, then the pivot, then every element `>` the pivot. The pivot now sits exactly where it belongs in the sorted output.
  </Step>
  <Step title="Sort both sides">
    Apply the same procedure to the part left of the pivot and to the part right of it. A range with zero or one element is already sorted, which ends the recursion.
  </Step>
</Steps>

<Callout title="Why the pivot never moves again">
After partitioning, everything to the left of the pivot is `<=` it and everything to the right is `>` it. No later step can change that, so every partition settles at least one element for good and the algorithm always makes progress.
</Callout>

## The Lomuto partition, step by step

The partition is the heart of the algorithm. The Lomuto scheme used here keeps a boundary index `i`: everything in `arr[low..i]` is known to be `<=` the pivot. A second index `j` scans the range once, from left to right:

- if `arr[j] <= pivot`, the left part grows by one (`i = i + 1`) and `arr[j]` is swapped into it;
- otherwise `arr[j]` stays where it is, because it already belongs to the right part.

When the scan ends, one last swap puts the pivot between the two parts. Here is the partition of `[10, 80, 30, 90, 40, 50, 70]` around the pivot `70`:

The scan touches each element once, so one partition of `n` elements costs <BigO of="n" /> time and no extra memory.

## Pseudocode

```text
quickSort(arr, low, high):
    while low < high:
        p = partition(arr, low, high)
        # recurse into the smaller side, loop on the larger one
        if p - low < high - p:
            quickSort(arr, low, p - 1)
            low = p + 1
        else:
            quickSort(arr, p + 1, high)
            high = p - 1

partition(arr, low, high):          # Lomuto, last element as pivot
    pivot = arr[high]
    i = low - 1
    for j = low to high - 1:
        if arr[j] <= pivot:
            i = i + 1
            swap(arr[i], arr[j])
    swap(arr[i + 1], arr[high])
    return i + 1
```

The `while` loop is the textbook "recurse on both sides", rewritten so that only the smaller side gets a new stack frame. It sorts in exactly the same way, but the recursion depth can never exceed log<sub>2</sub>(n).

## Complexity analysis

The ranges on one level of the recursion do not overlap, so partitioning a whole level costs <BigO of="n" />. The total time is therefore <BigO of="n" /> times the number of levels, and the number of levels depends only on how evenly the pivots split their ranges.

The two extremes as recurrences:

<Equation label="Balanced split" expr="T(n) = 2 T(n/2) + O(n)" result="O(n log n)" />
<Equation label="Lopsided split" expr="T(n) = T(n - 1) + O(n)" result="O(n^2)" />

<Callout title="Space is O(log n) only if you recurse into the smaller side">
Quick Sort needs no buffer, only the recursion stack. Recursing into the smaller part and looping on the larger one, as the Python version does, keeps the depth at most log<sub>2</sub>(n). The plain version with two recursive calls (the C++ and Go versions here) nests up to n calls on sorted input, so its worst-case stack is <BigO of="n" />. In Python that is a `RecursionError` at around 1,000 elements.
</Callout>

## Lomuto vs Hoare partition

Hoare's original scheme from 1961 moves two indices towards each other and swaps the pairs that are on the wrong side. It is harder to get right, but it does less work.

## Applications

- **Standard libraries.** C++ `std::sort` is usually introsort, Java sorts arrays of primitives with Dual-Pivot Quicksort, and Go's `slices.Sort` uses pattern-defeating quicksort (pdqsort).
- **Selection.** Quickselect reuses `partition` to find the median or the k-th smallest element without sorting the whole array.
- **Many duplicate keys.** A three-way partition into `< pivot`, `= pivot` and `> pivot` (the Dutch national flag problem) handles them in a single pass.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Wrong recursion bounds with Hoare.** Hoare returns a split point, not the pivot's index. Recursing on `(low, p - 1)` and `(p + 1, high)` skips an element and can leave the array unsorted.
- **Overflow when picking the middle.** With fixed-width integers, `(low + high) / 2` can overflow on very large arrays. Write `low + (high - low) / 2` instead.
- **Forgetting duplicates.** With `<=` in the Lomuto test, an all-equal array is the worst case. Use a random pivot plus a three-way partition when duplicates are common.
- **Unbounded recursion.** Recurse into the smaller side first, otherwise the stack grows to <BigO of="n" /> on sorted input.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is Quick Sort stable?">
    No. Partitioning swaps elements over long distances, so equal keys can change their order: sorting `[2a, 2b, 1]` with the Lomuto scheme returns `[1, 2b, 2a]`. If you need stability, use Merge Sort, or sort `(key, original index)` pairs.
  </FaqItem>
  <FaqItem question="Why is Quick Sort usually faster than Merge Sort when both are O(n log n)?">
    Big-O hides constant factors. Quick Sort works in place, scans memory sequentially and moves fewer elements. Merge Sort copies every element into a buffer and back on every level.
  </FaqItem>
  <FaqItem question="How do I avoid the O(n^2) worst case?">
    Pick the pivot at random: then no fixed input is bad, and the expected time is <BigO of="n log n" /> on every input. Library sorts go further with introsort, which switches to Heap Sort when the recursion gets too deep, so even the worst case stays <BigO of="n log n" />.
  </FaqItem>
  <FaqItem question="When should I not use Quick Sort?">
    When equal keys must keep their order (use Merge Sort), when you need a hard worst-case bound and have no fallback (Heap Sort or Merge Sort), and for linked lists, where Merge Sort needs no random access.
  </FaqItem>
</Faq>
