## Definition

An RS(n, k) code over GF(2<sup>8</sup>) turns a message of k bytes into a codeword of n &le; 255 bytes. The codeword, read as a polynomial, is a multiple of the generator

<Equation label="Generator" expr="g(x) = (x + a^fcr)(x + a^(fcr+1)) ... (x + a^(fcr+n-k-1))" result="degree n - k" />

where `a` is a primitive element of the field and `fcr` is the first consecutive root. Every codeword vanishes at the n-k roots of `g(x)`. Any two distinct codewords differ in at least n-k+1 positions, the largest distance possible for these parameters (an MDS code). That distance gives the budget:

<Equation label="Correction budget" expr="e + 2v <= n - k" result="e erasures, v unknown errors" />

An unknown error has two unknowns (where, and by how much); an erasure has one (by how much), so it costs half as much.

## Intuition

A polynomial of degree k-1 is determined by any k of its points. Send more than k evaluations and the receiver can rebuild the polynomial from whichever k it trusts. The systematic form used here does it differently but equivalently: the message sits unchanged in the codeword and the parity bytes are chosen so that the whole word is divisible by `g(x)`.

<Callout title="Layout in this repository">
Polynomials are stored lowest degree first, so a codeword is `[parity_0 ... parity_(n-k-1) | msg_0 ... msg_(k-1)]`: the message is the last k bytes. Erasure positions refer to this layout, counted from the start of the codeword.
</Callout>

## How it works

<Steps>
  <Step title="Build g(x) once per code">
    Multiply the n-k factors `(x + a^(fcr+i))`. In characteristic 2, minus is plus.
  </Step>
  <Step title="Encode systematically">
    Shift the message up by n-k positions, divide by `g(x)` and keep the remainder as the parity bytes. The codeword is `[remainder | message]`, divisible by `g(x)`.
  </Step>
  <Step title="Compute the syndromes">
    For the received word `r`, evaluate `s_i = r(a^(fcr+i))` for i from 0 to n-k-1. Because the codeword part vanishes, `s_i` depends only on the error pattern. All zeros and no declared erasures means the word is clean: return the last k bytes.
  </Step>
  <Step title="Find the locator with Berlekamp-Massey">
    Build the erasure locator `Gamma(x)` from the known positions and seed Berlekamp-Massey with it, starting at syndrome `e`. It returns the locator of all bad positions, `Lambda(x) * Gamma(x)`.
  </Step>
  <Step title="Chien search">
    Test every position p from 0 to n-1 and keep those where the locator is zero at `a^(-p)`. A locator of degree d must have exactly d roots inside the codeword; otherwise raise a decode error.
  </Step>
  <Step title="Forney and verification">
    Compute each error value with Forney's formula, XOR it in, then recompute the syndromes. If any is nonzero, raise a decode error instead of returning a wrong message.
  </Step>
</Steps>

<Callout title="Why decoding can be trusted">
Berlekamp-Massey always returns some polynomial, even when the damage exceeds the budget. The decoder therefore checks twice: the Chien search must find exactly deg(locator) roots, and the corrected word must have all-zero syndromes. Otherwise it reports failure.
</Callout>

## Pseudocode

```text
encode(msg):                                   # len(msg) == k
    dividend = [0] * (n-k) + msg               # msg * x^(n-k)
    remainder = dividend mod g
    return remainder (padded to n-k) + msg

decode(received, erasures):
    s = [received(a^(fcr+i)) for i in 0..n-k-1]
    if all(s == 0) and no erasures: return received[-k:]
    gamma = product over erased p of (1 + a^p * x)
    phi = berlekampMassey(s, e, gamma)         # from syndrome e on
    positions = [p for p in 0..n-1 if phi(a^-p) == 0]
    if len(positions) != degree(phi): fail
    for p in positions:
        r[p] ^= a^(p*(1-fcr)) * omega(a^-p) / phi'(a^-p)
    if any syndrome of r != 0: fail
    return r[-k:]
```

Here `omega = (s * phi) mod x^(n-k)`, and `phi'` is the formal derivative, which keeps only the odd-degree terms in characteristic 2.

## Implementation

All three versions support errors plus erasures and a configurable `fcr`, and are checked against the same RS(7, 5) fixture. They differ in structure. Python and C++ reuse the Galois Field topic (a `sys.path` shim and a relative `#include`); Go carries its own minimal GF(2<sup>8</sup>). Python runs Berlekamp-Massey in the swap-and-scale form, C++ and Go in the classical length-tracking form; all three return the same locator.

## The fcr parameter

`fcr` picks which consecutive powers of `a` are the roots of `g(x)`. The correction power is the same for every choice, but the codes are different: a codeword for one `fcr` is generally not a codeword for another. It must match in two places, the syndromes (`a^(fcr+i)`) and Forney's factor `X^(1-fcr)`, which is `X` for `fcr = 0` and 1 for `fcr = 1`. A clean `fcr = 1` RS(15, 11) word given to an `fcr = 0` decoder shows the syndromes `[190, 0, 0, 0]` and raises `DecodeError`.

<Callout title="Not bit-compatible with real standards">
This code fixes the field to `0x11B`. QR codes use `0x11D` with `a = 2` and `fcr = 0`, and CCSDS uses `0x187` with a dual-basis mapping, so these implementations teach the algebra but do not produce those formats' bytes.
</Callout>

## Applications

- **Storage and optical media:** two-layer Reed-Solomon codes protect CDs and DVDs against scratches.
- **QR codes:** the error-correction levels are Reed-Solomon parity.
- **RAID-6:** two parity blocks rebuild any two lost disks, the pure-erasure case.
- **Deep-space links:** the RS(255, 223) code with a 16-byte correction budget is used in space communication standards.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Using `a = 2` with `0x11B`.** Its order is 51, not 255, so the code silently breaks for longer words. Use 3, or switch the field to `0x11D`.
- **Mismatched parameters.** Field polynomial, `a` and `fcr` must agree between encoder and decoder.
- **Erasure positions in the wrong layout.** Positions count from the parity end of this repository's layout, not from the message.
- **Declaring too many erasures.** More than n-k erasures is rejected, and each erasure spends one parity byte even if the byte was actually fine.
- **Trusting Berlekamp-Massey blindly.** Check the root count and the final syndromes.
- **Forgetting Forney's `X^(1-fcr)` factor.** It gives wrong values that pass small tests.
- **Confusing bytes with bits.** RS(255, 223) corrects 16 bytes; 17 bit errors in 17 different bytes defeat it.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why n - k parity bytes for only (n-k)/2 errors?">
    Locating an error needs one equation and finding its value needs another. With known positions only the value is missing, so n-k parity bytes repair n-k erasures.
  </FaqItem>
  <FaqItem question="What happens if there are too many errors?">
    The decoder raises `DecodeError` (Python, C++) or returns `ErrDecode` (Go) when the Chien search or the final syndrome check fails. Malformed input, such as a wrong length, is a separate error. A pattern of more than t errors can still, rarely, look like a different valid codeword; the code cannot detect that.
  </FaqItem>
  <FaqItem question="Why is the message at the end of the codeword?">
    Polynomials are stored lowest degree first and the message is shifted up by n-k positions, so it occupies the high-degree end. Libraries that print high degree first show the message first.
  </FaqItem>
  <FaqItem question="Why does the syndrome ignore the message?">
    Each codeword is zero at the roots of g(x), so the evaluation of received = codeword + error equals the evaluation of the error alone.
  </FaqItem>
</Faq>
