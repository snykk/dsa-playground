## What a hash table is

A hash table is an array of **buckets**. To store a key, a hash function turns it into an integer and the table reduces it to a bucket index, `index = hash(key) mod capacity`. To find the key again, repeat the computation and look only in that bucket. No scanning of the whole table is needed.

Different keys can land in the same bucket (a *collision*). This table uses **separate chaining**: each bucket holds a small list of the pairs that hashed to it. Open addressing is covered in the Collision Handling topic.

<Callout title="Two ideas make it fast">
A good hash function spreads keys evenly, so chains stay short. And the table **resizes**: when the number of pairs divided by the number of buckets (the *load factor*) passes 0.75, the capacity doubles and every pair is placed again, which keeps the average chain length below 1.
</Callout>

### Get and remove

`get(13)` hashes 13 to bucket 5, compares with 5 (no) and then 13 (yes), and returns it: two key comparisons. `remove(9)` finds 9 in bucket 1 and unlinks it. A miss ends when the bucket's list ends.

## Why it is O(1) on average

With a decent hash, each key is equally likely to land in any bucket. If `n` pairs sit in `c` buckets, an average chain has `n / c` pairs, the load factor. Resizing keeps it at most 0.75, so a lookup compares a constant number of keys on average.

Resizing costs O(n), but it only happens when the size doubles: the cost of all resizes while inserting `n` keys is `n/2 + n/4 + ... < n`, so each insert pays O(1) amortized.

<Equation label="Amortized insert cost" expr="n + n/2 + n/4 + ... = 2n" result="O(1) per put" />

Space is O(n + capacity): one entry per pair plus the bucket array.

<Callout tone="warning" title="A bad hash function ruins O(1)">
The string hash used here is `h = h * 31 + c`, reduced at each step modulo the capacity. Because 31 is congruent to -1 modulo 32, strings such as `abcd` and `cdab` collide at every capacity up to 64. Over all 4096 four-letter words on the letters a to h, capacity 32 uses only 29 of its 32 buckets and its longest chain is 344 (the ideal is 128). Capacity 128 has a longest chain of 88 against an ideal of 32. Integer keys hashed as `key mod capacity` are just as bad when keys share a factor with the capacity (for example all multiples of 16).
</Callout>

## Applications

- Dictionaries, maps and sets in nearly every language; counting frequencies; caches and memoisation.
- Two-sum style lookups: store seen values, then ask for the complement in O(1).
- Detecting duplicates and grouping items by a key.
- Symbol tables in compilers and interpreters.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Using `get(key) is not None` as a membership test.** A key stored with the value None looks absent. `contains` and `in` now check the keys themselves, so `put('k', None)` followed by `'k' in table` is True.
- **Capacity 0.** `hash mod 0` divides by zero. Python raises `ValueError` and C++ throws `std::invalid_argument`; Go replaces a capacity of 0 or less with 16.
- **Negative remainders.** In Go, `-1 % 8` is `-1`, a bad index. The code folds it into `[0, capacity)`. Go also hashes other key types (int64, float64, bool...) through their printed form; before that they panicked.
- **Keeping a pointer across a resize in C++.** `get` returns `V*`. The resize splices the list nodes into the new buckets instead of copying, so the pointer stays valid, as with `std::unordered_map`. It dies when the key is removed or the table is destroyed.
- **Mutable keys.** Changing a key after insertion changes its hash and loses the entry.
- **A weak hash.** See the callout above: the same few collisions repeat at every size.
</Callout>

## Implementation

All three tables use separate chaining and double their capacity when the load factor passes 0.75. They compare keys with the language equality (`==`). Python hashes strings with `h*31 + c`, C++ uses `std::hash` (with an explicit 31-based hash only for `<std::string, std::string>` tables), and Go hashes ints directly and everything else through a string form.

## Frequently asked questions

<Faq>
  <FaqItem question="Why double the capacity instead of adding a fixed amount?">
    Doubling makes the total resize work geometric (n/2 + n/4 + ...) so each insert is O(1) amortized. Growing by a constant means resizing every few inserts and costs O(n) per insert on average.
  </FaqItem>
  <FaqItem question="What is the load factor?">
    The number of stored pairs divided by the number of buckets. With chaining it is also the average chain length. This table resizes when it passes 0.75.
  </FaqItem>
  <FaqItem question="Is a hash table the same as a hash map?">
    In practice yes: both mean a key-to-value table built on hashing. Some languages use "hash table" for the structure and "map" for the interface. The Hash Map topic here shows idiomatic helpers on top of it.
  </FaqItem>
  <FaqItem question="Why are iteration orders different between runs or languages?">
    Order follows bucket order, which depends on the hash function and the capacity. A resize reshuffles it. Never rely on it.
  </FaqItem>
</Faq>
