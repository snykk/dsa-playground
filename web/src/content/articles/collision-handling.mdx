## What a collision is

A hash table maps a key to a slot with `slot = hash(key) mod capacity`. There are far more possible keys than slots, so two keys can land on the same slot. By the pigeonhole principle this cannot be avoided, only handled. There are two families:

- **Separate chaining:** each slot holds a small list of all the keys that hash to it.
- **Open addressing:** each slot holds at most one key. A key that finds its home slot taken walks a *probe sequence* to another slot.

<Callout title="The invariant of open addressing">
A key is always stored on its own probe sequence, and every slot before it on that sequence is occupied (or was, see tombstones below). A lookup can therefore stop at the first truly empty slot and conclude "not present".
</Callout>

### Linear probing: the probe sequence

Linear probing tries `home, home+1, home+2, ...` modulo the capacity, so keys fill the table in runs. Look up 19 (home slot 3) in `[., ., ., 3, 11, 19, 6, 14]`: slot 3 holds 3, slot 4 holds 11, slot 5 holds 19, found after three probes. A missing key with home 3 would walk slots 3 to 7 and then 0, where it meets an empty slot and stops.

Long runs are called **primary clusters**. A key whose home falls inside a cluster joins the end of it, so clusters grow and merge. That is why probe counts explode as the table fills.

### Delete: why tombstones

Suppose 11 is removed by simply emptying slot 4. Now `get(19)` starts at slot 3, walks to slot 4, finds it empty, and wrongly answers "not present". Instead a removed slot gets a **tombstone** that lookups walk past and inserts may reuse:

/>

When inserting, the code must first walk the **whole** probe sequence, remembering the first tombstone, because the key may already live further down. Taking the first free slot without checking would create a duplicate. This was a real bug here: `put(17)` after removing an earlier collider added a second copy of 17, double counted `size`, and a later remove brought back the stale value. The code now looks for the key first and reuses the tombstone only if it is absent.

### Quadratic probing and the capacity trap

Quadratic probing breaks up clusters by jumping further each time. Plain `i * i` steps are not safe: modulo 16 the squares are only 0, 1, 4 and 9, so the sixth colliding key finds no free slot even though 12 of 16 slots are empty. This code uses **triangular numbers** `i (i + 1) / 2` (0, 1, 3, 6, 10, ...), which visit every slot when the capacity is a power of two. The default capacity 16 is one, so a table can be filled completely.

Keys that share a home slot still follow the same probe sequence, which is called **secondary clustering**. Double hashing (step size from a second hash) avoids it, but is not implemented here.

The linear probing formulas are the classic expected-probe counts under the usual uniform-hashing assumption. In practice open addressing is kept below a load of about 0.5 to 0.7. Since these tables never resize, they cannot keep the load low: a table with fixed capacity `c` costs O(n / c) per operation for chaining, so it is only fast while `n` stays close to `c`. The Hash Table topic adds resizing and shows why that gives amortized O(1).

Space is O(capacity + n) for chaining (list nodes) and O(capacity) for open addressing.

## Applications

- The core of every hash map and set; the Hash Table topic builds resizing on top of chaining.
- Language runtimes use both families; for example Python dictionaries use open addressing with a perturbed probe sequence (the exact scheme differs from the ones here).
- Symbol tables, caches and deduplication sets.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Emptying a slot on delete in open addressing.** It cuts probe sequences and loses keys. Use a tombstone.
- **Inserting at the first free slot.** The key may exist further along the sequence; check the whole sequence first, or you store duplicates.
- **Unbounded probe loops.** On a full table a lookup of a missing key never meets an empty slot. Stop after `capacity` probes. The C++ and Go code used to spin forever here.
- **Squares on a power-of-two table.** `i * i` covers only a few slots modulo 16. Use triangular steps or a prime capacity.
- **Negative keys.** `k % capacity` is negative in C++ and Go for negative `k`; fold it back into range (Go does now).
- **Believing the load stays low.** Nothing here resizes, so a full table is a real state: put raises (Python, C++) or panics (Go).
</Callout>

## Implementation

Python shares one base class between linear and quadratic probing and differs only in the step function. C++ stores open-addressing slots as optional key-value pairs held by value (`std::optional` of `std::pair`), so the table frees itself and copies deeply (an earlier version leaked every pair). Go keeps pointers to key-value structs and hashes any key type through its printed form.

## Frequently asked questions

<Faq>
  <FaqItem question="Which is better, chaining or open addressing?">
    Neither always. Chaining is simpler and forgiving; open addressing is faster on modern hardware when the table is kept at most about half full. Pick by memory constraints and whether deletes are common.
  </FaqItem>
  <FaqItem question="Why does quadratic probing need a special capacity?">
    The probe offsets must reach every slot, or an insert can fail with free slots left. Triangular offsets reach all slots of a power-of-two table, and plain squares do so for a prime table when it is at most half full.
  </FaqItem>
  <FaqItem question="What happens to tombstones over time?">
    They accumulate and lengthen probes even though they hold nothing. Real tables rebuild (rehash) when too many appear. This code never rebuilds, so a long run of puts and removes can leave a table that reports `size` low but is full of tombstones.
  </FaqItem>
  <FaqItem question="Can I get more than O(1) worst case?">
    Yes, in the worst case every scheme is O(n). Cuckoo hashing gives O(1) worst-case lookups, and chaining with balanced trees in each bucket bounds the chain cost at O(log n).
  </FaqItem>
</Faq>
