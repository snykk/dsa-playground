## What a skip list is

A sorted linked list needs O(n) steps to find a key, because it can only move one node at a time. A skip list keeps the bottom list intact (level 0 holds every key, in order) and adds sparser lists above it. Each key appears on level 0 and, with probability `p` (0.5 here), also on level 1; of those, a fraction `p` also appear on level 2, and so on. A key that reaches level `h` is a tower of height `h + 1`, with one forward pointer per level.

A search starts on the sparsest level, moves right while the next key is still smaller than the target, drops one level when it would overshoot, and repeats down to level 0.

<Callout title="Randomness replaces balancing">
A balanced tree keeps its shape with rotations. A skip list does not keep any shape: it flips a coin for each new key to choose its height. The heights are random but, with overwhelming probability, they are spread like the levels of a balanced tree, so searches are logarithmic. The guarantee is probabilistic: a bad run of coin flips can make the structure slow but cannot make it wrong.
</Callout>

Python and C++ constructors default to `max_level = 16` and `p = 0.5`. Go's `NewSkipList(maxLevel, p)` needs both arguments. C++ calls delete `deleteNode`, Python `delete` and Go `Delete`. The structure behaves as a set: inserting an existing key does nothing.

### Insert: coin flips and the update array

While descending, `insert` stores in `update[i]` the last node it stood on at level `i`. It then draws a height: start at 0 and keep adding one while a coin with probability `p` comes up heads (and the height is below `max_level`). Inserting `15` and drawing height 1:

If the drawn height exceeds the current `level`, the header becomes `update[i]` for the new levels and `level` grows.

### Delete: unlink on every level

`delete` finds the same `update` array, checks that the node after `update[0]` holds the key, and then, level by level from 0 up, sets `update[i].forward[i]` to the node's successor. It stops at the first level where the node does not appear. Finally it lowers `level` while the top level has no nodes. Deleting `6` and then `25` from the list above:

## Implementation

All three versions share this structure. The C++ class owns its nodes through a destructor, so its copy constructor and assignment are deleted: a shallow copy would free the same nodes twice. Each C++ instance has its own random generator. Python uses `random.random()`, and Go uses the global `math/rand`.

## Complexity

<DataTable
  columns={['Quantity', { label: 'Value', kind: 'mono' }, 'Why']}
  rows={[
    ['levels in use', 'about log2(n)', 'level k holds about n * p^k keys; it runs out near k = log(n) / log(1/p)'],
    ['moves per level', '1 / p = 2', 'a node taller than the current level is a coin flip away, so the expected run of same-level moves is geometric'],
    ['search, insert, delete', 'O(log n) expected', 'about (1 / p) * log2(n) moves in total'],
    ['expected pointers per node', '1 / (1 - p) = 2', 'height is geometric: P(height >= k) = p^k'],
    ['space', 'O(n) expected', 'about 2n pointers, plus a header with max_level + 1'],
    ['worst case', 'O(n)', 'all keys tall or all keys short: vanishingly unlikely'],
  ]}
/>

<Equation label="Expected pointers per key (p = 1/2)" expr="1 + p + p^2 + p^3 + ..." result="1 / (1 - p) = 2" />

Because heights are capped at `max_level` (16 by default), the structure stays efficient up to roughly 2<sup>16</sup> = 65,536 keys at `p = 0.5`. Beyond that the top levels fill up and search drifts toward O(n / 2<sup>16</sup>). Choose `max_level` near log<sub>1/p</sub>(n).

## Applications

- **Ordered in-memory maps and sets** where a simple, concurrency-friendly structure is preferred over a balanced tree.
- **Real systems:** Redis sorted sets, the LevelDB memtable and Java's `ConcurrentSkipListMap` are built on skip lists.
- **Range and neighbour queries** on a sorted set (find the next larger key by one search).

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Forgetting to lower `level` after a delete.** Searches stay correct but waste work on empty levels.
- **Using `update` from the wrong level.** Each level needs its own predecessor; reusing one node splices the tower into the wrong lists.
- **Re-seeding the random generator for every list.** Lists created in the same instant then get identical heights, and other users of the global generator are disturbed. The C++ class uses its own generator per instance for this reason.
- **A `max_level` that is too small** for the data. With 16 levels and `p = 0.5`, efficiency fades beyond about 65 thousand keys.
- **Treating the header key as a real key.** The header stores a placeholder `-1` that is never compared; negative keys, including `-1`, work normally.
- **Copying a C++ skip list.** A shallow copy double-frees; the copy operations are deleted.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is a skip list always O(log n)?">
    No. The bound is expected time over the random choices. In the worst case (all towers unlucky) it degrades to O(n), but the probability of anything far from logarithmic shrinks very quickly as n grows.
  </FaqItem>
  <FaqItem question="Why does insert flip coins instead of choosing a height from the data?">
    Random heights make the structure independent of the insertion order. A sorted input, which ruins an unbalanced binary search tree, does not hurt a skip list.
  </FaqItem>
  <FaqItem question="What happens when I insert a key that already exists?">
    Nothing: the code finds the key during the search and returns. The list stores each key at most once.
  </FaqItem>
  <FaqItem question="How do I choose p?">
    `p = 0.5` is the usual default: about 2 pointers per key and about 2 moves per level. A smaller `p` saves memory and levels but takes more moves per level.
  </FaqItem>
</Faq>
