## How KMP works

When the naive search fails after matching `j` characters, it throws that knowledge away and restarts one position to the right. But those `j` matched characters are known: they equal `pattern[0..j-1]`. If a prefix of the pattern is also a suffix of the matched part (a **border**), that prefix is already matched at the next useful alignment, and nothing needs to be compared again.

The **LPS table** (longest proper prefix which is also a suffix) holds exactly that: `lps[i]` is the length of the longest proper prefix of `pattern[0..i]` that is also a suffix of it.

<Steps>
  <Step title="Build the LPS table">
    Scan the pattern with `i` and a running border length `len`. If `pattern[i] == pattern[len]`, the border grows: `len += 1; lps[i] = len`. Otherwise fall back to the next shorter border, `len = lps[len-1]`, without moving `i`; at `len == 0` set `lps[i] = 0` and move on.
  </Step>
  <Step title="Scan the text with i and j">
    `i` indexes the text and `j` the pattern. While `text[i] == pattern[j]`, advance both.
  </Step>
  <Step title="On a mismatch, fall back in the pattern only">
    If `j > 0`, set `j = lps[j-1]` and compare `text[i]` again. If `j == 0`, advance `i`. The text index never decreases.
  </Step>
  <Step title="On a full match, report and keep going">
    When `j == m`, report `i - j` and set `j = lps[j-1]`, so the next match may overlap the last one.
  </Step>
</Steps>

<Callout title="Why falling back is safe">
After matching `j` characters, every border of `pattern[0..j-1]` is a candidate for what is still matched. The longest border is `lps[j-1]`; the next is `lps[lps[j-1]-1]`, and so on. Taking them from longest to shortest never skips an alignment that could match.
</Callout>

The text characters `D` (index 4) and `C` (index 8) are each compared with three pattern positions, so "each text character is examined once" is not literally true. What is true is that `i` never moves left, and at most `2n` distinct `(i, j)` pairs are compared: 22 here, with `n = 18`. The code's `elif` repeats many of these tests, so its raw count of `==` and `!=` tests is at most twice that (39 here).

## Pseudocode

```text
build_lps(pattern):
    lps = [0] * m; length = 0; i = 1
    while i < m:
        if pattern[i] == pattern[length]:
            length += 1; lps[i] = length; i += 1
        elif length != 0:
            length = lps[length - 1]          # fall back, keep i
        else:
            lps[i] = 0; i += 1
    return lps

kmp_search(text, pattern):
    if pattern is empty or text is empty or m > n: return []
    lps = build_lps(pattern)
    i = 0; j = 0
    while i < n:
        if text[i] == pattern[j]: i += 1; j += 1
        if j == m:
            report i - j
            j = lps[j - 1]
        elif i < n and text[i] != pattern[j]:
            if j != 0: j = lps[j - 1]
            else:      i += 1
```

## Implementation

All three languages are the same algorithm. Python exposes `build_lps`, `kmp_search`, `kmp_search_count` and `kmp_search_first`; C++ has `buildLPS`, `kmpSearch`, `kmpSearchCount` and `kmpSearchFirst`; Go has `BuildLPS`, `KMPSearch`, `KMPSearchCount` and `KMPSearchFirst`. An **empty pattern, an empty text, or a pattern longer than the text returns `[]`** here, as in the other three searches of this section. The `First` helpers compute all matches before returning the first. Python indexes code points; C++ and Go index bytes.

## Applications

- **Single-pattern search** in editors, log scanners and streams.
- **Smallest period of a string.** If `p = m - lps[m-1]` is less than `m` and divides `m`, the string is a repetition of its first `p` characters (this solves LeetCode 459).
- **Longest happy prefix** (LeetCode 1392): the longest border is `lps[m-1]`.
- **Building block** for Aho-Corasick, which generalises the table to a trie of patterns.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Moving `i` back.** On a mismatch only `j` falls back. Resetting `i` makes the algorithm quadratic again.
- **Falling back with `lps[j]` instead of `lps[j-1]`.** After `j` matched characters the relevant border is the one of `pattern[0..j-1]`.
- **Advancing `i` when `j > 0`.** A mismatch with `j > 0` must retry the same `text[i]` against the shorter border.
- **Stopping at the first match.** After a full match set `j = lps[j-1]`, which finds overlapping matches.
- **Wrong empty-pattern handling.** Here an empty pattern returns `[]`; check the convention before mixing implementations.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="What is the LPS array?">
    `lps[i]` is the length of the longest proper prefix of `pattern[0..i]` that is also a suffix of it. For `ABABCABC` it is `[0, 0, 1, 2, 0, 1, 2, 0]`. A proper prefix is shorter than the whole string.
  </FaqItem>
  <FaqItem question="Why is the search O(n) when there is a nested fall back?">
    `j` increases by one for every text character that matches and never goes below 0, while each fall back strictly decreases it. So the total number of fall backs cannot exceed the total number of increases, which is at most n.
  </FaqItem>
  <FaqItem question="Is KMP better than Boyer-Moore?">
    It is more predictable: linear time on every input. Boyer-Moore with only the bad-character rule can reach O(n*m), but it often skips most of the text and wins on long patterns and large alphabets.
  </FaqItem>
  <FaqItem question="How is KMP related to the Z-algorithm?">
    Both reuse information about prefixes to avoid re-comparing. The Z-array of the pattern and the LPS table carry the same information in different forms, and either gives a linear-time search.
  </FaqItem>
</Faq>
