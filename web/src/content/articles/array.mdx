## What an array is

An array is a fixed number of slots of equal size, laid out one after another. If the first slot sits at address `base` and each slot takes `w` bytes, slot `i` sits at `base + i * w`. No search is needed: the address is computed, so reading `a[i]` costs the same for `i = 0` as for `i = 10^9`.

<ArrayDiagram
  legend={{ p: 'the slot being read', f: 'the base address (index 0)' }}
  rows={[
    { label: 'int a[5], w = 4 bytes, base = 1000', values: [10, 20, 30, 40, 50], tones: 'f.p..', marks: { 0: '1000', 1: '1004', 2: '1008', 3: '1012', 4: '1016' }, note: '`a[2]` is at 1000 + 2 * 4 = 1008. One multiply, one add, one memory read.' },
  ]}
/>

Because neighbours share cache lines, scanning an array is also the fastest way to walk through data on real hardware.

<Callout title="Why the size is fixed">
The block must be contiguous, and whatever sits after it in memory may already be in use. A plain array therefore cannot grow in place. Growing means allocating a bigger block and copying, which is what a dynamic array automates.
</Callout>

The Python `DynamicArray` in this repository implements `len()`, `a[k]` (no negative indexes), `append` and `pop`. Insert and remove are not implemented; the walk-through below shows what they cost.

### Shrinking

`pop` clears the vacated slot (`None`), so the array does not keep the popped object alive. When the length falls to a quarter of the capacity the array halves its capacity. Popping everything from the nine-element array above:

<ArrayDiagram
  legend={{ l: 'live elements', m: 'unused capacity' }}
  rows={[
    { label: 'n = 5, capacity 16', values: [10, 20, 30, 40, 50, '-', '-', '-'], tones: 'lllllmmm', note: 'shown: the first 8 of 16 slots. After popping 90, 80, 70, 60 the capacity is still 16.' },
    { label: 'n = 4, capacity 8', values: [10, 20, 30, 40, '-', '-', '-', '-'], tones: 'llllmmmm', note: 'pop 50: 4 elements = 16 / 4, so halve to 8.' },
    { label: 'n = 2, capacity 4', values: [10, 20, '-', '-'], tones: 'llmm', note: 'pop 30: 2 elements = 8 / 4, so halve to 4.' },
  ]}
/>

Shrinking at one half would be a trap. A full array of capacity 8 that appends (grows to 16) and pops (falls to 8 elements, half of 16, shrinks to 8) would copy all elements on every operation. Waiting for one quarter leaves a gap, so after any resize at least `capacity / 4` cheap operations must happen before the next one.

### Two dimensions in one block

A 3 by 3 grid is stored as 9 consecutive slots, row after row. Cell `(i, j)` is at flat index `i * cols + j`:

Walking the grid row by row touches consecutive addresses; walking it column by column jumps `cols` slots each time and loses the cache advantage. A list of lists (nested slices, nested vectors) allows rows of different lengths but stores each row in its own block.

**Why append is amortized O(1).** With doubling, the resizes copy 1, 2, 4, ..., n/2 elements, which sums to less than n. Over n appends that is fewer than n extra copies, so the total is under 2n writes and the average per append is a constant. For example, 1000 appends from capacity 1 perform 1023 element copies in resizes (the last resize at append 513 copies 512 elements), about one per append. A single append can still cost O(n), so this is an average over a sequence, not a bound on each call.

<Equation label="Total copy work for n = 2^k appends" expr="1 + 2 + 4 + ... + 2^{k-1}" result="2^k - 1 < n" />

The growth factor only needs to be greater than 1 for the amortized argument to hold. CPython lists grow by about 12.5 percent, C++ libraries typically double, and Go slices roughly double for small sizes and grow more slowly for large ones. The exact factor is an implementation detail.

## Applications

- **Storage for other structures:** stack, queue, binary heap and hash table buckets are arrays underneath.
- **Matrices and images** as flat row-major buffers; **DP tables** and **grids** in algorithm problems.
- **Prefix sums, frequency counts and sieves** that index by value.
- **Binary search** on sorted data, which needs random access.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Off-by-one at the end.** Valid indexes are `0` to `n - 1`. Python `DynamicArray` raises `IndexError` for `a[n]` and does not accept `a[-1]`, unlike a built-in `list`.
- **Keeping references across growth.** After a resize the old block is gone. In C++ a pointer or iterator into a `vector` is invalid after `push_back` may reallocate.
- **Go slice aliasing.** `b := a[:2]` shares the backing array with `a`; `append(b, x)` can overwrite `a[2]`.
- **Shrinking at half full.** It makes alternating append and pop copy the whole array every time. Shrink at a quarter.
- **Forgetting to clear popped slots** in a language with garbage collection: the array keeps the object alive.
- **Inserting in a loop at the front.** n inserts at index 0 cost O(n<sup>2</sup>). Append and reverse, or use a deque.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Is a Python list a linked list?">
    No. A Python `list` is a dynamic array of references. `lst[i]` is O(1), `lst.append` is amortized O(1), and `lst.insert(0, x)` is O(n).
  </FaqItem>
  <FaqItem question="Why is append O(1) if resizing copies everything?">
    Resizes are rare and their cost is spread out. With doubling, the copies of all resizes up to n elements add up to less than n, so the average per append is constant. This is amortized analysis, not a per-call guarantee.
  </FaqItem>
  <FaqItem question="Why do arrays start at index 0?">
    The index is an offset from the base address: `base + i * w`. The first element is zero slots away from the start.
  </FaqItem>
  <FaqItem question="When is a linked list better than an array?">
    When you insert or remove at known positions in the middle very often and never need random access. In practice arrays win for most sizes because of cache locality, so measure before choosing a list.
  </FaqItem>
</Faq>
