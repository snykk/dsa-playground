## What an adjacency matrix is

Number the vertices `0..V-1` and keep a V &times; V table. Row `i`, column `j` describes the edge from `i` to `j`. In an unweighted graph the cell is 1 for an edge and 0 for none. In a weighted graph it holds the weight.

<Callout title="Row = out-edges, column = in-edges">
Reading row `i` lists the neighbors of `i`. Reading column `j` lists the vertices with an edge into `j`. For an undirected graph the two agree, so you only ever need one of them.
</Callout>

## See it in action

Run **Self-loop and zero weight**: `add_edge(0, 1, 0)` stores the weight 0, and the filled cells (where `present` is True) keep it apart from "no edge". `get_neighbors` reads a whole row, and **Out of range: ValueError** shows that the matrix cannot grow past its `n`.

Python also has `get_weight`, `get_degree`, `dfs_recursive`, `is_connected` and `get_matrix`. C++ has `get_weight` and `try_get_weight`, `bfs` and `dfs`. Go has `AddEdge`, `HasEdge`, `GetNeighbors` and `BFS`. The vertex count is fixed at construction. An out-of-range vertex makes Python `add_edge` raise `ValueError`, while C++ and Go ignore it silently.

### Weights and "no edge"

A weighted matrix needs a value for "no edge", and the natural choices collide with real weights. Infinity is a common marker, but zero is a legal weight, and so are negative numbers and very large ones. This implementation keeps a separate presence table next to the weights, so `has_edge` reads the presence table and the weight cell can hold any value, including 0. Unused cells hold infinity and the diagonal 0, the usual convention for shortest-path matrices.

### Neighbors and traversal

`get_neighbors(u)` scans all V cells of row `u`, even when `u` has two neighbors. BFS does that once per visited vertex, which totals O(V<sup>2</sup>) regardless of E. On `[0, 1, 2, 3]` from vertex 0 the BFS scans rows 0, 1, 2 and 3 in turn and returns `[0, 1, 2, 3]`.

    ['BFS / DFS', 'O(V^2)', 'one row scan per vertex'],
  ]}
/>

In the repository's Python version `get_degree` on a **directed** graph returns in-degree plus out-degree, which needs a column scan as well.

The table is the cost: 10<sup>4</sup> vertices already mean 10<sup>8</sup> cells. That is only reasonable when the graph is dense (E close to V<sup>2</sup>) or V is small.

## Applications

- **All-pairs shortest paths:** Floyd-Warshall works directly on a weight matrix.
- **Dense graphs and small graphs:** tournaments, complete graphs, graphs of a few hundred vertices.
- **Fast adjacency tests:** checking whether two vertices are joined inside a tight loop.
- **Bitmask DP over small graphs:** a row stored as an integer mask lets you intersect neighbor sets with one operation.
- **Graph theory by linear algebra:** powers of the matrix count walks of a given length.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Using 0 for "no edge" in a weighted graph.** A zero-weight edge then disappears. Keep a separate presence flag or a different marker, and remember that a negative weight or a huge one must stay valid too.
- **Updating only one cell of an undirected edge.** The matrix must stay symmetric.
- **Assuming a sentinel like `INT_MAX` is safe.** An edge with exactly that weight would vanish. Infinity from floating point or a presence table avoids it.
- **Treating the diagonal as edges.** Distance-matrix convention puts 0 on the diagonal. It means "distance to itself", not a self-loop.
- **Using it for a large sparse graph.** A million-vertex graph needs 10<sup>12</sup> cells.
- **Forgetting that `get_weight` can be ambiguous in C++.** It returns -1.0 for "absent", which is also a legal weight. Use `try_get_weight` when negative weights are possible.
</Callout>

## Implementation

All three versions allocate a V &times; V table of numbers. Python stores 0/1 for unweighted graphs and weights (infinity for absent) for weighted graphs. C++ and Go store `double` values in both cases. Each version also keeps the boolean presence table described above.

## Frequently asked questions

<Faq>
  <FaqItem question="When is an adjacency matrix better than an adjacency list?">
    When the graph is dense, V is small, or edge-existence queries dominate. Then O(1) lookup is worth more than the extra memory. For sparse graphs and traversal-heavy code, a list is better.
  </FaqItem>
  <FaqItem question="Why is the matrix symmetric for undirected graphs?">
    Edge `{u, v}` is the same edge as `{v, u}`, so both cells `(u, v)` and `(v, u)` are set. A directed graph has no such rule: `(u, v)` can be set while `(v, u)` is not.
  </FaqItem>
  <FaqItem question="How do I represent a missing edge in a weighted graph?">
    Use a separate presence table, as this repository does, or a marker no weight can equal, such as floating-point infinity. Do not use 0 unless zero weights are forbidden.
  </FaqItem>
  <FaqItem question="Can an adjacency matrix store parallel edges?">
    Not directly: one cell holds one value. Store a count or a list in each cell, or use an adjacency list.
  </FaqItem>
</Faq>
