## When to use it

A problem is interactive when the statement says:

- "Your program communicates with the judge by reading and writing to standard streams."
- The input is **hidden** and you may only ask a limited number of questions about it.
- The response to one query decides the next query.
- You must print a final answer in a specific format, such as `! x`.

## How it works

<Steps>
  <Step title="Read the protocol exactly">
    Note the query format (`? x`), the answer format (`! x`), what the judge replies, what an invalid reply looks like (often `-1`), and the maximum number of queries.
  </Step>
  <Step title="Count the queries before coding">
    Compute the worst case of your strategy. Binary search over `n` values needs about log<sub>2</sub> n queries. If the limit is smaller than that, you need a different idea.
  </Step>
  <Step title="Write query, flush, read, repeat">
    Each query must reach the judge before you wait for its answer. Flushing is part of the query.
  </Step>
  <Step title="Stop on errors and print the answer once">
    If the judge sends `-1`, exit immediately. Print the final answer in the required format and flush it.
  </Step>
</Steps>

<Callout title="Flushing is part of the protocol">
Standard output is buffered. If you print `? 5` and read the reply without flushing, the judge never receives the query and both programs wait for each other. Most judges report that as an idleness or timeout verdict. Flush after **every** line you write.
</Callout>

## Template

```text
solve():
    n = read()
    while the answer is not known:
        q = choose next query from what we know     # e.g. the midpoint
        print("? " + q)
        flush()
        r = read()
        if r == -1: exit                            # judge says we erred or ran out of queries
        update what we know using r
    print("! " + answer)
    flush()
```

## Worked example: guess a number

The judge holds a secret in `1..10`. `guess_number(10)` asks the midpoint and the judge answers `higher`, `lower` or `correct`. For the secret 7:

The interval has one value left, so the program prints `! 7`. That is 3 queries. The interval shrinks like this:

If the judge ever replies `correct`, the function returns at once without printing `! x`, because in this protocol the judge ends the game itself. If your problem wants an explicit answer line, print it.

Why it takes at most floor(log<sub>2</sub> n) queries: a query on an interval of s values leaves at most floor(s/2) of them, and the loop stops when one value is left. For n = 10 that is 3, and the secret 10 needs all three.

## Implementation

The three languages share the idea but not the helpers:

- **Python** has query and answer helpers (`query`, `query_multi`, `answer`, `answer_multi`) and strategies: `guess_number`, `binary_search_answer`, `explore_graph`, `find_maximum`, `tournament`, `guess_subset`, `binary_subset_search`, plus `check_response` and a `solve` template.
- **C++** has `queryWithEndl`, `queryWithFlush`, `answer`, `guessNumber`, `findMinimumInteractive`, `exploreGraph`, `findMaximum`, `guessSubset`, `checkResponse` and a `solve` template.
- **Go** has `Query`, `Answer`, `GuessNumber` and `BinarySearchAnswer`.

All three read the judge's reply after flushing. In the tests each language drives its functions against a small in-process fake judge: Python replaces `input()` and stdout, C++ swaps the `cin` and `cout` buffers, Go swaps its reader and writer for pipes. The tests check the final answers and the query counts, and they fail if a query is read before it is flushed (Python).

Each query is O(1) work on your side, so the running time is the number of queries plus bookkeeping. The limit that matters is the judge's query limit, not the CPU time.

## Variants

- **Adaptive judge:** the hidden value is not fixed; the judge may change it as long as it stays consistent with earlier replies. Your strategy must work for the worst case.
- **Multiple test cases:** loop and keep a separate budget for each case.
- **Batching:** some problems allow several questions in one line to save round trips.
- **Randomised strategies:** useful against an adaptive judge, but you need an upper bound on the failure probability.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Forgetting to flush** after a query or the final answer.
- **Printing debug output on stdout.** The judge reads it as a query. Write debug text to stderr.
- **Reading ahead of the protocol.** Do not read a reply the judge has not sent.
- **Ignoring `-1`.** Keep going after an error and the verdict becomes unclear. Exit at once.
- **Wasting queries.** The original C++ `findMinimumInteractive` re-asked `hi` in every iteration and spent two queries per step; it now asks it once.
- **Answering twice or not at all.** Print `! x` exactly once, unless the protocol ends on `correct`.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="How do I test an interactive solution without the judge?">
    Write a fake judge. It is a small function that receives each line you print and returns the reply. The tests in this repository do exactly that in all three languages. For stand-alone binaries use two pipes or a local interactor program that plays the judge.
  </FaqItem>
  <FaqItem question="Why does the code use higher and lower instead of numbers?">
    The reply format comes from the problem statement. Here it is a word; many judges use `<`, `>` and `=` or numbers. Parse exactly what the statement defines.
  </FaqItem>
  <FaqItem question="Can I use fast input in an interactive problem?">
    Only reading what is available now. Reading the whole input up front blocks forever, because the judge only writes after your query. Use line-based reads or token reads that stop at the end of the reply.
  </FaqItem>
  <FaqItem question="What does the tournament function do differently from find_maximum?">
    Both use n - 1 comparisons. The tournament compares in rounds of independent pairs, so the comparisons of one round could be sent together if the problem allows batching.
  </FaqItem>
</Faq>
