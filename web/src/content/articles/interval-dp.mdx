## How interval DP works

The input is a row of `n` things, and the question can be asked of any contiguous part of it: "what is the cheapest way to merge piles `i..j`?", "how many coins can the balloons between these two earn?", "how few cuts split this substring into palindromes?". `dp[i][j]` holds the answer for the range `i..j` alone. Matrix Chain Multiplication is the classic example; here the pattern carries three problems.

The main one merges piles. Piles of stones lie in a row; you may merge two neighbouring piles into one, and a merge costs the size of the pile it makes. The cheapest way to end with one pile:

<Steps>
  <Step title="Look at the last merge">
    Whatever the order, the last merge of piles `i..j` joins a pile made of `i..k` with a pile made of `k+1..j`, for some split `k` with `i <= k < j`. It costs `sum(i..j)`, whichever `k` it is.
  </Step>
  <Step title="The two parts are independent">
    Before that merge, the left pile was built from its own piles only, and the right pile from its own. So each must be built as cheaply as possible: `dp[i][j] = min over k of dp[i][k] + dp[k+1][j] + sum(i..j)`, with `dp[i][i] = 0`.
  </Step>
  <Step title="Fill by length">
    Both parts are shorter than `i..j`. Filling every range of length 2, then 3, up to `n` means the two cells a split reads are always final. Prefix sums give `sum(i..j)` in O(1).
  </Step>
  <Step title="Keep the split and read it back">
    `split[i][j]` keeps the `k` that won. From the whole row, follow `split` down to single piles; listed in post-order, the merges are an order that costs exactly `dp[0][n-1]`.
  </Step>
</Steps>

<Callout title="Why the order is by length">
A split of `i..j` reads `dp[i][k]` and `dp[k+1][j]`: one in the same row to the left, one in the same column further down. Both are shorter ranges. Going row by row from the top would read `dp[k+1][j]` before it is computed, and on piles `3, 2, 4, 1` that order returns 10 instead of 20, with no error. Any order that finishes shorter ranges first works, for example rows from the bottom up; by length is the clearest.
</Callout>

## See it in action

The two tables are `dp` and `split`; the piles are the chips above `dp`, with their positions under them. Each diagonal is one length. For each cell, every split `k` is tried in turn: the cell is filled with the best cost so far, the two cells it reads are outlined, and `split` shows the `k` kept so far. When the table is full, the merge tree is read back from `split`, and each merge appears as soon as both of its parts are built. Try **Greedy fails**, where merging the cheapest neighbours first pays 21 instead of 20, and **Equal piles (ties)**, where several splits tie and the smallest one is kept.

## Pseudocode

```text
merge_piles_plan(piles):
    n = len(piles)
    P = prefix sums: P[0] = 0, P[t + 1] = P[t] + piles[t]
    dp[i][i] = 0 for every i
    for length = 2 to n:                        # shorter ranges first
        for i = 0 to n - length:
            j = i + length - 1
            dp[i][j] = infinity
            for k = i to j - 1:                 # the last merge joins i..k and k+1..j
                cost = dp[i][k] + dp[k+1][j] + P[j+1] - P[i]
                if cost < dp[i][j]:             # strict: the smallest k wins a tie
                    dp[i][j] = cost
                    split[i][j] = k
    merges = []
    stack = [(0, n - 1, parts_built = false)]
    while stack is not empty:
        (lo, hi, parts_built) = stack.pop()
        if lo == hi: continue                   # a single pile is already built
        k = split[lo][hi]
        if parts_built: merges.append((lo, k, hi))
        else: push (lo, hi, true), then (k + 1, hi, false), then (lo, k, false)
    return dp[0][n - 1], merges
```

**Which merges.** The splits are tried in increasing order and a cell changes only on a strict gain, so `split[i][j]` is the smallest `k` that reaches the minimum. On piles `1, 1, 1` both splits cost 5 and `k = 0` is kept, so the merges are `(1, 1, 2)` and then `(0, 0, 2)`: the last two piles first. The merges come in post-order: those that build the left part, then those that build the right part, then the merge that joins them. The C++ and Go tests check the costs and the merges on 40 rows of piles, and the other two problems on 24 inputs each, against outputs of the Python code.

**Edge cases.** No piles and one pile cost 0, with no merges. Two piles cost their sum. Equal piles tie often, and the smallest `k` decides. A pile of size 0 is fine; a negative size is an error.

**Overflow.** C++ and Go keep costs in 64-bit integers. A candidate whose cost does not fit simply loses: on piles 2<sup>62</sup>, 0, 1 the split after pile 1 would cost 2<sup>63</sup> + 1, but the minimum, 2<sup>62</sup> + 2, fits and is returned. Only when the answer itself does not fit, as for piles 2<sup>62</sup> and 2<sup>62</sup>, do they report an overflow; Python returns 2<sup>63</sup>.

## Complexity analysis

There are `n - L + 1` ranges of length `L`, and each tries `L - 1` splits. Summed over the lengths, that is exactly `(n^3 - n) / 6` candidates; the tests count them and fail if a loop bound is off by one.

Doubling `n` multiplies the work by about 8. In Python 400 piles take about 3 seconds; in C++ and Go 1000 piles take under a second. For pile merging, the best split of `i..j` lies between the best splits of `i..j-1` and `i+1..j`, and Knuth's optimization uses that window to bring the time down to O(n<sup>2</sup>).

## Burst balloons: choose the last action

Bursting a balloon earns the product of its value and its two current neighbours, with a 1 past either end. The first balloon you burst makes its neighbours meet, so the two sides interact and a split by the first burst does not work. The **last** balloon burst between two balloons that stay, `left` and `right`, has exactly those two as neighbours, and until it goes it keeps the balloons on its left apart from those on its right.

<Equation label="Burst balloons" expr="dp[left][right] = max over left < k < right of dp[left][k] + v[left] * v[k] * v[right] + dp[k][right]" />

With `v = [1] + nums + [1]`, the answer is `dp[0][n+1]`. On balloons `3, 1, 5, 8`, `burst_balloons` returns 167: the last balloon of the whole row is 8 (1 x 8 x 1 = 8), before it the 3 (1 x 3 x 8 = 24), before that the 5 (3 x 5 x 8 = 120), and first the 1 (3 x 1 x 5 = 15).

## Palindrome cuts: a table feeding a table

`min_palindrome_cuts` first fills `pal[i][j]`, "`s[i..j]` reads the same both ways", by length too: the ends match and the inside is a palindrome. That is O(n<sup>2</sup>). Then a palindrome needs no cut, and any other range has a first cut after some `k`:

<Equation label="Cuts" expr="cuts[i][j] = 0 if pal[i][j], else min over i <= k < j of cuts[i][k] + 1 + cuts[k+1][j]" />

`min_palindrome_cuts("banana")` returns 1: `b | anana`. The interval form costs O(n<sup>3</sup>), but only the end of the first piece matters, so the same table also feeds an O(n<sup>2</sup>) form over prefixes; the tests check that the two agree with brute force.

## Top-down, with a memo

`merge_piles_memo` is the same recurrence written as a recursive function: before trying a split `k`, it asks for `i..k` and `k+1..j`, computing each once and remembering it. The recursion finds the order by itself, tries the same candidates as the loops in another order, and fills the same tables, which the tests compare cell by cell. The price is a recursion `n` calls deep: past Python's default limit of 1000 frames it raises `RecursionError`.

## Applications

- **Merging files or runs.** The cheapest order to merge neighbouring sorted runs or files when a merge costs their total size.
- **Products and expressions.** The order of a chain of matrix products, or the best way to parenthesize an expression.
- **Cutting.** Cutting a rod, a string or a polygon where each cut costs the length of the piece it splits, or splitting text into palindromes.
- **Parsing.** Grammar parsing over spans (the CYK algorithm) fills its table by span length the same way.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Filling row by row from the top.** A split reads `dp[k+1][j]` before it is computed: 10 instead of 20 on piles `3, 2, 4, 1`.
- **Summing the range inside the split loop.** That makes it O(n^4); prefix sums give the sum in O(1).
- **Choosing the first balloon.** After the first burst its neighbours meet and the sides are no longer independent; choose the last one.
- **Forgetting the padding.** Without a 1 at each end, the end balloons have nothing to multiply by.
- **Using `<=` for the update.** The cost is the same, but `split` keeps the largest tied `k` and the merges change.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="How is this different from Matrix Chain Multiplication?">
    It is the same pattern. Matrix Chain Multiplication splits a chain of matrices and pays `dims[i-1] * dims[k] * dims[j]` to join the two halves; merging piles pays `sum(i..j)`. The loops, the fill order and the split table are the same.
  </FaqItem>
  <FaqItem question="Why does the tie rule matter if the cost is the same?">
    Several orders can cost the same. With a strict `<` and `k` going up, the code keeps the smallest `k`, so Python, C++ and Go return the same merges, and the tests can pin them.
  </FaqItem>
  <FaqItem question="Can a pile be empty?">
    Yes. A pile of size 0 costs nothing to merge, and on a row of zeros every split ties, so the smallest is kept each time. A negative size is rejected.
  </FaqItem>
  <FaqItem question="When should I use the top-down form?">
    When the order of the ranges is hard to see, the recursion finds it by itself. For merging piles the loops by length are simple, need no recursion, and do the same work.
  </FaqItem>
</Faq>
