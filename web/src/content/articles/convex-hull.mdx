## How convex hull works

Everything rests on one test, the **cross product** `cross(o, a, b) = (a.x - o.x)(b.y - o.y) - (a.y - o.y)(b.x - o.x)`. Walking from `o` to `a` and then to `b`, the sign tells the kind of turn: positive for a left (counterclockwise) turn, negative for a right turn and zero if the three points are collinear. A counterclockwise walk around a convex polygon only ever turns left, so any vertex where the walk would turn right (or go straight) is not a hull vertex.

### Graham's scan

<Steps>
  <Step title="Remove duplicates and pick a pivot">
    Equal points are dropped (compared exactly). The pivot is the bottom-most point, leftmost on a tie. It is always a hull vertex, and every other point lies at or above its horizontal line.
  </Step>
  <Step title="Sort by angle around the pivot">
    Point `a` comes before `b` if `cross(pivot, a, b) > 0`. Points on the same ray from the pivot are ordered nearest first.
  </Step>
  <Step title="Scan with a stack">
    For each point `p`, pop the stack while the last two stack points and `p` do not make a strict left turn (`cross <= 0`), then push `p`. Each point is pushed once and popped at most once.
  </Step>
</Steps>

### Jarvis march (gift wrapping)

<Steps>
  <Step title="Start at the leftmost point">
    The leftmost point (lowest on a tie) is a hull vertex.
  </Step>
  <Step title="Pick the next vertex">
    From the current vertex, scan all points and keep the one that is the most clockwise. On a tie (same ray) keep the farthest. Every other point is then on the left of, or on, the line to it.
  </Step>
  <Step title="Wrap until you return">
    Repeat from the new vertex. The walk ends when the best next point is the starting point again.
  </Step>
</Steps>

<Callout title="The invariant">
In Graham's scan the stack always holds a strictly convex chain from the pivot through the points seen so far. A new point can only cut off the tail of that chain, never the front. In Jarvis march every point added is a hull vertex, because all other points lie on its left.
</Callout>

Jarvis march gives the same polygon: from `A` the most clockwise point is `B`, from `B` it is `F`, from `F` it is `G`, and from `G` it is `A`, which ends the walk. The loop has four rounds, one per hull vertex, each scanning all seven points.

## Pseudocode

```text
grahamScan(points):
    pts = distinct points (exact comparison)
    if size(pts) < 3: return pts sorted by (y, x)
    bottom = point with smallest (y, x)
    sort the other points: a before b if cross(bottom, a, b) > 0,
                           on a tie, nearer to bottom first
    hull = []
    for p in [bottom] + sorted others:
        while size(hull) > 1 and cross(hull[-2], hull[-1], p) <= 0:
            pop hull
        push p on hull
    return hull

jarvisMarch(points):
    pts = distinct points (exact comparison)
    if size(pts) < 3: return pts sorted by (x, y)
    leftmost = point with smallest (x, y)
    hull = [leftmost]
    while size(hull) <= size(pts):
        current = last of hull
        next = none
        for p in pts, p != current:
            if next is none: next = p
            else if cross(current, next, p) < 0
                 or (cross == 0 and dist(current, p) > dist(current, next)):
                next = p
        if next == leftmost: break
        append next to hull
    return hull
```

## Implementation

Both functions take a list of points and return a new list: the hull vertices in counterclockwise order. Graham's scan starts at the bottom-most point and Jarvis march at the leftmost point. Duplicates are removed, and with fewer than three distinct points the distinct points themselves are returned. All points collinear gives the two end points. The input is never modified, including in Go.

All decisions use exact comparisons, with no tolerance. For integer coordinates this is exact in Python, and exact in C++ and Go as long as the cross products stay below 2<sup>53</sup>, which holds when coordinate differences are below about 6.7 &times; 10<sup>7</sup>. For non-integer coordinates the result can still differ in near-collinear cases, because of rounding.

## Applications

- **Collision detection.** A convex shape is cheaper to test than the raw point cloud.
- **Diameter and width.** The farthest pair of points is always a pair of hull vertices; Rotating Calipers finds it from the hull.
- **Shape analysis and graphics.** Bounding outlines, clipping and shape descriptors.
- **Fencing and enclosure problems.** The shortest fence around a set of posts is its hull.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **A tolerance on the angle sort.** Treating angles that differ by less than 1e-9 as equal is not a consistent ordering. The scan can then keep interior points and return a hull that is not convex. Compare with the cross product instead.
- **A tolerance in the gift-wrapping loop.** With an absolute 1e-9 on the cross product, tiny-scale input looks collinear everywhere, and the wrap never returns to the start. This is why the loop here uses exact comparisons and a size bound.
- **Using `<` instead of `<=` when popping.** Popping only on right turns keeps collinear points on the boundary. This code pops on `cross <= 0`, so collinear boundary points are excluded.
- **Forgetting duplicates.** Equal points make a zero-length edge and a zero cross product; they are removed first.
- **Fewer than three points.** The hull is the distinct points themselves, not an error.
- **Sorting the caller's list.** Work on a copy: reordering the argument is a side effect that callers do not expect.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does the cross product decide hull membership?">
    On a counterclockwise walk around a convex polygon every turn is a left turn. If the last two stack points and the next point make a right turn or are collinear, the middle point lies inside or on an edge of the polygon, so it cannot be a strict vertex and is popped.
  </FaqItem>
  <FaqItem question="Are collinear points on the hull boundary included?">
    No. Only the corner vertices are returned. If all points are collinear, the result is the two end points.
  </FaqItem>
  <FaqItem question="Which one should I use?">
    Use Graham's scan by default. Use Jarvis march when you know the hull is tiny compared with n. For production code, Andrew's monotone chain is the common choice, but it is not implemented in this repository.
  </FaqItem>
  <FaqItem question="Can I use decimals?">
    Yes, but the orientation test is only as exact as the arithmetic. For decimal data that may be nearly collinear, scale to integers first, or accept that borderline points may be kept or dropped differently on different platforms.
  </FaqItem>
</Faq>
