## How Activity Selection works

One person (or one room, or one machine) can do a single activity at a time. Each activity `i` occupies the half-open interval from `start` to `finish`, so two activities are compatible when one finishes no later than the other starts: `start >= last_finish`. The goal is the **largest set of pairwise compatible activities**.

<Steps>
  <Step title="Sort by finish time">
    Order the activities by `finish`, smallest first. The code keeps each activity's original index so it can return indices into the caller's list.
  </Step>
  <Step title="Take the first activity">
    The activity that finishes earliest is always part of some optimal answer. Remember its finish time as `last_finish`.
  </Step>
  <Step title="Scan the rest once">
    For each remaining activity in sorted order, if `start >= last_finish` select it and set `last_finish` to its finish time. Otherwise skip it: it overlaps the activity you already hold.
  </Step>
</Steps>

<Callout title="Why earliest finish is the right rule">
Finishing early leaves the largest possible room for everything that comes after. Take any optimal schedule and look at its first activity. The earliest-finishing activity ends no later, so swapping it in cannot collide with the rest of the schedule, and the count stays the same. So some optimal schedule contains the greedy choice. What remains is the same problem on the activities that start at or after that finish, and the argument repeats (induction).
</Callout>

## Pseudocode

```text
activitySelection(activities):
    if activities is empty: return []
    order = indices of activities sorted by finish time
    selected = [order[0]]
    lastFinish = finish of activities[order[0]]
    for k = 1 to n - 1:
        i = order[k]
        if start of activities[i] >= lastFinish:
            append i to selected
            lastFinish = finish of activities[i]
    return selected
```

The result lists indices into the original input, in order of finish time.

## Implementation

All three languages use the same algorithm. The Python version also has the weighted variant (`activity_selection_with_weights`, a dynamic program that returns the best total weight) and a recursive version (`activity_selection_recursive`). The C++ and Go versions only have the greedy function.

<TopicCode topic="Algorithms/Greedy/Activity_Selection" />

**Tie-breaking.** When two activities finish at the same time, which one is picked depends on the sort. Python's `sorted` is stable, so the one that comes first in the input wins. C++ `std::sort` and Go `sort.Slice` are not stable, so the chosen index among ties is not specified. The number of activities selected is the same in all cases.

The recursive Python version is slower on purpose: it slices `activities[1:]` and builds `selected + [idx]` in every call, which is <BigO of="n^2" /> time and space, and it recurses n levels deep, so it hits Python's recursion limit on large inputs.

The weighted dynamic program in Python scans backwards for the last compatible activity, which is <BigO of="n^2" /> in the worst case. A binary search over finish times would make it <BigO of="n log n" />; the repository does not do that.

## Weighted activity selection

If every activity has a weight and you want the largest total weight, earliest finish is no longer enough. With `(1, 4, 10)`, `(3, 5, 5)`, `(0, 6, 15)` and `(5, 7, 7)`, the best set is `(1, 4)` and `(5, 7)` with weight 17, while the single heavy activity `(0, 6)` is worth only 15. The Python function `activity_selection_with_weights` solves it with dynamic programming: sort by finish, and let `dp[i]` be the best weight using the first `i` activities, either skipping activity `i` or taking it together with `dp[j]` for the last compatible `j`.

## Applications

- **Single-room booking.** Accept the largest number of meetings for one room.
- **Interval clean-up.** Dropping the fewest intervals so the rest do not overlap is the same problem: answer is n minus the maximum number kept.
- **Resource allocation.** One machine, one antenna, one lecture hall: any exclusive resource with fixed time slots.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Sorting by start time.** It looks natural and it is wrong; see the counterexamples above.
- **Using `>` instead of `>=`.** Activities may touch: `1-2` and `2-3` are compatible. With `>` you would drop valid activities.
- **Forgetting the original indices.** After sorting, positions no longer match the input. The code sorts `(index, activity)` pairs so it can return the original indices.
- **Starting `last_finish` at -1 (or 0).** A sentinel that is a real time breaks inputs with negative times; the Python recursive version once did this. Start from the first selected activity, or from negative infinity.
- **Using it for weights.** A heavy activity can outweigh several short ones; use dynamic programming.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why is sorting by finish time correct but sorting by duration is not?">
    The proof only needs that the chosen activity ends no later than the first activity of an optimal schedule. Earliest finish guarantees that. A short activity can still sit in the middle of the day and block two long ones, as `0-5, 4-6, 5-10` shows.
  </FaqItem>
  <FaqItem question="Is the answer unique?">
    The size of the answer is unique, the set is not. Different tie-breaks or different optimal schedules can produce different index lists of the same length.
  </FaqItem>
  <FaqItem question="What if an activity has zero length?">
    Nothing special happens: it is selected when `start >= last_finish`, like any other activity, and then `last_finish` becomes its finish time.
  </FaqItem>
  <FaqItem question="How do I solve it when the intervals carry weights?">
    Use dynamic programming over the intervals sorted by finish time, as `activity_selection_with_weights` does. It is the same sort, but each step chooses between skipping an interval and taking it plus the best result before it.
  </FaqItem>
</Faq>
