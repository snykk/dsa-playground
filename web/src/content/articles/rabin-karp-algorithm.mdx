## How Rabin-Karp works

Comparing two strings of length `m` costs O(m); comparing two numbers costs O(1). Rabin-Karp turns each window of the text into a number (a hash) and compares numbers. The trick is a hash that can slide: the hash of the next window comes from the previous one in O(1).

The hash treats a string as a number in base `d = 256`, reduced modulo a prime `q`. For `s[0..m-1]` it is `(s[0]*d^(m-1) + s[1]*d^(m-2) + ... + s[m-1]) mod q`.

<Steps>
  <Step title="Hash the pattern and the first window">
    Compute both with Horner's rule: `hash = (d * hash + code(c)) mod q` for each character. Precompute `h = d^(m-1) mod q`.
  </Step>
  <Step title="Compare hashes at each window">
    If the window's hash equals the pattern's hash, the strings might be equal. If they differ, the strings are certainly different, and the window is skipped.
  </Step>
  <Step title="Verify a hash hit">
    Compare the window with the pattern character by character. Equal hashes of different strings (a collision, or spurious hit) are rejected here, so the answer is always exact.
  </Step>
  <Step title="Roll the hash">
    Move to the next window: subtract the leading character's contribution, multiply by `d`, add the new trailing character: `hash = (d * (hash - lead * h) + trail) mod q`.
  </Step>
</Steps>

<Callout title="One-sided error">
Different strings can share a hash, but equal strings never have different hashes. So a hash mismatch is proof, a hash match is only a hint, and the verification step turns the hint into a certainty.
</Callout>

## Pseudocode

```text
rabin_karp_search(text, pattern, base = 256, mod = 101):
    if pattern is empty: return []
    if text is empty or m > n: return []
    h = base^(m-1) mod mod
    pattern_hash = 0; text_hash = 0
    for i = 0 to m - 1:
        pattern_hash = (base * pattern_hash + code(pattern[i])) mod mod
        text_hash    = (base * text_hash    + code(text[i]))    mod mod
    for i = 0 to n - m:
        if pattern_hash == text_hash and text[i .. i+m-1] == pattern:
            report i
        if i < n - m:
            text_hash = (base * (text_hash - code(text[i]) * h) + code(text[i+m])) mod mod
            if text_hash < 0: text_hash += mod
```

## Implementation

Python takes `base` and `mod` as parameters (defaults 256 and 101) and also has `rabin_karp_search_count` and `rabin_karp_search_first`. C++ and Go fix the constants at 256 and 101. In C++ the characters are hashed as `unsigned char`: a plain `char` is signed, so a byte of 0x80 or more would make the initial hash negative while the rolled hash is normalised to `[0, mod)`, and equal windows would stop matching. An **empty pattern, an empty text, or a pattern longer than the text returns `[]`**. Python indexes code points; C++ and Go index bytes.

    { case: 'Worst case', time: 'O(n*m)', when: 'Every window has the pattern hash (or the text is full of real matches, such as `AAAAA` with `AAA`) and each hit costs O(m) to verify.' },
  ]}
/>

The default modulus here is 101, which is small on purpose so the code reads easily: about 1 window in 101 shares the pattern hash by chance. Results stay correct because hits are verified, but a large prime (around 10<sup>9</sup> or more) makes spurious hits rare.

<Callout title="Mind the arithmetic when you raise the modulus">
In C++ and Go the hash is a machine integer. `base * (hash - lead * h)` is about `256 * mod * mod` in magnitude, so with a modulus near 10<sup>9</sup> it overflows 32 bits and needs 64-bit arithmetic (and care with negative values). Python integers have no such limit.
</Callout>

## Applications

- **Searching for many equal-length patterns.** Hash them once, scan the text once.
- **Plagiarism and duplicate detection.** Fingerprint windows of documents.
- **Finding repeated substrings of a given length**, by hashing every window.
- **2D pattern matching** in grids and images.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Trusting equal hashes.** A hash hit is only a candidate. Skipping the verification returns wrong answers.
- **Negative hashes.** In C and Go the `%` of a negative number is negative, so normalise after the rolling step. Python's `%` is already non-negative.
- **Signed bytes in C++.** Hash `unsigned char` values; a negative byte value breaks the match between the initial and the rolled hashes.
- **A tiny modulus on adversarial text.** Correct but slow. Use a large prime in real code.
- **A wrong power.** `h` is `base^(m-1)`, not `base^m`.
- **Calling a match a collision.** In `AAAAA` against `AAA` the equal hashes are real matches; a collision is equal hashes with different strings.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does the rolling hash work modulo a prime?">
    Modular arithmetic keeps the numbers small, and subtracting `lead * h` then multiplying by the base removes the old leading digit and shifts the rest, exactly as in decimal. A prime modulus spreads values evenly, which keeps collisions rare. Correctness does not depend on the modulus, only speed does.
  </FaqItem>
  <FaqItem question="Can Rabin-Karp give a wrong answer?">
    No. A hash mismatch proves the strings differ, and every hash match is verified character by character. A bad modulus only makes it slower.
  </FaqItem>
  <FaqItem question="What if the pattern is longer than the text?">
    The search returns `[]` immediately. Without this check the first window would index past the end of the text.
  </FaqItem>
  <FaqItem question="Why is 101 used, and is it enough?">
    It is a small prime that keeps the arithmetic easy to follow. It is fine for learning, but with about 1 in 101 windows colliding by chance it is far too small for large inputs.
  </FaqItem>
</Faq>
