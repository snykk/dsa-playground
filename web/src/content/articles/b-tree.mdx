## What a B-tree is

A B-tree of **minimum degree** `t` (at least 2) is a search tree with these rules:

- Every node holds its keys in sorted order. A node with `k` keys has `k + 1` children, and the keys separate the children: everything in child `i` lies between key `i - 1` and key `i`.
- Every node except the root holds between `t - 1` and `2t - 1` keys. The root holds between 1 and `2t - 1` (or 0 when the tree is empty).
- All leaves are at the same depth.

Unlike a B+ tree, **every node stores real keys**, internal nodes included. A binary search tree is the case of one key per node; a B-tree packs many keys into one node so that one node visit does the work of several BST levels. The repository's default is `t = 3` (2 to 5 keys per node); `t = 2` gives the 2-3-4 tree.

Because the tree only grows at the root (a root split) and shrinks at the root (a root merge), all leaves always move down or up together. That is how the equal-depth rule survives every operation.

<Callout title="Height is logarithmic in the node size">
A tree whose leaves are at depth `h` (root at depth 0) holds at least `2 t^h - 1` keys: the root has 2 children and every other internal node at least `t`. Solving for `h` gives `h <= log_t((n + 1) / 2)`. With `t = 100` a billion keys fit in a tree about five levels deep. Each level is one node read, which is why B-trees dominate on disks.
</Callout>

The API differs a little per language. Python: `search` returns `(node, index)` or `None`, and `delete` returns nothing. C++ and Go: `search` returns a boolean, `remove` (C++) and `Delete` (Go) return whether a key was removed, and `traverse` / `Traverse` return a sorted list. Inserting a key that is already present stores a second copy; delete removes one copy.

### Search

In each node, scan to the first key that is `>=` the target. If it equals the target, done. Otherwise follow the child just left of that key, or report a miss at a leaf. Searching `30` in the tree above:

### Insert: split on the way down

Inserting always happens in a leaf. The classic trick (CLRS, and this repository) is to split every **full** node (`2t - 1` keys) *before* entering it, so the leaf always has room and the algorithm never has to walk back up. A split cuts a full node around its median key: the left half and the right half become two siblings, and the median moves up into the parent (which is known not to be full).

Inserting `10, 20, 30, 40, 50, 60` into an empty `t = 2` tree:

Only a root split makes the tree taller. That is the only way the height can increase, and every leaf gets one level deeper at the same moment.

### Delete: keep every node above the minimum

Deleting could leave a node with fewer than `t - 1` keys. The repository's delete avoids that by making sure the child it is about to enter has more than `t - 1` keys, fixing it first if not. There are three cases:

<Steps>
  <Step title="Key is in a leaf">
    Remove it. The leaf was topped up on the way down, so it still has at least `t - 1` keys.
  </Step>
  <Step title="Key is in an internal node">
    If the child on its left has more than `t - 1` keys, replace the key by its **predecessor** (the largest key of that subtree) and delete the predecessor below. Otherwise do the same with the **successor** from the right child. If both children are minimal, **merge** them with the key into one node and continue deleting inside it.
  </Step>
  <Step title="Key is not in this node">
    Before descending into child `i`, if it has exactly `t - 1` keys, fix it: **borrow** a key through the parent from a sibling that has spare keys (left first, then right), else **merge** it with a sibling. A last child merges with its left sibling, any other child with its right one.
  </Step>
</Steps>

Deleting `40` and then `10` from the `t = 2` tree `[20, 40]` over `[10]`, `[25, 30, 35]`, `[50, 60]`:

Then `delete(20)` finds a minimal child with only minimal siblings, so it merges `[20]`, `25` and `[35]` into `[20, 25, 35]`. The root `[50]` keeps two children:

## Implementation

The three versions share the same structure: a node with `keys` and `children`, a proactive `split_child`, `insert_non_full`, and a delete built from `fill_child`, borrow and merge helpers. All three are tested against a sorted reference on thousands of random insert/delete/search operations, with an invariant checker (fill bounds, key order, equal leaf depth) after the run. The C++ tree owns its nodes (destructor, copying disabled).

<DataTable
  columns={['Operation', { label: 'Node reads', kind: 'mono' }, { label: 'Comparisons', kind: 'mono' }, 'Why']}
  rows={[
    ['search', 'O(log_t n)', 'O(t log_t n)', 'height is at most log_t((n + 1) / 2); each node is scanned linearly'],
    ['insert', 'O(log_t n)', 'O(t log_t n)', 'one descent; a split costs O(t) and happens at most once per level'],
    ['delete', 'O(log_t n)', 'O(t log_t n)', 'one descent; a borrow or merge costs O(t) per level'],
    ['traverse', 'O(n / t)', 'O(n)', 'every key is visited once'],
  ]}
/>

The code scans each node linearly, hence the factor `t`. Binary search inside the node would make comparisons O(log n) again, but the point of a B-tree is to minimise node reads, not comparisons. Space is O(n); the recursion is as deep as the tree is tall.

## Applications

- **Database and file-system indexes:** the structure is designed for block storage. Production systems often use the B+ variant (see B+ Tree).
- **Ordered key-value stores in memory** with a large `t`, where cache-line-sized nodes beat pointer-chasing binary trees.
- **Teaching balanced trees:** the `t = 2` case is the 2-3-4 tree, a clean way to understand red-black rotations.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Splitting after the insert instead of before the descent.** The one-pass algorithm relies on the parent never being full when a child splits.
- **Merging with the wrong sibling.** The last child must merge with its left sibling; if the delete then keeps descending at the old index it enters the wrong subtree (this was a real bug in the Python version) and may leave a key behind.
- **Forgetting to shrink the root.** After a merge, an empty internal root must be replaced by its only child.
- **Mixing up `t` with the maximum.** `t` is the *minimum* degree: a node has at most `2t - 1` keys.
- **Expecting set semantics.** Inserting an existing key adds a second copy.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why do B-trees use many keys per node?">
    Reading a disk block costs far more than comparing keys already in memory. A node sized to one block lets a single read narrow the search by a factor of `t` or more, so the tree is only a few levels deep.
  </FaqItem>
  <FaqItem question="What is the difference between a B-tree and a B+ tree?">
    In a B-tree every node holds keys (and, in a map, values). In a B+ tree only leaves hold data, internal nodes hold copies of separators, and the leaves are linked for fast range scans.
  </FaqItem>
  <FaqItem question="Why split a full node before descending into it?">
    It guarantees the parent has room for the promoted median, so the insert never has to go back up. The cost is that a node may be split slightly before it is strictly necessary.
  </FaqItem>
  <FaqItem question="Can the root have fewer than t - 1 keys?">
    Yes. The root is exempt from the minimum; it only needs one key (or none when the tree is empty), and it is the only node whose removal makes the tree shorter.
  </FaqItem>
</Faq>
