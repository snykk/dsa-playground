## How Fractional Knapsack works

You are given `n` items, each with a `value` and a `weight`, and a capacity `W`. You may take any amount `x` between 0 and 1 of each item, which brings in `x * value` and uses `x * weight` of capacity. The goal is the largest total value that fits.

The deciding number is the **ratio** `value / weight`: how much value one unit of capacity buys.

<Steps>
  <Step title="Compute each ratio">
    Divide `value` by `weight`. An item of weight 0 uses no capacity, so its ratio is treated as infinite and it is taken first.
  </Step>
  <Step title="Sort by ratio, highest first">
    The best deals come first. Ties can go in either order; the total is the same.
  </Step>
  <Step title="Fill the bag in that order">
    While capacity remains: if the whole item fits, take it all and subtract its weight. If it does not fit, take the fraction `remaining / weight` of it, which fills the bag exactly, and stop.
  </Step>
</Steps>

<Callout title="Why the best ratio first is optimal">
Suppose a full bag contains some of a lower-ratio item while a higher-ratio item is not used up. Remove a small amount of weight `d` from the lower item and add `d` of the higher one. The weight is unchanged, and the value changes by `d * (high ratio - low ratio)`, which is at least 0. So the swap never hurts, and repeating it turns any solution into the greedy one without losing value. This only works because items can be cut: you can always move exactly `d` of weight.
</Callout>

## Worked example

Capacity 50 and three items, written `value / weight`: `60 / 10`, `100 / 20`, `120 / 30`. Their ratios are 6, 5 and 4, so they are already in the right order. `fractional_knapsack` returns a total of 240 and the fractions `1.0`, `1.0` and `2/3`.

The same items with the 0/1 rule (take an item whole or not at all) give a different answer. The greedy order would take the first two items (value 160, weight 30) and then find that the third no longer fits. The real 0/1 optimum is the second and third items together, value 220. That is why greedy is only safe when items can be split.

## Pseudocode

```text
fractionalKnapsack(items, W):
    if items is empty or W <= 0: return 0
    sort items by value / weight, highest first     # weight 0: ratio = infinity
    total = 0
    remaining = W
    for each item (value, weight) in that order:
        if remaining <= 0: break
        if weight == 0:
            total += value                          # free item: take all of it
            continue
        take = min(weight, remaining)
        total += value * (take / weight)
        remaining -= take
    return total
```

## Implementation

The Python version has two functions: `fractional_knapsack` returns the total and the list of `(value, weight, fraction)` it took, and `fractional_knapsack_value_only` returns just the total. C++ and Go return only the total. In Python, items are `(value, weight)` tuples; in C++ they are `std::pair<double, double>` and in Go `Item{Value, Weight}`.

<TopicCode topic="Algorithms/Greedy/Fractional_Knapsack" />

**Two differences to know.** Python sorts a copy, so your list keeps its order. The C++ and Go versions sort the vector or slice you pass in, so the caller's order changes. And C++ and Go work in `double` / `float64`, so totals are floating-point values.

The fractional answer is always at least the 0/1 answer for the same items, because every 0/1 choice is also a legal fractional choice. That makes it a quick upper bound, which branch-and-bound solvers use for 0/1 knapsack.

## Applications

- **Divisible resources.** Filling a tank, a truck or a budget with materials that can be taken in any quantity, such as liquids, grain or computing time.
- **Upper bounds.** The fractional optimum bounds the 0/1 optimum from above, which is how branch and bound prunes.
- **Choosing the best mix** under a single resource limit when the amounts are continuous.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Sorting by value or by weight alone.** Only the ratio works. A heavy valuable item can have a lower ratio than a small cheap one.
- **Using the greedy for 0/1.** It is wrong there. Use dynamic programming.
- **Dividing by a zero weight.** `value / weight` fails for a free item. The code gives such items an infinite ratio and takes them whole. It once raised `ZeroDivisionError` in Python and returned NaN in C++ and Go.
- **Capacity of 0 or less.** All three versions return 0 immediately, before looking at the items. That also skips a free item (weight 0) that could have been taken.
- **Forgetting the partial item.** After the whole items, the last one is cut with `remaining / weight`. Stopping early leaves value on the table.
- **Surprised by reordering.** In C++ and Go the input is sorted in place.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does the greedy rule work here but not for 0/1 knapsack?">
    Because here you can move any amount of weight between items, so the exchange argument always applies. With whole items, the best-ratio item may leave a gap that no remaining item fills well, and a different set of items can be better. The example above shows 160 against 220.
  </FaqItem>
  <FaqItem question="Is the optimal answer unique?">
    The total is unique. The chosen items are not when ratios tie: any order of equal-ratio items gives the same total.
  </FaqItem>
  <FaqItem question="Can the result be larger than the sum of the values?">
    No. The total is at most the sum of all values, and it equals that sum when everything fits (the all-items-fit test).
  </FaqItem>
  <FaqItem question="Which language returns the fractions taken?">
    Only Python, through `fractional_knapsack`. C++ and Go return the total value only.
  </FaqItem>
</Faq>
