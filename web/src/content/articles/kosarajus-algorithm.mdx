## How Kosaraju's algorithm works

A strongly connected component (SCC) is a maximal set of vertices in which every vertex can reach every other. Collapsing each SCC into one node gives the **condensation**, which is always a DAG. The algorithm peels this DAG from its source end.

<Steps>
  <Step title="DFS on G, recording finish order">
    Run a DFS from every unvisited vertex. When a vertex has no more unvisited neighbours it is finished: append it to the finish order.
  </Step>
  <Step title="Reverse every edge">
    Build the transpose `G^T`. It has exactly the same SCCs as `G`, but the arrows between components point the other way.
  </Step>
  <Step title="DFS on the transpose, latest finisher first">
    Take vertices in decreasing finish time. If a vertex is unvisited, a DFS from it on `G^T` collects exactly one SCC. Skip vertices that already belong to a component.
  </Step>
</Steps>

<Callout title="Why the finish order works">
Take two SCCs `C` and `C'` with an edge from `C` to `C'`. The latest finish time in `C` is always later than the latest finish time in `C'`. So the vertex that finishes last overall lies in a **source** SCC of `G`. In `G^T` that component has no outgoing edges, so a DFS started there cannot leak into another component. Once it is collected, the next unvisited vertex with the latest finish time is in a source of what remains, and the argument repeats.
</Callout>

The Python code returns `[[0, 2, 1], [3, 4], [5]]`: components come out source first, in topological order of the condensation. The order of vertices inside a component is the DFS discovery order and carries no meaning.

If the second pass used the **increasing** finish order instead, it would start at 5. The DFS on `G^T` would go 5, 4, 3, 2, 1, 0 and merge everything into one wrong component.

## Pseudocode

```text
kosaraju(graph):
    visited = {}; finish = []
    for each vertex s in graph:
        if s not in visited: dfs1(s)          # appends a vertex when it finishes
    rev = transpose(graph)                    # a vertex only seen as a neighbour gets an entry
    visited = {}; sccs = []
    for v in reverse(finish):
        if v not in visited:
            component = []
            dfs2(v, rev, component)           # collects everything reachable in rev
            sccs.append(component)
    return sccs
```

## Implementation

Python and C++ run both passes with an explicit stack of (vertex, next neighbour) pairs, so a path or cycle of a million vertices does not overflow the call stack (Python's recursion limit is only about 1000). Go uses recursive closures, which is fine because goroutine stacks grow on demand.

Graphs are maps from a vertex to its neighbour list. A vertex that only appears as a neighbour is handled in all three languages and ends up as its own component if nothing leads back. Vertex ids can be any integer in every language. An empty graph returns no components, and `is_strongly_connected` of an empty graph is false in all three.

Python also provides `kosaraju_scc_count`, `is_strongly_connected` and `kosaraju_condensation_graph` (a map from component index to the components it points to). C++ has `kosarajuSCC`, `kosarajuSCCCount` and `isStronglyConnected`; Go has `KosarajuSCC`, `KosarajuSCCCount` and `IsStronglyConnected`.

Both produce the same partition into components on every graph. Only the order of the list differs.

## Applications

- **Is the graph strongly connected?** Exactly one component, as in CSES Flight Routes Check.
- **Condensation DAG.** Contract every component, then run DP or topological sort on the DAG.
- **2-SAT.** Components of the implication graph decide satisfiability and the assignment.
- **Cycle detection in a directed graph.** A component with more than one vertex, or a vertex with a self-loop, contains a cycle.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Wrong pass-2 order.** Process vertices by decreasing finish time. The increasing order merges components.
- **Forgetting to reverse.** A second DFS on the original graph just collects reachable sets, not components.
- **Neighbour-only vertices.** A vertex that is never a key of the dictionary still needs an entry in the transpose; the repository uses `setdefault` for this.
- **Recursive DFS.** Deep graphs overflow the stack; use an explicit stack in Python and C++.
- **Quoting O(V) space.** The transpose makes the memory O(V + E).
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why reverse the edges in the second pass?">
    The first vertex of pass 2 sits in a source component of `G`. In the original graph a DFS from it would escape into every component it points to. In the reverse graph those arrows point inward, so the DFS stays inside its own component.
  </FaqItem>
  <FaqItem question="Do the two DFS passes need the same vertex order?">
    No. Pass 1 can start anywhere, because any DFS forest gives finish times with the property above. Pass 2 must follow the finish order.
  </FaqItem>
  <FaqItem question="Which is faster, Kosaraju or Tarjan?">
    Both are linear. Tarjan makes one pass and needs no transposed graph, so it is usually a bit faster and lighter. Kosaraju is easier to remember and to prove.
  </FaqItem>
  <FaqItem question="Does the algorithm work with self-loops and multiple edges?">
    Yes. A self-loop only affects a single-vertex component, and repeated edges are just visited twice.
  </FaqItem>
</Faq>
