## How graph coloring works

A coloring is **proper** if the two ends of every edge have different colors. The **m-coloring problem** asks whether a proper coloring with at most m colors exists. The **chromatic number** is the smallest such m.

The solver fills the color array one vertex at a time, in index order `0, 1, ..., V-1`:

<Steps>
  <Step title="Take the next vertex">
    Vertex `v` is the first one without a color. If `v == V`, every vertex is colored and the search succeeds.
  </Step>
  <Step title="Try each color from 1 to m">
    A color `c` is **safe** for `v` when no neighbor of `v` already has color `c`. `is_safe` scans row `v` of the adjacency matrix, so one check costs <BigO of="V" />.
  </Step>
  <Step title="Commit and recurse">
    Give `v` the color and move on to `v + 1`. If that call succeeds, return success up the stack.
  </Step>
  <Step title="Backtrack when stuck">
    If the recursive call fails, reset `color[v] = 0` and try the next color. When all m colors fail, return failure; the caller then changes its own choice.
  </Step>
</Steps>

`chromatic_number` calls the m-coloring solver for `m = 1, 2, ...` and returns the first m that works. That is correct because any proper coloring with m colors is also a proper coloring with m + 1 colors, so the answer is monotone in m.

<Callout title="The invariant">
At every call for vertex `v`, the colored vertices `0..v-1` form a proper partial coloring. A color is committed only after `is_safe` confirms it, so the invariant holds on entry to every deeper call, and a full assignment is automatically a proper coloring.
</Callout>

## Pseudocode

```text
isSafe(graph, v, color, c):
    for i = 0 to V - 1:
        if graph[v][i] == 1 and color[i] == c:
            return false
    return true

solve(graph, m, color, v):
    if v == V:
        return true
    for c = 1 to m:
        if isSafe(graph, v, color, c):
            color[v] = c
            if solve(graph, m, color, v + 1):
                return true
            color[v] = 0            # backtrack
    return false

chromaticNumber(graph):
    for m = 1 to V:
        if graphColoring(graph, m) succeeds:
            return m
    return V
```

## Implementation

All three versions share the same structure: `is_safe`, a recursive helper, `graph_coloring(graph, m)` and `chromatic_number(graph)`. A graph is an adjacency matrix of 0 and 1. Python returns a list or `None`, C++ returns `std::optional<std::vector<int>>` and Go returns a slice or `nil`. Colors are numbered from 1, and 0 means "uncolored".

The search tree has depth V and branching factor m, which gives:

<Equation label="Search tree" expr="nodes <= 1 + m + m^2 + ... + m^V" result="O(m^V)" />

Pruning with `is_safe` cuts most of that tree in practice, but the bound cannot be improved in general: deciding 3-colorability is NP-complete. The recursion depth is V and the color array has V entries, so space is <BigO of="V" /> beyond the input matrix.

The order in which vertices are visited matters a lot. Coloring the vertex with the highest degree first makes conflicts appear early, so the tree is pruned near its root. This repository uses plain index order.

## Applications

- **Scheduling.** Exams are vertices, a shared student is an edge, colors are time slots; the chromatic number is the minimum number of slots.
- **Register allocation.** Variables that are live at the same time conflict; colors are CPU registers.
- **Map coloring.** Regions are vertices and shared borders are edges. Maps are planar, so four colors always suffice.
- **Frequency assignment.** Transmitters that interfere may not share a frequency.
- **Sudoku.** Cells are vertices and cells in a shared row, column or box are edges, with nine colors.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Forgetting to reset the color.** Without `color[v] = 0` after a failed branch, a stale color blocks the neighbors that are tried next.
- **Asymmetric or self-loop matrices.** The code reads `graph[v][i]` only, so the matrix must be symmetric. A self-loop `graph[v][v] = 1` is never detected, because `color[v]` is still 0 when `v` is checked.
- **Using 0 as a color.** 0 marks an uncolored vertex, so valid colors start at 1.
- **Expecting a minimal coloring from `graph_coloring`.** It returns some coloring with colors in `1..m`, not necessarily one that uses fewer colors. Use `chromatic_number` for the minimum.
- **Assuming the greedy bound is tight.** A graph with max degree d can still need far fewer than d + 1 colors, and an unlucky greedy order can use more than the chromatic number.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why does chromatic_number try m = 1, 2, 3, ... instead of binary search?">
    Binary search would also be correct, because the answer is monotone in m. Linear order is simpler, and the calls with a small m have a small search tree (m<sup>V</sup>), so they are cheap to fail. The most expensive failed call is the one just below the answer, and binary search has to make it too.
  </FaqItem>
  <FaqItem question="What is the chromatic number of common graphs?">
    A graph with no edges needs 1, an even cycle or any tree with at least one edge needs 2, an odd cycle needs 3, and the complete graph on n vertices needs n. The tests in this repository check all of these cases except the tree.
  </FaqItem>
  <FaqItem question="Is there a fast algorithm?">
    Not for the general problem unless P = NP. Two colors can be tested in <BigO of="V + E" /> by checking whether the graph is bipartite. For three or more colors the problem is NP-complete, so practical solvers use better vertex ordering and pruning, or heuristics such as DSatur.
  </FaqItem>
  <FaqItem question="How is this different from the N-Queens search?">
    The pattern is the same: place one item, check constraints, recurse, undo. Here the choice for vertex v is a color and the constraint is its neighbors; in N-Queens the choice for row r is a column and the constraint is the earlier queens.
  </FaqItem>
</Faq>
