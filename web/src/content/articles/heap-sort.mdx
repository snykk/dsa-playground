## How Heap Sort works

A binary heap can be stored in an array without any pointers: the children of index `i` are at `2i + 1` and `2i + 2`, and its parent is at `(i - 1) / 2` (integer division). In a **max-heap** every parent is at least as large as its children, so the maximum sits at index 0. Heap Sort is Selection Sort with a faster way to find the maximum.

<Steps>
  <Step title="Build a max-heap">
    Go through the indexes `n/2 - 1, ..., 1, 0`, and sift each one down: swap it with its larger child while a child is larger. Indexes from `n/2` on are leaves and are already heaps.
  </Step>
  <Step title="Move the maximum to the end">
    Swap `arr[0]` (the maximum) with the last element of the heap. That element is now in its final position, and the heap shrinks by one.
  </Step>
  <Step title="Repair the heap">
    The new root may be too small, so sift it down within the shrunken heap. Repeat steps 2 and 3 until the heap has one element.
  </Step>
</Steps>

<Callout title="The invariant">
During the extraction phase, `arr[0..size-1]` is a max-heap and `arr[size..n-1]` holds the largest elements, sorted, in their final places. Each swap moves the heap maximum to the front of the sorted part, so the sorted part grows by one correct element.
</Callout>

## Pseudocode

```text
heapSort(arr):
    n = length(arr)
    for i = n/2 - 1 down to 0:          # build a max-heap
        siftDown(arr, n, i)
    for end = n - 1 down to 1:          # extract the maximum
        swap(arr[0], arr[end])
        siftDown(arr, end, 0)           # heap is arr[0 .. end - 1]

siftDown(arr, size, i):                 # called heapify in the code
    largest = i
    left = 2 * i + 1
    right = 2 * i + 2
    if left < size and arr[left] > arr[largest]:   largest = left
    if right < size and arr[right] > arr[largest]: largest = right
    if largest != i:
        swap(arr[i], arr[largest])
        siftDown(arr, size, largest)
```

## Implementation

All three versions are the pseudocode above, with the sift-down called `heapify`. Python's `heap_sort` sorts in place and returns the same list; C++ is a template over the element type of a `std::vector` (instantiated for `int` and `double`), returns nothing and returns at once for fewer than two elements; Go sorts a `[]int`. In all three, `heapify` is recursive.

## Complexity analysis

**Extraction** performs `n - 1` sift-downs, each of which walks down at most the height of the heap, <BigO of="log n" />, so it costs <BigO of="n log n" />.

**Building** looks like `n/2` sift-downs of cost `log n`, but most nodes are near the bottom and sift only a little. A node at height `h` costs `O(h)`, and there are at most `n / 2^(h+1)` such nodes:

<Equation label="Build cost" expr="sum over h of (n / 2^(h+1)) * O(h)" result="O(n)" />

<Callout title="Space: O(1) heap, O(log n) stack">
The heap lives inside the input array, so no buffer is needed. The recursive `heapify` in the Python, C++ and Go versions adds up to log<sub>2</sub>(n) stack frames. Writing the sift-down as a loop would bring the extra space to <BigO of="1" />.
</Callout>

## Applications

- **A guaranteed bound without extra memory.** Introsort falls back to Heap Sort when Quick Sort recurses too deep, which keeps the worst case at O(n log n).
- **Partial results.** Stopping the extraction phase after `k` steps gives the `k` largest elements in `O(n + k log n)`.
- **Priority queues.** The same sift-down is the core of a heap-based priority queue.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Starting the build at the wrong index.** The last non-leaf is `n/2 - 1`. Starting from `n - 1` is correct but wastes time on leaves; starting from `n/2` leaves the last parent unfixed.
- **Sifting within the full array.** After each swap the heap size is `end`, not `n`. Passing `n` pulls the sorted elements back into the heap.
- **Unsigned underflow in C++.** `n - 1` wraps around for an empty vector. The code returns early when `n < 2`.
- **Using `>=` in the child comparison.** It still sorts correctly, but it does needless swaps on equal keys.
- **Expecting stability.** Sort `(key, index)` pairs if equal keys must keep their order.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why is building the heap O(n) and not O(n log n)?">
    A sift-down costs as much as the height of the node. Half of the nodes are leaves (height 0), a quarter have height 1, an eighth height 2, and so on, so the total is `n` times the convergent sum of `h / 2^h`, which is a constant.
  </FaqItem>
  <FaqItem question="Is Heap Sort stable?">
    No. Swapping the root with the last element moves it across the whole array, past any equal keys, so the relative order of equal keys can change.
  </FaqItem>
  <FaqItem question="Why is Quick Sort usually faster than Heap Sort?">
    Both are O(n log n), but Quick Sort scans memory sequentially while Heap Sort's accesses jump between distant indexes, and Heap Sort makes more comparisons. That makes Quick Sort friendlier to the CPU cache.
  </FaqItem>
  <FaqItem question="Does Heap Sort use a min-heap or a max-heap?">
    A max-heap, so the largest element can be swapped to the end of the same array. With a min-heap you would get descending order in place, or need an output array for ascending order.
  </FaqItem>
</Faq>
