## How 0-1 BFS works

Many shortest-path problems have only two kinds of move: a free one and one that costs 1. Walking along a road is free and breaking through a wall costs 1; following a cell's arrow is free and changing it costs 1. Dijkstra's algorithm solves them, but its heap costs O(log V) per operation. With weights 0 and 1 a **deque** keeps the same order in O(1).

<Steps>
  <Step title="Start">
    Set `dist[start] = 0`, every other distance to -1 (not reached) and every parent to -1. The deque holds one entry, `(0, start)`.
  </Step>
  <Step title="Pop the front">
    Take the entry `(d, u)` at the front. If `d > dist[u]`, it is stale: `u` was reached more cheaply after this entry was pushed. Skip it.
  </Step>
  <Step title="Relax the edges, pushing to either end">
    For each edge `(u, v, w)` in input order, if `v` is not reached or `d + w < dist[v]`, set `dist[v] = d + w` and `parent[v] = u`. An edge of weight 0 pushes `(d, v)` to the **front**, an edge of weight 1 pushes `(d + 1, v)` to the **back**.
  </Step>
  <Step title="Repeat until the deque is empty">
    Vertices that were never reached keep distance -1 and parent -1. The path to any vertex is read back along `parent`.
  </Step>
</Steps>

<Callout title="Why the front is always the closest">
The deque only ever holds two distances, `d` and `d + 1`, in that order. When the front entry has distance `d`, everything behind it is `d` or `d + 1`. A weight-0 edge gives `d`, which belongs before all of them, and a weight-1 edge gives `d + 1`, which belongs after all of them. So the order never breaks, entries come out by distance exactly as from Dijkstra's heap, and the first time a vertex comes out its distance is final.
</Callout>

A vertex can be pushed twice: at `d + 1` through a weight-1 edge, then at `d` when a free path reaches it. The cheaper entry goes to the front and is processed first. When the older entry comes out later, its distance is above `dist[v]`, and the stale check skips it. Since a distance can drop only once in this way, each vertex is pushed at most twice.

## Pseudocode

```text
zero_one_bfs(edges, n, start):
    adj[u] = (v, w) for each edge (u, v, w), in input order
    dist = [-1] * n; parent = [-1] * n
    dist[start] = 0
    deque = [(0, start)]
    while deque is not empty:
        d, u = deque.popFront()
        if d > dist[u]: continue            # stale entry
        for (v, w) in adj[u]:
            if dist[v] == -1 or d + w < dist[v]:
                dist[v] = d + w
                parent[v] = u
                if w == 0: deque.pushFront((d, v))
                else:      deque.pushBack((d + 1, v))
    return dist, parent
```

`path_to(parent, start, target)` follows `parent` from the target back to the start and reverses the list: `[start]` for the start itself, `[]` when the target was never reached.

## Implementation

Each language takes the edges as `(u, v, w)` triples, the number of vertices and the start, and returns `dist` and `parent`. An undirected edge is given in both directions; self-loops and parallel edges are allowed. A path function reads one path back from `parent`, and the grid example builds the edges of a grid (entering a wall costs 1, a road 0) and runs the search on them.

**Unreachable vertices.** All three report them the same way: distance -1, parent -1, and an empty path. For an unreachable target the path functions return `(-1, [])` in Python, `{-1, {}}` in C++ and `-1, []int{}, nil` in Go.

**Bad input.** A weight other than 0 or 1 is an error, checked for every edge before the search starts, even on a part of the graph the source cannot reach. So are an endpoint out of range, a negative vertex count and a start that is not a vertex: a graph with no vertices has no valid start.

**Which shortest path.** A parent changes only when a distance strictly drops. Entries pushed to the back come out in push order, entries pushed to the front in reverse, and the edges of a vertex are relaxed in input order. Python, C++ and Go follow the same rules and return the same `parent`: the C++ and Go tests check 40 graphs against outputs of the Python code.

## Complexity analysis

Let `V` be the number of vertices and `E` the number of edges. Each vertex is processed once, at its first pop, so each adjacency list is read once: at most `E` edge reads. Each vertex is pushed at most twice and the source once, so there are at most `2V - 1` pushes and pops, each O(1).

The pops include the stale ones. Both algorithms handle about the same number of entries; the difference is that each deque operation is O(1) and each heap operation O(log V). A shortest distance is at most V - 1, so even a 32-bit integer cannot overflow.

## 0-1 BFS vs Dijkstra and BFS

**Against BFS.** When every weight is 1, every push goes to the back and 0-1 BFS is plain BFS: the tests check that its distances equal BFS hop counts on random graphs. BFS alone cannot handle a free edge, since it would put the vertex behind others that are farther away.

**Against Dijkstra.** On weights 0 and 1 both give the same distances (the tests compare them on more than 2000 random graphs), and both skip stale entries in the same way. 0-1 BFS saves the log factor; Dijkstra handles any non-negative weight.

## Applications

- **Grids with walls or obstacles.** Fewest walls to break, fewest obstacles to remove, fewest unsafe cells on a walk.
- **Grids with arrows or currents.** Following the given direction is free and any other move costs 1: fewest arrows to change, least energy against a current.
- **Fewest uses of a resource.** Any problem where most moves are free and some use a coupon, a punch or a change of direction.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Marking a vertex done when it is pushed.** A vertex reached at `d + 1` can be reached again at `d`; compare with `dist[v]` and allow the improvement.
- **Skipping the stale check.** Without `if d > dist[u]: continue`, a stale entry processes its vertex again. The distances stay right, but the work is no longer bounded by E edge reads.
- **Pushing both kinds to the back.** The deque is no longer in order, the first pop of a vertex is no longer final, and a vertex can be pushed again and again.
- **Relaxing on `<=`.** On a cycle of weight 0 every vertex keeps offering the same distance to the next, and the loop never ends.
- **Feeding it other weights.** A weight of 2 breaks the two-distance order. The code rejects it rather than return a wrong answer.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why can't I use a plain queue?">
    A plain queue puts every newly reached vertex at the back. A vertex reached over a free edge has the same distance as the one being processed, so it must come out before the vertices at the next distance. Only a deque can put it there.
  </FaqItem>
  <FaqItem question="Can a vertex be in the deque twice?">
    Yes, once at `d + 1` and once at `d`, when a free path reaches it after a paid edge did. The entry at `d` is processed first; the other is stale and skipped. A third push cannot happen, because the distance has no lower value left to drop to.
  </FaqItem>
  <FaqItem question="What about weights 0, 1 and 2, or other small integers?">
    The deque trick needs the two-distance order, so it works for 0 and 1 only. For small integer weights use Dijkstra, or split an edge of weight k into k edges of weight 1 through new vertices, which pays off only for very small k.
  </FaqItem>
  <FaqItem question="How are unreachable vertices reported?">
    With distance -1 and parent -1, and an empty path, in Python, C++ and Go alike.
  </FaqItem>
</Faq>
