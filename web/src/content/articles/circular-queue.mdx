## What a circular queue is

A queue serves items in first-in, first-out order. A plain array queue wastes space: every dequeue frees a slot at the front that is never used again, or forces all remaining items to shift left. A circular queue fixes this by treating the array as a ring. When an index runs off the end, `% capacity` sends it back to slot 0, so freed slots at the front are reused.

The queue keeps two indices:

- `front`: the slot of the oldest item (the next one to dequeue);
- `rear`: the slot of the newest item (the last one enqueued).

The queue is not stored in index order: it is the slots from `front` up to `rear`, going forward and wrapping at the end. Both indices only ever move forward, by one slot per operation, except that Python and C++ reset them to -1 when the last item leaves.

<Callout title="One formula does all the wrapping">
`next(i) = (i + 1) % capacity`. Dequeue advances `front` with it, enqueue advances `rear` with it, and nothing else ever moves. That is why both operations are O(1).
</Callout>

The API names are `enqueue`, `dequeue`, `peek`, `is_empty`, `is_full` and `size` in Python and C++, and the capitalised forms (`Enqueue`, `IsFull`, ...) in Go. Errors differ per language:

- Python raises `OverflowError` when full and `IndexError` when empty.
- C++ throws `std::overflow_error` when full and `std::runtime_error` when empty.
- Go returns an `error` from `Enqueue`, `Dequeue` and `Peek`.

## Empty versus full

Whether the queue is empty or full, `front` and `rear` alone can look the same: a full ring has `rear` right behind `front`, and an empty ring has no items to point at. The indices need extra information, and there are three standard ways to provide it:

<DataTable
  columns={['Strategy', 'Empty when', 'Full when', 'Cost']}
  rows={[
    ['Size counter', '`size == 0`', '`size == capacity`', 'one extra field, all slots usable'],
    ['Wasted slot (`rear` is the next free slot)', '`front == rear`', '`(rear + 1) % cap == front`', 'one slot is never used'],
    ['Sentinel (`front = -1`)', '`front == -1`', '`(rear + 1) % cap == front`', 'reset both indices when the last item leaves'],
  ]}
/>

The repository uses two of them. Python and C++ use the sentinel: `front == -1` means empty, the first enqueue sets `front = 0`, and removing the last item resets `front` and `rear` to `-1`. They compute `size()` from the two indices. Go keeps an explicit `size` counter, starts with `rear = -1` and never needs a sentinel.

<Callout title="Why the full test is safe">
With the sentinel, the queue is full exactly when `(rear + 1) % capacity == front`, meaning the next slot to write is the oldest item. The empty state is checked first and uses `front == -1`, so the two never collide.
</Callout>

## Pseudocode

```text
enqueue(x):
    if isFull(): error "full"
    if isEmpty(): front = 0
    rear = (rear + 1) % capacity
    queue[rear] = x

dequeue():
    if isEmpty(): error "empty"
    x = queue[front]
    if front == rear: front = rear = -1      # last item left
    else:             front = (front + 1) % capacity
    return x
```

This is the Python and C++ scheme. Go replaces the `-1` bookkeeping with `size++` and `size--`.

## Implementation

All three versions allocate the array once. The capacity must be at least 1: Python raises `ValueError` and C++ throws `std::invalid_argument` for a smaller value, while Go's constructor has no error return, so a capacity of 0 gives a queue that is always full and a negative capacity panics in `make`. The C++ class owns a raw array, so copying is deleted. Python clears a slot on dequeue so the removed object can be garbage collected.

## Applications

- **Streaming and I/O buffers:** a producer writes at `rear` while a consumer reads at `front`.
- **Keeping the last N items:** with an overwriting variant, such as recent log lines.
- **Fixed-size task or request queues** where bounded memory matters more than accepting every item.

## Common mistakes

<Callout tone="warning" title="Watch out for these">
- **Capacity 0.** `% 0` divides by zero. Validate the capacity in the constructor (Python and C++ do).
- **Confusing empty with full.** Without a counter, a sentinel or a wasted slot, `front == rear` is ambiguous.
- **Forgetting to wrap.** Using `rear + 1` instead of `(rear + 1) % capacity` runs off the array.
- **Computing `size` as `rear - front + 1`.** It is wrong after wrap-around, when `rear < front`. Add `capacity` in that case.
- **Copying a C++ queue that owns a raw array.** Both copies free the same memory. The class deletes its copy operations for this reason.
</Callout>

## Frequently asked questions

<Faq>
  <FaqItem question="Why not just shift the elements on dequeue?">
    Shifting makes dequeue O(n). The circular queue moves the `front` index instead, so nothing is copied, and the wrap-around lets the freed slots be reused.
  </FaqItem>
  <FaqItem question="How does the queue know whether it is empty or full?">
    The repository uses a `front = -1` sentinel in Python and C++ and an explicit `size` counter in Go. The other common choice is to leave one slot unused, so that `front == rear` always means empty.
  </FaqItem>
  <FaqItem question="Can a circular queue grow?">
    The bounded version cannot. A growable ring buffer allocates a larger array when full and copies the items in logical order, which makes enqueue amortized O(1). The Deque article describes that design.
  </FaqItem>
  <FaqItem question="Is it thread-safe?">
    No. The implementations here assume a single thread. A ring buffer can be made lock-free only for exactly one producer and one consumer, and that needs careful memory ordering.
  </FaqItem>
</Faq>
